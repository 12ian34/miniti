# Key patterns

Cross-cutting conventions, hot-path rules, and non-obvious gotchas that span multiple files. If you're making changes, check whether any of these apply.

## Logging and diagnostics

- **Debug logging**: `DebugLogger.shared` is an in-memory ring-buffer (1000 entries) with thread-safe `log(_ category:_ message:)`. Categories: `.audio`, `.deepgram`, `.app`; levels: `.routine`, `.recovery`, `.warning`, `.error`. Existing log messages are auto-classified by keywords so routine setup/success/heartbeat lines stay available without dominating the viewer. API keys are automatically redacted via patterns set by `AppState.updateLogRedaction()`. Key instrumentation points: audio device info + format on capture start, route/device-change events, 10-second audio heartbeats, silent-buffer warnings, Deepgram WebSocket/audio/transcript heartbeats, transcript-health watchdog breadcrumbs, managed-mode API request/response failures (including HTTP status + endpoint/body snippet), speaker-name inference decisions, and app state transitions (start/stop recording). On macOS, `AudioObjectAddPropertyListenerBlock` monitors default input/output device changes (critical for diagnosing Bluetooth headphone issues), and device summaries include transport/profile hints for Bluetooth handoffs. On iOS, route-change logs include AVAudioSession category/mode/options, input/output ports, sample rate, and IO buffer duration. `DebugLogView` is accessible by tapping the version text 5 times in Settings — terminal-style viewer with category filters, priority filtering (important entries by default, "show routine" for verbose logs), pretty/raw view modes, copy, and clear. Raw mode enables partial text selection. Log lines stay in the hidden debug buffer/export and are not mirrored to stdout.
- **Expected CoreAudio noise during Bluetooth route handoff (macOS)**: When the default input/output device changes mid-capture (for example AirPods connect while taking/ending a phone call), CoreAudio/HAL may emit transient teardown/rebuild errors such as `!dev`, `!obj`, `who?`, `no object with given ID`, and `throwing -10877`. Treat this as expected if logs show successful restart (`Engine config changed`, `Mic restart complete`, `system audio process tap created`) and capture continues. Treat as a bug only when capture fails to recover.

## Version checks and gates

- **Version check on launch**: `AppState.checkForUpdates()` calls `GET /api/version` once at startup (all modes). It sends `X-Device-ID`, `X-App-Version`, `X-Platform`, and `X-App-Mode` (`"byok"` or `"managed"`) so the backend can create/touch lightweight device records and evaluate the per-platform minimum version. Normal update notices are intentionally absent from the home screen. If the backend returns `min_version` and the running app version is below it, `requiresForceUpdate` is set and a non-dismissable `ForceUpdateView` blocks the entire app (above even terms/onboarding gates) with a download link. Bumping `min_version` on the server instantly forces all older clients to update on next launch — no app release needed. Supported clients clear any stale force-update state. The call remains fire-and-forget (failure is silent — a failed version check never blocks the app).
- **Sparkle auto-update (macOS)**: Sparkle 2 (`UpdateService.swift`) is the sole normal-update UI on macOS. It polls `https://api.miniti.app/appcast.xml` every 24h + on launch + on demand (Miniti menu → Check for Updates…). New versions are downloaded, EdDSA-verified against the embedded public key in Info.plist, installed in place, and relaunched — no manual DMG drag. See [distribution.md](distribution.md). iOS relies on App Store automatic/manual updates.
- **Third-party AI permission (terms versioning)**: `AppState.hasAcceptedTerms` is computed from `acceptedTermsVersion >= currentTermsVersion` (currently `2`, the Deepgram/OpenAI disclosure of 3.3.0) and gates every recording start and every network insight. `TermsAcceptanceView` is the first screen until the current version has been answered either way (`hasAnsweredThirdPartyAIConsent`: accepted or `declinedTermsVersion` at the current version). "not now" opens the app with nothing sent; `startNewMeeting()` without permission sets `showThirdPartyAIConsent`, and the main view presents the same screen as a sheet. Settings, Privacy shows the choice and withdraws or grants it (`setThirdPartyAIConsent`). App init migrates old boolean-only users to version `1`. To force a new answer after a disclosure change, bump `currentTermsVersion`.

## Subscription + mode routing

- **StoreKit state in AppState (iOS)**: `AppStoreSubscriptionService` lives in `AppState.swift` under `#if os(iOS)`. It loads `com.miniti.mobile.pro.monthly`, handles purchase, restore (`AppStore.sync()`), listens to `Transaction.updates`, and publishes `hasActiveSubscription`.
- **Managed Pro fast-path on iOS**: `AppState.isPro` and `isLimitReached` consider local StoreKit entitlement (`hasActiveAppStoreSubscription`) in addition to backend usage response. Display helpers (`displayMinutesLimit`, `displayMinutesRemaining`, `displayUsagePercentage`) keep iOS UI consistent at 5,000 min/month when StoreKit entitlement is active.
- **Pro follows the account (2.8.0)**: the backend overlays a sponsoring device's subscription onto every other installation on the same anonymous account (`lib/accountEntitlement.ts` in `miniti-api`; Polar sponsors any platform, Apple sponsors iOS only). `/api/usage` then reports `tier: "pro"` plus `entitlement_via_account: true`; `UsageInfo.isProViaAccount` / `AppState.isProViaAccount` drive the Settings plan row, which hides "Manage Subscription" for a sponsored device (the Polar portal would 404 with `no_subscription`). Nothing about sponsorship is stored client-side.
- **Move a device to another account (2.8.0)**: `ClientAuthManager.attachToAccount(recoveryKeyInput:)` calls `POST /api/auth/account/attach` (device auth + proof) and, on success, rewrites the stored recovery key, account id, and tokens in place; the device is never signed out and `enrollmentPath` is unchanged. `AppState.attachManagedDevice` refreshes auth status, the device list, and usage. The Settings sheet is `RestoreRecoveryKeySheet(mode: .move)`; `.restore` remains the unenrolled path (which does sign out first). Server refusals map to `ClientAuthError.deviceCapReached`, `.recoveryKeyUnknown`, `.subscriptionConflict` (the moving device and the destination both hold a subscription on the same rail), and change nothing locally.
- Mode-aware service routing: `startRecording()`, `updateLiveInsights()`, `generateFinalInsightsAndSave()`, `generateInsights()` all branch on `appMode`.
- BYOK keys persist in `@AppStorage` regardless of active mode — switching never clears user-entered keys (only Secrets defaults are stripped in managed mode).
- Secrets.swift (gitignored) provides default API keys; Secrets.example.swift is the template. **Only seeded in BYOK mode** — managed users never get Secrets keys written to `@AppStorage`. On switch to managed, any keys matching Secrets defaults are cleared.

## Integrations

- **Google Calendar integration (macOS + iOS)**: OAuth is backend-mediated (Google redirects to the backend, which may currently be served from either `miniti-api.vercel.app` or `api.miniti.app` during host transition; backend stores token in KV keyed by device ID, then redirects back to app custom URL scheme `miniti-google://`). Both targets register `miniti-google` as a URL scheme (macOS via `Miniti/Info.plist`, iOS via `MinitiMobile/Info.plist` `CFBundleURLTypes`). macOS routes the callback through `AppDelegate.application(_:open:)` → `NotificationCenter` → `SettingsView`/`MainWindow` listeners; iOS routes it through `MinitiApp_iOS.onOpenURL` → direct call to `appState.handleGoogleOAuthCallback(_:)`. `googleConnect()` validates `callback_scheme == "miniti-google"` before opening the auth URL and no longer copies the OAuth URL to the clipboard on macOS. `handleGoogleOAuthCallback(_:)` only accepts `miniti-google://oauth-callback?...` payloads; duplicate windows are still collapsed by `AppDelegate.closeDuplicateWindows()` after the open event. `AppState` manages connection status, upcoming events (refreshed every 60s), and `startMeetingFromEvent(_:)` which pre-fills title, calendar event ID, attendees, and any locally prepared notes. Home screen shows "coming up" list of next 5 events across future days when connected (macOS: `UpcomingEventsPanel` + `CompactEventRow` with `DomainFavicon`; iOS: `UpcomingEventsPanel_iOS` + `CompactEventRow_iOS`, no favicons because `DomainFavicon` uses `NSImage`). Attendees are passed to managed insights API for better speaker attribution and MEDDPICC analysis. **Auto-start (both platforms)**: 5-second timer checks upcoming events; when an event's start time is within 16s, shows a countdown banner on the home screen with "start now" and "dismiss" buttons; auto-starts after 15s if not dismissed. Dismissed event IDs are tracked in-memory; cancelled events are skipped. Only fires while the app is foregrounded — iOS cannot wake the app from a calendar event. **Launch-time status check (2026-09-25)**: `refreshGoogleCalendarStatus()` treats a thrown `/google/status` as unknown, never as disconnected (after a reboot with Launch at Login the app often starts before the network), keeps the previous state, and retries on a 5s/15s/45s/120s then 5-minute ladder (`calendarStatusRetryDelay`); only an explicit `connected: false` disconnects. In managed mode the first check runs after `refreshUsage()` so enrollment cannot race it into `notEnrolled`. `recheckGoogleCalendarStatusIfNeeded(trigger:)` re-asks on macOS activation, wake, and iOS foreground while enabled-but-unconfirmed, at most once a minute. `DeviceIdentifier` only mints and persists a new ID when the Keychain read returns `errSecItemNotFound`; any other status logs `device_id_keychain_unreadable` and uses a session-only ID, because a replaced device ID is a Google Calendar disconnect on the backend; while `DeviceIdentifier.isUsingSessionOnlyID` is true, managed enrollment and the calendar status check defer rather than bind state to the temporary identity. **Calendar-aware auto-stop**: when recording from a calendar event and the event's end time passes, `calendarEventEndedWhileRecording` flag triggers a 2-minute silence threshold. **Auto CRM sync (macOS only)**: independent `autoAttioSync` and `autoTwentySync` toggles are hidden on iOS because the CRM integrations are macOS-only. On meeting finalization, Attio searches companies and people while Twenty searches companies for distinct external-attendee domains; exactly one match triggers a note export, while zero or ambiguous matches are skipped. iOS Settings Google Calendar section has enable, connect/disconnect, status, auto-start, and auto-stop controls only.
- **Smart meetings (macOS + iOS)**: `@AppStorage("smartMeetingsEnabled")` defaults true and controls only inferred end/transition assistance. It does not gate configured silence auto-stop, calendar auto-start, calendar-aware auto-stop, one-minute reminders, manual transitions, or recovery. A non-calendar prompt requires meaningful final transcript plus both transcript and audio quiet; its threshold is 2 minutes for a 3-minute auto-stop, 3 minutes for 5, and 5 minutes for Off/10/15. A `:00` or `:30` boundary can bring it forward to 2 minutes only after 15 recorded minutes. One prompt appears per quiet episode; Keep suppresses prompt and auto-stop for five minutes unless real speech resets it. Calendar transition prompts appear within a minute of another event. The 15-second automatic handoff additionally requires the current linked event to have ended, a non-overlapping next event within 15 minutes, both existing calendar automations enabled, and 2 minutes of transcript plus audio quiet; speech cancels it. `PendingMeetingCompletion` makes every end/start action wait for the existing durable transcript-save fence, clear the old session, then attach calendar title/ID/attendees before the next Deepgram connection. In-app state remains authoritative. On macOS every prompt, including quiet and calendar fallback decisions, raises the non-activating floating recording surface when enabled; an already-authorized actionable system notification is mirrored when another app is active or that surface is disabled. iOS preserves background-only notification mirroring. Notification, floating-surface, menu-bar, and main-window actions call the same AppState transaction.
- **Call lifecycle detection (macOS, unreleased)**: `CallActivityMonitor` polls Core Audio process objects at 1 Hz (off-main, public HAL properties only, own PID/bundle excluded) and feeds `AppState.handleCallActivitySnapshot`, which runs the pure `CallLifecycleEngine` (`Miniti/Models/CallLifecyclePolicy.swift`) and acts on its events. Association forms **only at recording start** — from the start prompt's app or exactly one active recognized call; mid-recording calls are transition candidates, never retroactive associations, so an unrelated FaceTime ending can't end an in-person recording. Start prompts need 2s continuous input, are suppressed per uninterrupted call after dismissal, and use `SmartMeetingPrompt` kinds `.callStart`/`.callEnd`/`.callTransition` through the existing prompt/notification machinery. Call-start UI uses the neutral `Meeting detected` title rather than exposing browser/process terminology. Browsers still carry internal `browser` confidence and use a slower 8s/8s debounce+quiet policy versus 4s/5s for native apps, because another tab can mask or mimic a call. A failed HAL process-list query yields an **unreliable** snapshot (`isReliable == false`): policy treats it as "no information", clears in-flight candidates, and never advances start or end detection from it — a coreaudiod restart must not read as the call ending. If AppState can't show an offered start prompt (terms gate, stopped session open), it calls `noteStartPromptNotShown` so the same call is re-offered once the gate clears. The monitor runs only while Smart meetings is on and pauses across system sleep. Reason-code logs only (`supported_call_started`, `ending_grace_kept`, …) — never raw bundle IDs.
- **Ending grace = deferred stop (macOS, shipped in v2.4.0)**: a strong call end (associated app's input stream gone 4s **and** no transcript for 5s — the transcript veto catches push-to-talk/listen-only/release-on-mute; deliberately not audio-level-based because post-call music would block forever) starts a reversible 10s countdown **before** `stopRecording()` is ever called, because `stopRecording()` is irreversible from its first lines (endTime, managed session-end report + credential clear, capture teardown). During grace: `AudioCaptureService.suspendSending()` drops audio pre-accounting (Deepgram sample clock and source log pause together; nothing private is transcribed), the socket stays open on KeepAlive, and the tap watchdogs, transcript-health reconnect, auto-stop, and quiet prompt all stand down (`endingGrace != nil` guards). Keep/reactivation resumes on the **same socket** (no reconnect → no speaker-identity reset) and advances `deepgramTimelineOffset` by the suspended wall-clock so later word times stay on the meeting timeline; Keep also sets a 5-minute `suppressAutoCallEndUntil` that speech deliberately does not clear. Timeout/End now runs the normal `stopRecording()` exactly once (timeout sets the `.callEnded` auto-stop banner). Visibility rule: the main-window check looks for the **identified main window being visible** (`NSApp.isActive` is not proof — only Settings may be open); with no countdown surface, an inactive app with notification authorization gets the notification countdown, and anything else degrades to an ask-first `.callEnd` prompt. Turning Smart meetings off cancels a pending grace and resumes sending. Sleep records the decision (`ending_grace_deferred_to_wake`) and runs the finalization on wake, when async save/report work can actually complete. The quiet fallback prompt now applies to calendar-linked and non-calendar meetings alike, standing down only while another prompt or a grace is on screen. `stopRecording()` now also guards on `isRecording` (the no-content branch never set `isFinalizingMeeting`, so a double stop could double-report managed session end), and markdown re-exports remove the stale file when an AI title change renames it.
- **Recording presence (macOS, shipped in v2.4.0; interaction fixes in v2.4.1; attention routing in v2.5.0)**: menu bar label renders `● REC mm:ss` as one fixed-size text run (ColorPalette.Status.recording, monospaced digits, Reduce Motion-aware pulse) so MenuBarExtra cannot compress the elapsed time away; grace renders `ENDING Ns`. The floating `NSPanel` appears for recording/grace and every Smart-meeting prompt, including quiet and calendar handoffs. A new prompt, recording start, ending countdown, or foreground question/coaching nudge auto-expands the panel and explicitly calls `orderFrontRegardless()` even when the window was already visible; timer ticks never continuously reorder it. Call-start content uses the Miniti ⬢ lockup plus `take notes with miniti`; every action uses the shared `MinitiControlLabel` chrome. The entire full-width header is the disclosure target, with a bordered chevron making expand/collapse visible. A manual collapse is respected until the next meaningful attention transition. Pointer input on the header goes to an explicit AppKit drag handle (`RecordingIndicatorDragHandle`, an `NSViewRepresentable` overlay): a press that travels past the disclosure tolerance moves the window through `performDrag(with:)`, a press released in place toggles disclosure, so dragging never changes expansion. The header stopped relying on `isMovableByWindowBackground` reaching through the hosted SwiftUI Button because macOS 27 keeps the mouse-down in the hosting view (2026-09-25); the Button remains for VoiceOver label, hint, and help text. The panel is non-activating (never steals focus from the call app), all-Spaces/full-screen-auxiliary, drag-anywhere, and follows the independent default-on `showRecordingIndicator` Appearance setting. AppKit never resizes a borderless panel to its SwiftUI content: the coordinator owns expansion state (`RecordingIndicatorModel`), resizes to the hosting view's `fittingSize`, anchors the nearest horizontal edge while growing downward, and clamps the entire frame inside the chosen display rather than accepting a partial intersection. Every button calls the same AppState methods as the main window, menu bar, and notifications. Its Open meeting action calls the centralized activate/restore-or-recreate transaction, so an existing main window is unhidden and ordered front regardless of the non-activating caller, while an X-closed SwiftUI scene is recreated with bounded retries rather than mistaken for a usable hidden window. The menu bar segment count uses `liveSegments.count` — the array is finalized-only by contract; never reintroduce a per-tick `.filter`.
- **Calendar meeting filters (2.8.0)**: `upcomingEvents` is derived, never assigned from the network directly. `fetchUpcomingEvents` requests `include_filtered=true`, stores every non-cancelled event in `fetchedCalendarEvents`, and applies `calendarMeetingFilters` (`MinitiAPIService.CalendarMeetingFilterPreferences`, UserDefaults `calendarMeetingFilters.v1`, saved as absent when equal to the defaults so a future default change applies). Changing the preferences re-derives the list and reschedules reminders without a refetch. `CalendarEvent.skipReason(under:)` is the single rule: all-day, self-declined, Google `eventType` (outOfOffice / focusTime / workingLocation / birthday), then a title-prefix match at a word boundary. The backend's `skipReason` field is informational only. Settings UI is the shared `CalendarMeetingFiltersSection` (in `ManagedAccountViews.swift`, used by both Settings views); its preview calls `previewCalendarMeetingFilters()`.
- **Calendar discoverability nudge (v1.24.1)**: When Google Calendar is disabled or disconnected AND `calendarNudgeDismissedUntil <= now`, the home screen shows a `CalendarNudgeCard` (macOS) / `CalendarNudgeCard_iOS`. "connect calendar" enables the integration and kicks off OAuth via `startCalendarConnectFromNudge()`. "not now" calls `snoozeCalendarNudge()` (30-day hide). × calls `dismissCalendarNudgeForever()` (~10-year hide). State is in `@AppStorage("calendarNudgeDismissedUntil")` as a Double timestamp.
- **CRM send (macOS history only)**: Attio and Twenty are independently enabled from Settings and appear as provider-specific actions on saved meeting detail. Both use the shared `CRMSendSheet`: an unconnected sheet is read-only except for Connect, Search/Send stay disabled, actions use semantic controls and neutral scope tabs, and provider colors identify integration content only. Enabling task creation reveals the complete task preview; every row shows the exact deadline policy, assignee policy, and linked record, starts selected, and can be unchecked without removing that action item from the exported meeting note. The client sends an explicit `tasks` array and disables the legacy task switch, so an older backend safely creates no tasks instead of recreating excluded ones; the compatible backend honors the explicit list while older clients can keep using `create_tasks_from_action_items`. OAuth is backend-mediated and device-keyed; the backend returns through `miniti-attio://` or `miniti-twenty://`, both registered in `Miniti/Info.plist` and forwarded by `MinitiApp.onOpenURL` through provider-specific notifications. Sheet presentation resolves the Keychain-backed device ID off-main, and requests have bounded waits (status 10s, connect/search 15s, send 30s). Frontend calls additive `/api/{attio|twenty}/connect/start`, `/status`, `/search`, and `/send` routes and fails gracefully against older backend deployments. App payload omits full transcript by default; the backend also ignores transcript from older clients. Twenty Cloud search covers people, companies, and opportunities; sends create a Note + NoteTarget and optional Task + TaskTarget records. Attio previewed deadlines are submitted explicitly; Twenty tasks currently show and use no deadline, matching its current send contract. Twenty OAuth uses authorization code + PKCE, server-side refresh tokens, and dynamic client registration when fixed `TWENTY_CLIENT_ID` credentials are absent; self-hosted Twenty is not yet exposed in the app.

## Live insights pipeline

- **Decoupled live insights**: `updateLiveInsights()` runs Summary insights inline (applies immediately, clears `isGeneratingInsights`), then fires Questions and—only when `salesInsightsEnabled` is true—Sales/MEDDPICC as separate background tasks via `updateQuestionsInBackground()` and `updateMeddpiccInBackground()`, each gated by its own `isGenerating*Insights` flag. They never block each other. `fetchLiveInsights(mode:...)` is the shared helper for Summary/Sales/Questions. Playbook (`.docs`) is **not** part of this pipeline — it maintains an updating topic list via its own cadence branch (`refreshDocsTopics()` extracts lookup-worthy topics ~every 20s while Playbook is active), then looks up each topic independently. `switchInsightsMode()` opts a selected specialist view in, schedules Coaching recomputation, and seeds Playbook topics on first visit. Managed Sales requests retry once on transient timeout/network failures. Questions cadence is staggered 22s after Summary (vs 15s for enabled Sales). Questions use the rolling-state planner in both BYOK and managed mode.
- **Client insights reliability (v1.13.0, retuned v2.0.3)**: Summary, Sales, and Questions live insights share one incremental request planner. After two successful responses, the client switches from full transcript requests to a recent-window + delta payload (10k recent chars, fallback to full when delta exceeds 35k chars). Managed mode only advances cursors for non-degraded responses and rejects stale/out-of-order responses. Warmup still fires at 4 segments (Summary) or 6 (Questions and enabled Sales), with failed warmup cycles capped to one attempt per 30s. Steady state is mode-specific: Summary requires 60s + 4 new segments (120s maximum-age escape hatch), Questions 60s + 6 (120s max), and enabled Sales 90s + 8 (180s max). Every policy also gates on the last attempt—not only the last success—so persistent network failures cannot turn the 5s scheduler tick into a retry storm. The maximum-age path lets a quiet meeting update once it has any new final text instead of starving on segment count. Manual update generates only the selected view; stopping always refreshes Summary and Questions, plus Sales when it is enabled.

## Transcript + live UI

- **Transcript speaker-turn batching**: streaming-finalized chunks from the same resolved speaker are rendered under one speaker/timestamp header until the resolved speaker changes. Sentence punctuation does not start a new visual turn. The live lazy-row cache replaces only its final rendered speaker turn when segments append; speaker renames, self-speaker changes, or non-append mutations trigger a full turn-cache rebuild. Saved/trim-enabled transcripts omit repeated headers while retaining one native render span per stored segment, so copy and precise trim mapping still work without changing persisted transcript data.
- **Interim presentation throttle (v2.0.3)**: `TranscriptRuntimeState` publishes interim text + current/interim speaker as one revisioned snapshot. `TranscriptView` presents non-empty snapshots at most every 125ms and coalesces scroll-to-bottom work, while empty/final clears apply immediately. A revision guard prevents an older throttled fragment from reappearing after a final; pending scroll work re-checks the user-controlled auto-scroll lock before moving. Raw runtime state remains current for stop-time transcript preservation and iOS Live Activity updates.
- **Markdown transcript speaker labels**: Transcript markdown export uses each segment's computed `speakerLabel` (for example `You`) instead of always rendering generic numbered labels.

## Design system code contract

- All colors route through `ColorPalette` in [`Miniti/Models/ColorPalette.swift`](../Miniti/Models/ColorPalette.swift) — never hardcode hex literals in view code. If a value is missing from the palette, add it to `ColorPalette` and reference it, don't inline it.
- `Theme` aliases in `MainWindow.swift` are convenience shorthand that resolve to `ColorPalette` tokens.
- `Color(hex:)` is defined in `ColorPalette.swift`. The Live Activity widget extension is a separate target and duplicates a handful of palette values as private constants at the top of `MinitiLiveActivityLiveActivity.swift` — when a palette token used there changes, update the mirrored constants by hand.
- Typography uses the Apple system font for readable prose, controls, and primary Home / Coaching / History navigation. The wordmark remains the deliberate monospaced identity exception; timers/counters use monospaced digits. Transcript and insight prose share the same size and line spacing at each interface scale. Dark mode only.
- Full spec: [../design.md](../design.md) (Google DESIGN.md format — colors, typography, spacing, components, contrast rules, do's and don'ts). Read it before making visual changes; keep it updated when the design changes.

## AppStorage settings + audio recovery
- **Share Diagnostics defaults on (2.8.0)**: `@AppStorage("shareDiagnostics")` defaults to `true` in `AppState` and both Settings views (keep the three in sync). The default only applies to an unset key, so anyone who switched it off stays off. Events are still gated to managed mode with no transcript or audio content (`enqueueDiagnosticEvent`), and `ScreenshotMode` forces it off. The privacy page on miniti.app describes it as on by default.
- **Filler counting (P0.8, 2.8.0)**: per-speaker filler stats and the live filler-rate nudge use `TrainingMetrics.countFillerOccurrences(of:in:)`, a one-pass longest-match scan across every configured phrase, so a token is never counted twice ("uh huh" is one "uh huh", not also an "uh"). `countPhraseOccurrences` remains for single-phrase presence checks (sales signals). Coaching copy calls the number "detected fillers" and a floor, because Nova-3 under-transcribes hesitations.

- `AppState` is the single source of truth, injected via `@EnvironmentObject`.
- `AppMode` enum (`.byok` / `.managed`) stored in `@AppStorage("appMode")` — purely a routing toggle.
- `InterfaceScale` (`compact` / `standard` / `large`) is stored in `@AppStorage("interfaceScale")` and injected into every scene. Compact pins the legacy metrics; transcript sizes and leading differ by platform, and both live and saved transcript builders must receive the same scale values.
- **Reduce Motion**: both app roots apply `minitiReduceMotionAware()`, which clears descendant animation transactions when the system accessibility setting is enabled. Continuous decorative views still branch on `accessibilityReduceMotion` so they stop scheduling animation frames entirely.
- **Adaptive shell state**: macOS uses `.contentMinSize` window resizing and persists sidebar/history/insights collapse choices. The left sidebar collapses once recording actually begins, stays user-controllable during the recording and stopped/resumable state, then expands when the session is saved, discarded, or left via Home. Below the width needed for the expanded sidebar plus transcript/insights pane minimums, the shell keeps a 52pt compact rail in the layout and opens the full 220pt sidebar as a dismissible overlay drawer; it never overwrites the user's saved wide-window preference. This prevents an oversized `HSplitView` from clipping the window's leading edge while retaining History, Coaching, search, and keyboard access. Main-window destinations (Home, Coaching, saved meetings) also feed a browser-style back/forward stack. A passive AppKit scroll-event observer recognizes only completed, dominant, precise horizontal trackpad gestures; it returns events unchanged, ignores sheets, momentum, and ordinary text editing, but permits a focused meeting-search field and automatically blurs that field when navigation commits. It prunes deleted meetings and clears forward history after a new visit. Eligible swipes drive a neutral edge progress cue and commit only after the shared `NavigationGesture` distance/dominance thresholds. iPhone always keeps bottom tabs; regular-width iPad uses adaptive sidebar/split navigation. Keep the `miniti` label monospaced in any custom navigation shell.
- **Live Activity privacy**: `liveActivity.showTranscript` defaults to `true`. Every ActivityKit state update passes transcript text through `LiveActivityPreferences.presentedTranscript`; changing the setting refreshes the current activity immediately. The widget URL uses `miniti://meeting/<id>` to route back to the Record tab.
- **Undo + inline status**: reversible transcript trims and speaker identity/name edits register with the platform `UndoManager`; keep the existing nearby “saved”, “exported”, and “copied” confirmations rather than introducing success alerts.
- Audio levels: `AudioLevelsState` publishes mic, system, and combined meters as one atomic snapshot. The independently sampled service publishers are coalesced to a 20 Hz display cadence so waveform views invalidate once per frame rather than once per property.
- Audio monitoring: opt-in "test audio" button on home screen starts lightweight capture (no Deepgram) to verify sources before recording. On macOS, `AudioSourcePanel` uses local `@State isTesting`; on iOS, `isMicTesting` in `ReadyStateView_iOS`. Monitoring stops on view disappear or when the user taps stop.
- **Audio engine/device-change recovery**: Both macOS and iOS listen for `AVAudioEngineConfigurationChange`. On macOS, route changes trigger a guarded full mic restart and dynamic converter rebuild based on callback format (tap installed with nil format), with coalescing/rate-limit checks to avoid restart storms. Default output changes schedule a debounced system-tap restart and reset recovery timers so the app does not immediately re-restart. On iOS, route changes are actively inspected for input-identity changes and trigger a debounced proactive mic restart (not just logging), improving Bluetooth route/profile reliability. Observer lifecycles are cleaned up in `stopMicrophoneCapture()`. See [audio.md](audio.md) for the full recovery state machine.
- **Deepgram reconnect + transcript starvation watchdog**: While recording, Deepgram connection errors/disconnects trigger bounded reconnect attempts (1s/2s/5s). A transcript-health watchdog also triggers one reconnect cycle if speech-like audio levels continue but no transcript arrives for an extended window, and recording continues during transport recovery. On macOS mic+system captures, reconnect uses `multichannel=true` again, flushes pending genuine mic text, clears the echo-comparison buffer, and reconnects with `preserveSpeakerIdentities: true` so the identity allocator hands the new socket fresh, collision-free app speaker IDs (see the reconnect identity pattern below). `resetSourceTracking()` clears the source-energy log so its stream times realign after reconnect. Before every managed connect/reconnect, `AppState` refreshes the Deepgram JWT via `/api/session` when missing or within 60s of `expires_at`, then configures Deepgram with `Authorization: Bearer …` (BYOK stays `Authorization: Token …`). Reconnect-only JWT refresh may create a new backend `session_id` (session-count churn is acceptable until a lighter token-refresh endpoint exists); `/api/session/end` still runs only when the meeting actually stops.
- **macOS multichannel Deepgram (mic+system)**: dual-source sessions send interleaved stereo PCM (`ch0=mic`, `ch1=system`) and connect with `channels=2&multichannel=true`. `channel_index` and an explicit `TranscriptSource` are carried through transcript updates, finalized segments, `LiveSegment.source`, save snapshots, and the optional `TranscriptSegment.sourceRaw` column (nil on all legacy rows; additive, lightweight-migratable). Both channels retain Deepgram's per-channel diarized IDs, mapped to collision-free app speaker IDs by `SpeakerIdentityState` (system → low range, microphone → `1000 + n`; `1000` reserved for the first mic speaker and legacy meetings). Mic-channel finals pass conservative playback-echo reconciliation before commit: clear mic energy commits immediately; ambiguous mic finals wait for a time-aligned fuzzy text match on the system channel; short matches also require system-dominant energy. A non-match is released as soon as the system transcript watermark passes it, with a four-second fallback if the system channel does not advance. Unrelated overlapping mic speech is preserved. No mono mix / dual AGC or destructive acoustic cancellation is used.
- **Mic speaker promotion (v2.7.0)**: `segmentBySpeaker` gates the first speaker of every response like a mid-response switch: an unconfirmed, non-privileged first speaker is a candidate away from `SegmentationState.lastCommittedSpeakerBySource[source]` and folds into it until `PendingSpeakerEvidence` passes. `MicSpeakerPromotionPolicy` (`standard` 6 words / 1.5 s / 0.65, `strict` 12 words / 4 s / 0.85) applies to additional mic IDs (1001+) only; `AppState.evaluateEnvironmentInference` pushes `strict` while the environment is `remoteLikely`. Promotion evidence is written back from finals only, never from cumulative interims, which replay the same words. `MeetingEnvironmentInferenceEngine` promotes remote to hybrid only after `hybridSecondaryMicSpeechSeconds` (20 s) of speech from non-primary mic IDs, so one promoted clone cannot flip the policy back. Context evidence (call app, calendar link) is refreshed at meeting start and the persisted environment is reconstructed on resume (`restoreEnvironmentInference(from:)`). `ImplicitSelfPolicy.allowed` keeps "You" on 1000 in remote-likely meetings even with several mic IDs; unknown, in-room, and hybrid keep the no-assumption rule.
- **Speaker identity across Deepgram reconnects (v2.5.0)**: Deepgram's speaker numbers restart at 0 on every new socket, so `SpeakerIdentityState.beginConnection(preservingIdentities: true)` allocates the new socket **fresh, collision-free app IDs** instead of reusing old ones — system speakers get the next sequential low IDs, mic speakers get the next `1000 + n` slots, with one continuity rule: while the meeting has seen at most one mic speaker, the next socket's first mic speaker maps back to `1000` (preserving the shipped single-user "You" contract). Because old app IDs stay valid for old segments, `resetSpeakerIdentityForDeepgramReconnect()` now *preserves* all names, overrides, and self marks and only resets the naming-cadence counters so inference re-runs for the new identities; identically re-inferred names merge presentation via the name-keyed display group. Resume-after-relaunch seeds the allocator from restored segment IDs (`seedRestoredSpeakerIdentities`). Covered by `testResetSpeakerIdentityForDeepgramReconnectPreservesIdentities` and `testSpeakerIdentityAllocationAcrossReconnects`.
- **Managed session-end durability queue**: If managed `session/end` reporting fails, the app persists pending reports locally and retries on launch, foreground, and after managed-session success paths. `managedSessionId` is only cleared after successful acknowledgment or durable queue persistence.
- `@AppStorage` persists API keys, audio source toggles, app mode, onboarding state, terms acceptance state (`acceptedTermsVersion` + legacy `hasAcceptedTerms`), markdown export settings (`autoExportMarkdown`, `markdownExportFolderPath`, `generateAgentsMd` — macOS only), webhook URL (`webhookURL`), auto-stop timeout (`autoStopMinutes`, default 5, 0 = disabled), default transcription language (`defaultLanguage`, default `"en"`), personal transcription dictionary (`personalDictionaryTerms.v1`, JSON-backed list sent as Deepgram keyterms), Google Calendar integration (`googleCalendarEnabled`, `autoAttioSync`, `autoTwentySync`, `autoStartFromCalendar`, `autoStopFromCalendar`), CRM surfaces (`attioExportEnabled`, `twentyExportEnabled`), calendar-nudge state (`calendarNudgeDismissedUntil`). Transcription is fixed to Nova-3. There is no model selector: BYOK requests use pinned `gpt-5-mini-2025-08-07`; managed requests are selected server-side between pinned `gpt-5-mini-2025-08-07` for incremental updates, speaker naming, catch-up, and Playbook topic extraction, and pinned `gpt-5.4-mini-2026-03-17` for non-incremental summaries, MEDDPICC, questions, and grounded Playbook answers.
- **Dictionary corrections (v2.7.0)**: `PersonalDictionaryPreferences.correctionsStorageKey` (`personalDictionaryCorrections.v1`) holds up to 100 `CorrectionPair`s (`heard` lowercased, trimmed, collapsed, colons stripped; `correct` as typed). Write through `upsertCorrection(heard:correct:)`, which replaces an existing `heard` (last write wins) and returns `.saved` / `.invalid` / `.full`; never append to the array and re-save, that path silently drops duplicates. Saving also adds `correct` to the term list. Each connect appends `replace=heard:correct` after the keyterms. `AppState.transcriptCorrector` (a `TranscriptCorrector`, nil when the store is empty so the hot path costs nothing) applies precompiled longest-first word-boundary regexes with `escapedTemplate` replacements to every new final before it reaches `liveSegments`, to interim text on publish, and, on "fix earlier mentions", once over `liveSegments` in a single assignment (`applyRetroactiveCorrectionsToLiveTranscript`, never from `handleSpeakerSegments`). Saved meetings use `applyDictionaryCorrection(heard:correct:to:)` plus `Meeting.markTranscriptCorrected()`, which bumps the revision without clearing insights (trim still clears). macOS live UI: the pane's `Coordinator` is the `NSTextViewDelegate`; it publishes only the snapped heard text into `LiveTranscriptSelectionState` (no geometry: the screen-to-SwiftUI rect conversion of an unflipped AppKit rect was the cause of an invisible popover), the pill in `TranscriptView` anchors the popover on itself and stays mounted while editing, and `requestDeselect()` collapses the native selection after save. `TranscriptCorrectionSelection.snappedHeardText` scans a window of `maxCharacters` either side of the selection, never the whole document, and rejects selections that cross a paragraph or reach into interim text.
- **Deepgram keyterms**: each connect merges (1) system defaults (`Miniti`, `Lightdash`, `Ahuja`), (2) personal dictionary terms, (3) session terms from `AppState.deepgramSessionKeyterms()` — meeting title + non-self attendee display names + non-consumer email domains — capped at 100. Rebuilt on every connect/reconnect so calendar-started meetings pick up fresh attendee names.

## Export, webhooks, history management

- **Markdown auto-export (macOS only)**: When `autoExportMarkdown` is enabled, finalized meetings are written as `.md` files to a local folder (default `~/Documents/miniti/`). Trigger points: `goHome()` (reads live AppState data synchronously before `clearCurrentSession()` to avoid async save queue timing issues), `generateInsightsForMeeting()` (re-exports after insight updates from history), and a manual "export" button in `MeetingDetailView`. Filenames are dev-friendly with no spaces: `yyyy-MM-dd-HHmm-sanitized-title.md`. Section order: notes → insights (including MEDDPICC) → Coaching metrics → transcript (high-value content first). Optional `AGENTS.md` index file lists all exported meetings for AI agent discovery. All export code is guarded with `#if os(macOS)`.
- **Webhook transport (P0.9, 2.8.0)**: `WebhookService.validate(_:)` is the single rule for both Settings views and `send`: HTTPS with a host, or `http://` only to a loopback host (`localhost`, `127.0.0.1`, `::1`) for a hook on the same machine. Anything else is refused at send time as well as flagged in Settings, so a stored plaintext URL from an older version stops being used. Logs and exported diagnostics only ever carry `WebhookService.redactedEndpoint` (scheme + host), never the path or query where Zapier/Make/n8n keep the hook secret; `URLError` text is reduced to its code, and `updateLogRedaction()` also registers the full webhook URL as a redaction pattern.
- **Outbound webhooks**: When `webhookURL` is non-empty, a JSON POST is fired on meeting finalization (`goHome()` with event `meeting.saved`) and after insight regeneration for saved meetings (`generateInsightsForMeeting()` with event `meeting.updated`). Payload includes title, start date, end time, duration, language, summary, action items, key decisions, topics, discussion flow, notes, MEDDPICC, Coaching metrics (serialized under the backward-compatible `training` field; per-speaker fillers/min, pace, talk ratio, monologue length, questions, clarity), suggested questions (array of `{question, type, context}`), speaker count, full transcript (array of `{speaker, text, timestamp}` entries with human-readable speaker labels like "You" and "Speaker 2"), and optionally `calendar_event_id` and `attendees` (array of `{email, name, domain}`) when meeting was started from a calendar event. Coaching metrics are computed from transcript segments at send time. Fire-and-forget via `Task.detached`, 10s timeout, success/failure logged to `DebugLogger`. Configurable in Settings on both macOS and iOS. Works with Zapier "Webhooks by Zapier", Make, n8n, and any HTTP endpoint. **Known caveat kept intentionally for now**: Settings currently treat both `http://` and `https://` as valid, and failure/non-2xx logs currently include the full webhook URL; if a user embeds a secret in the URL itself, that secret can land in exported debug logs.
- **Saved transcript trimming**: Trim is only available on saved/stopped meetings. The UI keeps one native `SelectableTextView` so users can still copy arbitrary transcript spans, then maps body-text selections back to `TranscriptSegment` UTF-16 ranges for deletion. macOS also treats Backspace/Delete as "delete selection" only when a real transcript body selection exists. Every trim shows a confirmation warning that Summary, Sales, Questions, and Playbook insights will be cleared and must be regenerated. `AppState.applyTranscriptTrim(_:to:)` is the only mutation entry point: it deletes/updates persisted segments, marks `transcriptEditedAt`/`transcriptRevision`, clears generated insights so deleted content cannot leak through derived text, saves SwiftData, re-exports markdown on macOS auto-export, and fires a `meeting.updated` webhook from the trimmed meeting. Undo restores the previous transcript snapshot only; it intentionally does not restore old insights.

## Persistence commit policy (v2.9.0, roadmap P0.3)

- **Never write `try? modelContext.save()` in production code.** Every user-initiated mutation goes through `AppState.commit(_:in:mutate:revert:)` and every fetch whose failure must not read as "no meetings" goes through `AppState.fetchMeetings(_:in:)` / `load(_:_:)` (`Miniti/Models/AppState+Persistence.swift`). `grep -rn "try? .*\.save()" Miniti MinitiMobile` must return only `ScreenshotMode.swift`. The operation enum (`PersistenceOperation`) names the user action; its `userLabel` is the banner copy.
- **What a failure does**: runs the site's explicit `revert` (pin toggles back), logs `Persistence save FAILED op=… domain=… code=…` (never `localizedDescription`, which can echo attribute values), queues a `persistence_save_failed` / `persistence_load_failed` diagnostics event with only `op`, `domain`, `code`, and sets `appState.persistenceIssue`, rendered once per platform by `PersistenceIssueBanner` (mounted in the entry points via `.persistenceIssueOverlay()`). A later success for the same operation clears it; dismiss and a successful retry clear it too.
- **Never call `ModelContext.rollback()`**: SwiftData traps (`ModelSnapshot.swift:46 Unexpected backing data for snapshot creation`) when a pending cascade delete is rolled back, and the live-transcript queue shares `mainContext`, so a rollback would also discard its unsaved work. A failed delete or discard therefore stays pending in the context, keeps its `noteMeetingDeleted` mark, and is committed by the banner's retry or by the next successful save. The list hides it meanwhile; it reappears only if the app relaunches before any save succeeds.
- **Retryable or not**: everything is retryable (the stored `mutate` runs again, then save) except `staleMeetingFinalize` (next launch retries and no `PendingSessionEndReport` is queued for a finalization that did not persist) and `liveTranscript` (the 60 s queue retries itself; the banner is raised once per outage, not per tick).
- **Fetch failure is not empty history**: `MainWindow.refreshMeetings()` keeps the previous list, `resumeInterruptedMeeting()` reports instead of silently landing on Home, and `clearManagedSessionReference` reports instead of leaving `managedSessionId` set.
- **Corrections**: `applyDictionaryCorrection` returns `.saveFailed` when the store rejects the rewrite; the three editors already render `message(...)`, so the user sees "correction didn't save. try again" instead of a quietly closed editor.
- **Tests**: `PersistencePolicyTests` injects failures through `AppState.persistenceSaveHandler` / `persistenceFetchHandler` and asserts events through `AppState.diagnosticEventObserver`. `enqueueDiagnosticEvent` never queues from the XCTest host (it shares this device's defaults and enrollment with the installed app).

## Custom insight templates (v2.9.0, roadmap P2.1)

- **One shape**: custom templates are plain `InsightTemplate` values with ids `custom_…`, stored as JSON in UserDefaults (`customInsightTemplates.v1`, `CustomInsightTemplates.swift`). The request path, the specialist view, exports, webhooks, and CRM notes never branch on built-in vs custom.
- **Resolve through AppState**: `appState.insightTemplate(id:)` (built-in first, then custom) and `availableInsightTemplates`. Never call `InsightTemplate.builtIn(id:)` from a view or a request path; the only remaining callers are the resolver itself and `Meeting.insightTemplate`.
- **Meetings keep their own copy**: `Meeting.applyInsightTemplate(_:)` writes `insightTemplateID` and, for custom templates, `templateDefinitionJSON`; `Meeting.insightTemplate` decodes it when the id is not a built-in. Editing or deleting a template never changes a saved meeting. Assign templates to meetings only through `applyInsightTemplate`.
- **Keys**: section keys derive from titles via `CustomInsightTemplates.baseSectionKey` (ASCII-folded, `^[a-z][a-z0-9_]{0,31}$`, the backend's `TEMPLATE_KEY_PATTERN`); two titles with the same base key are a validation error, not a suffix. `InsightTemplateDraft.problems` is the single source of editor validation and mirrors the limits on `InsightTemplate`.
- **Preview** (`AppState.previewInsightTemplate(_:using:)`) runs the normal template request against a saved meeting's transcript and returns sections without writing anything.
- **Deliberately absent**: free-text prompts and cross-device sync. Export/import of one template as JSON (ids regenerated on import) is the manual transfer path.

## Persistent store open (v2.9.0, roadmap P0.2)

- Both entry points call `PersistentStore.open()` instead of `fatalError`. A failed read-write open logs one content-free `Persistent store open FAILED: category=… domain=… code=… reason=…` line, tries a read-only open so meetings can still be exported, and renders `StoreRecoveryView` as the first gate branch (before force-update and terms). The store file is never deleted, moved, or recreated; "try again" simply reopens it.
- `PersistentStoreOpenFailure.classify` walks the underlying-error chain (CoreData migration codes, `NSSQLiteErrorDomain`, POSIX/file codes, then text) and, when SwiftData hides the CoreData error, falls back to the SQLite header preflight (`fileHasForeignHeader`). Paths in the reason are redacted to `~`.
- While the store is down, `AppState.persistentStoreFailure` is set: Settings disables Export All and Granola import, macOS `Settings` and the main scene get an in-memory fallback container so `@Environment(\.modelContext)` never traps, and the Debug Log window keeps working (it needs no container).
- Debug builds honour `-MinitiStoreURL <path>` so the recovery screen can be exercised against a scratch file; see the manual drill in [testing.md](testing.md).

## Save queue, discard, resume

- **Segment persistence**: `saveCurrentMeetingIfNeeded()` snapshots current live state, enqueues a save payload, computes a segment diff plan off-main, then applies an incremental sync (`delete missing IDs`, `upsert changed/new IDs`) to `meeting.segments`. New segments are collected first and appended to the SwiftData relationship in one mutation; never append each segment separately while a saved meeting detail may already be observing that relationship. Segment IDs persist from `LiveSegment.id`, so resumed sessions update incrementally instead of full rebuilds.
- **Lifecycle save fences (v2.0.3)**: The save queue stays async so transcript diffs never block UI, but `saveCurrentMeetingAndWait()` returns only after its exact revision—or a newer coalesced revision for the same meeting—has committed to SwiftData. iOS begins a named UIKit background task before awaiting that fence and ends it exactly once on completion/expiration. macOS returns `.terminateLater` for a dirty session, awaits the same fence, and replies to AppKit after commit or a five-second fail-open timeout; never block the main actor with a semaphore in termination handling.
- **Discard meeting**: `discardCurrentMeeting()` deletes the current meeting from SwiftData, ends Live Activity (iOS), and clears the session without saving. Used from the "discard" button (with confirmation alert) when a recording is stopped.
- **Deleted meetings must never be resurrected**: `persistMeetingSavePayload` inserts the meeting into the `ModelContext` on first save, and the off-main segment diff before that insert is a suspension point — so a save that was already in flight can resume *after* the user discarded, re-insert the deleted meeting, and make it reappear in history. `deletedMeetingIDs` is the single record of "this meeting is gone": `discardCurrentMeeting()` adds to it, and so must every history delete via `noteMeetingDeleted(_:)` *before* `modelContext.delete(_:)` (macOS `MainWindow.deleteMeeting`, iOS `HistoryView_iOS.deleteMeetings`). A delete removes pending work only for that meeting rather than cancelling the shared serialized worker, which may also be carrying another meeting's terminal save. Anything that resumes after a suspension point re-checks `isMeetingDeleted(_:)` — `persistMeetingSavePayload` plus every history regeneration path (`generateInsightsForMeeting`, `refreshDocsTopics(for:)`, `lookupDocTopic(id:for:)`), which otherwise write insight fields into a row the user deleted minutes later. The payload snapshots its ID *before* the suspension point too, since reading a property of a dead model traps. Don't replace this with a `currentMeeting?.id == payload.meeting.id` / `modelContext != nil` heuristic: `goHome()` enqueues the save and then clears `currentMeeting` synchronously, so identity checks silently drop the final save of a meeting that had never been persisted.
- **Recording timer**: Uses date-based computation (`recordingStartDate`) instead of incrementing a counter. `Timer.scheduledTimer` fires every 1s and computes `Date().timeIntervalSince(recordingStartDate)`. This ensures accurate duration even when the app is backgrounded on iOS (timer may not fire reliably, but duration is correct when it does). Paused time is excluded by re-anchoring `recordingStartDate` from the accumulated active duration on resume; `recordingStartDate` is cleared on stop and `goHome()`.
- **Auto-stop on silence**: `autoStopTimer` fires every 30s during recording and compares `CFAbsoluteTimeGetCurrent() - lastTranscriptReceivedAt` against `autoStopMinutes * 60`. If the gap exceeds the threshold, calls `stopRecording()` and sets `wasAutoStopped = true` plus an `autoStopReason`, whose `label`/`icon` drive the amber banner in the stopped state on both macOS and iOS. Keep the reason honest: `.silence` says "no speech detected", `.stalledPipeline` says transcription stopped responding, because telling someone the room was quiet when their meeting was in full flow is how the original bug was reported. `wasAutoStopped` is cleared on `startNewMeeting()` and `goHome()`. Timer starts in `startRecording()`, stops in `stopRecording()` and `clearCurrentSession()`. Configurable in Settings: off (0), 3, 5 (default), 10, or 15 minutes. **Calendar-aware**: when `autoStopFromCalendar` is on and a calendar event's end time passes during recording, the silence threshold drops to 2 minutes regardless of `autoStopMinutes`. `calendarEventEndedWhileRecording` flag triggers an amber banner in the recording header. The auto-stop timer also runs when `autoStopMinutes == 0` if a calendar event is active.
- **Auto-stop must not fire on a stalled transcript pipeline**: a transcript gap means "no words came back", which is only the same thing as "nobody is talking" while the transcript pipeline is healthy. If Deepgram drops or system audio stops being captured, the gap grows while people are still talking, and auto-stopping there kills a live meeting under a misleading "no speech detected" banner. So the decision also takes audio into account: `lastAudioActivityAt` is stamped from the audio-level stream whenever levels clear `speechMicLevelThreshold` / `speechSystemLevelThreshold`, and while that is within `autoStopAudioActivityWindow` (60s) auto-stop holds off and lets `checkTranscriptHealth()` reconnect, giving up only at `autoStopStalledPipelineMultiplier` (3×) the silence window. Track the timestamp from the level stream — do **not** sample `microphoneLevel` inside the 30s tick, which is as likely to land in a pause between words as on actual speech. The decision itself is the pure `AppState.evaluateAutoStop(transcriptGap:audioGap:autoStopMinutes:calendarEventEnded:)`, covered by `testAutoStop*` in `AppStateComputationTests`; `checkAutoStop()` only gathers inputs and logs. `lastTranscriptReceivedAt` is stamped from both transcript callbacks — `handleTranscriptUpdate` *and* `handleSpeakerSegments` — because the former early-returns on an empty `alternative.transcript` while words still land as final segments, which would otherwise grow a transcript gap during visibly working transcription.
- **Transcript health watchdog**: `transcriptHealthTimer` fires every 4s and decides through the pure `AppState.evaluateTranscriptHealth(...)` (covered by `testTranscriptHealth*`). A stall is words missing for `transcriptStarvationGap` (20s) *and* speech having happened since the last words came back — `audioGap + transcriptFinalizeLatencyMargin < transcriptGap`, bounded by `transcriptHealthAudioActivityWindow` (60s). The comparison is deliberately relative: an absolute "audio within the last N seconds" window reconnects during any ordinary pause that outlasts the starvation gap, and a reconnect is not free (it drops the socket and resets macOS multichannel speaker identity). Two things this must keep doing: judge audio from `lastAudioActivityAt` rather than an instantaneous `microphoneLevel` sample (a 4s tick lands in a pause between words about as often as on speech), and retry after the backoff ladder in `scheduleDeepgramReconnect` has been exhausted (`.reconnectAfterExhaustion`, on the longer `transcriptExhaustedRetryCooldown` of 60s). Reconnects are otherwise only triggered by a connection-state *transition*, so a socket left in `.error` after the final attempt would stay dead for the rest of the meeting while auto-stop deliberately keeps recording through the stall. Recoveries that don't bring words back double the cooldown (`transcriptRecoveryCooldown`, capped at 10 min, reset by `consecutiveTranscriptRecoveries` going back to 0 once the gap closes): a room whose ambient noise clears the speech thresholds otherwise looks like a permanent stall and would reconnect every 30s all meeting.
- **Periodic auto-save**: A 60-second `periodicSaveTimer` runs during recording, calling `saveCurrentMeetingIfNeeded(onlyIfChanged: true)`. A fingerprint skips unchanged ticks; a failed periodic save clears its pending fingerprint so the next tick retries. Backgrounding, stop, Home, and explicit state-changing save points remain immediate. Saves are serialized through one worker with a FIFO of meeting IDs; queued snapshots coalesce only within the same meeting, so starting meeting B can never replace meeting A's terminal payload. Each meeting has monotonic requested/successful revisions, and `hasUnsavedSession` clears only when the latest revision committed and the live-state fingerprint still matches that snapshot. `saveCurrentMeetingIfNeeded()` does NOT set `endTime` — only `stopRecording()` and `goHome()` set it. Meetings with `endTime == nil` are identified as interrupted/resumable on next launch.
- **Resume interrupted meetings**: On launch (when `modelContext` is set), `resumeInterruptedMeeting()` queries SwiftData for meetings with `endTime == nil`. If found, it restores the full session: `currentMeeting`, `liveSegments` (reconstructed from `TranscriptSegment`s), all insights, notes, MEDDPICC fields, `detectedSpeakers`, `recordingDuration` (from last segment timestamp), and title tracking. Title restore handles both old timestamp-prefixed titles (via `parseMeetingTitle`) and new clean titles for backward compatibility. The UI automatically shows the stopped-session view (because `currentMeeting != nil`), where the user can resume recording or go home (which finalizes `endTime` and saves). Works on both iOS and macOS. In managed mode, if the interrupted meeting has a `managedSessionId`, the orphaned session's usage is reported to the backend (duration computed from saved segments) and the session ID is cleared to prevent double-reporting.
- **Stale interrupted-meeting guard (v1.24.2)**: Before restoring, `resumeInterruptedMeeting()` filters candidates through `isInterruptedMeetingTooOldToAutoResume(_:)`. Staleness is computed from `estimatedLastActivity(_:)` — the max of `startTime` and the newest `TranscriptSegment.timestamp` — so a long meeting with recent activity is never considered stale, but a meeting whose last segment is older than `interruptedMeetingAutoResumeMaxAge` (12 h) is. Stale drafts are finalized via `finalizeStaleInterruptedMeetings(_:now:)` which sets `endTime` (to the last activity time, or now if none), saves the `ModelContext` first, then spawns `Task`s to send any pending `PendingSessionEndReport`s for managed sessions. Covered by `testResumeInterruptedMeetingDoesNotRestoreStaleDraft` and `testResumeInterruptedMeetingRestoresLongRunningDraftWithRecentActivity` in `AppStateComputationTests`.
- **Live Activity (iOS only)**: `Activity.request()` is called in `startRecording()`, `activity.update()` on stop (paused state), title changes, transcript updates, and a privacy-setting change, and `activity.end(.immediate)` on `goHome()`. Transcript updates are throttled to max 1 per 3 seconds (`liveActivityUpdateInterval`) to stay within ActivityKit's update budget. The widget uses `Text(timerInterval: startTime...Date.distantFuture, countsDown: false)` for an auto-updating timer when recording; when stopped, `elapsedSeconds` is set and the timer switches to a static `Text(formatDuration(_:))` so it freezes. All visual elements (dot, status, title, timer) switch to `pausedGray` when stopped. `LiveActivityPreferences.presentedTranscript` strips transcript text before it is sent to ActivityKit when the Settings privacy toggle is off; the default remains on for continuity. `currentTranscriptLine` returns interim text if available, otherwise the last finalized segment. Static attributes include the meeting UUID, and the extension attaches `miniti://meeting/<UUID>` so a tap routes the app to the active Record tab. All ActivityKit code is guarded with `#if os(iOS)` in `AppState.swift`. Note: compact Dynamic Island width is system-controlled and cannot be reduced by apps.
- **Never read a SwiftData model across a `Task` hop**: reading any property of a deleted model traps the process (`This model instance was destroyed by calling ModelContext.reset and is no longer usable`) — and a `nil` check on `currentMeeting` does not protect you, because the reference is non-nil while the object behind it is dead. Anything that hops through a `Task` before touching a meeting must therefore snapshot the plain values it needs (id, title) *before* the hop. `startLiveActivity()` / `restorePausedLiveActivity()` do this and pass `meetingID` + `meetingTitle` into `replaceLiveActivity`, which is why that function takes strings rather than reading `currentMeeting` itself. This used to crash the iOS test host on every run, because tests create an `AppState` whose container is torn down before the queued Live Activity task runs.
- **iOS background recording & kill recovery**: iOS can terminate backgrounded apps at any time (memory pressure, battery, etc.); there is no way to guarantee completion after a force-quit or kill. Mitigations: (1) `UIBackgroundModes: [audio]` keeps the app running longer while recording. (2) Dirty periodic auto-save (every 60s) persists changed finalized transcript/insight state to SwiftData. (3) Entering background begins a UIKit background task before snapshotting and awaits a revision-fenced save; expiration ends the lease exactly once and recovery still falls back to the most recent successful periodic save. (4) On launch, `cleanupOrphanedLiveActivities()` ends stale Live Activities, then `resumeInterruptedMeeting()` restores the session from SwiftData so the user lands directly in the stopped-session view with their transcript. Interim text remains best-effort until Deepgram finalizes it (or stop-time preservation promotes the visible interim); persisting raw interim fragments would need separate schema/reconciliation semantics.

## Performance / hot-path rules (critical)

- **Atomic array mutations for ForEach-bound arrays**: Never do `removeAll` + `append` (or multiple mutations) on a `@Published` array that drives a SwiftUI `ForEach`. Each mutation fires a separate `objectWillChange`, and SwiftUI's AttributeGraph can see intermediate states (items removed but view nodes still referencing them), causing `EXC_BAD_ACCESS` in `AGGraphGetWeakValue`. Instead, build the final array in a local `var`, then assign it once: `liveSegments = updated`. This is especially critical for arrays that grow over long sessions (30+ minutes of recording).
- **`liveSegments` invariant**: `AppState.liveSegments` contains finalized, non-empty segments only; interim text belongs in `TranscriptRuntimeState`. Enforce that invariant when restoring an interrupted meeting so finalization callbacks can copy the array directly instead of filtering the full, ever-growing transcript on every callback.
- **Chronological dual-channel finals**: macOS dual-source sessions order finals by `Deepgram SpeakerSegment.startTime` on a meeting-wide timeline. Each WebSocket gets an offset from the precise active recording duration because Deepgram restarts word times at zero after reconnect. Nearby channel callbacks rendezvous in a 350ms bounded buffer; ambiguous mic speech can be released later by echo reconciliation and is inserted with a binary timestamp search. Persisted timestamps are made unique by microsecond tie-breaks so SwiftData relationship iteration cannot reshuffle equal-time segments after reload. The ordinary path remains append-only; never replace this with a full-array sort on every final callback.
- **Incremental finalized transcript rendering**: Interim transcript updates never rebuild finalized content. `TranscriptView` maintains a merged attributed document and an incremental final-tail mutation. On macOS, `LiveTranscriptTextPaneMac` owns one native `NSScrollView` + selectable TextKit 2 `NSTextView`; it is not self-sized inside a SwiftUI scroller, preserves selection outside the changing range, and normally updates only the final turn/interim suffix. Rare chronological middle insertions rebuild the value model but compute a UTF-16 common prefix/suffix and apply only the affected whole paragraphs to TextKit; speaker-name/interface-scale rebuilds remain full replacements because attributes may change without text changing. The view is read-only with rich-text editing, Inspector Bar, Font Panel, ruler, native find UI, writing/text-checking tools, graphics import, and selection rollover UI disabled; attributed display remains intact, and selection explicitly uses accent green with primary-background text for dark-mode contrast. Do not restore per-row `.textSelection(.enabled)` on the macOS live path: each row creates a SwiftUI `SelectionOverlay`, and long-transcript window resizing can loop in `SelectionOverlay.updateNSView`, consume gigabytes, and hang the main thread. Native live follow is immediate and listens to `NSScrollView.didLiveScrollNotification`, so layout/programmatic scrolls cannot disable follow and a moving bottom target cannot bounce the scrollbar. iOS retains the existing lazy selectable speaker-turn rows and Reduce-Motion-aware animated follow behavior. Saved/trim-enabled transcripts retain their separate bounded `SelectableTextView` required for cross-segment selection and precise deletion mapping.
- **Cached saved transcript rendering**: `TranscriptTrimView` caches its sorted segments and attributed render model. Rebuild only for segment-count/edit-revision, speaker identity, or interface-scale changes, and debounce SwiftData notification bursts. Pass a full-range mutation when rebuilding so native text storage updates in place. `SelectableTextView` also skips deep attributed-string equality when SwiftUI passes the same immutable input object during an unrelated state update; without both guards, opening a sheet after a long Save can repeatedly walk and lay out the entire transcript.
- **Cached transcript and persistence projections**: `AppState.liveSegments.didSet` maintains the plain transcript, raw-speaker transcript, persistence snapshots, and a monotonic revision. Hot insight, Docs, naming, and save paths consume these projections instead of filtering/sorting/mapping the full growing array. Exact Coaching metrics snapshot on main and compute in a utility detached task with revision/mode latest-wins guards.
- **Instruments points of interest (v2.0.3)**: Release/Profile builds retain privacy-safe signposts around full transcript cache rebuilds, live transcript view cache updates, off-main meeting save-plan construction, main-actor plan application, and the SwiftData commit. Signpost payloads contain counts only—never transcript, title, attendee, or meeting text. Use the Points of Interest instrument alongside Time Profiler for 60+ minute validation; save-plan intervals measure wall time across the detached suspension, while Time Profiler identifies actual CPU ownership.
- **Ordered background Deepgram parsing**: WebSocket messages are decoded and speaker-segmented off the main actor, but only one message is processed at a time. The next receive begins after the prior parse applies, preserving stream order. A connection generation plus WebSocket identity check drops results from an old connection after reconnect; only compact publish/log state is applied on main.
- **Bounded diagnostic/source history**: Debug entries and macOS source-energy samples use fixed-capacity rings, not `removeFirst`. Debug UI publishing is coalesced to 100ms while export retains every buffered entry. The system-audio callback reuses conversion scratch storage and writes interleaved PCM directly into owned `Data`.
- **Avoid main actor hops from audio threads**: `nonisolated func sendAudio()` on `@MainActor` services should NOT use `Task { @MainActor }` to access properties — this creates a new main-thread task per audio buffer (~4/sec), competing with SwiftUI layout passes. Instead, use `nonisolated(unsafe)` shadow properties (e.g., `_sendTask`, `_sendConnected`) written from `@MainActor` context (connect/disconnect) and read from audio threads. `URLSessionWebSocketTask.send` is thread-safe and doesn't need the main thread.
- **User-dismissable async feature pattern**: For any feature that kicks off an async fetch from a button and can be cancelled by the user (sheet swipe-down, popover outside-click, Escape), follow the Zoned Out template: (1) store the in-flight `Task<Void, Never>?` on AppState (e.g. `activeCatchUpTask`); (2) cancel the prior task before starting a new one; (3) check `Task.isCancelled` after every `await` boundary and return without applying state if cancelled; (4) treat `CancellationError` as a silent no-op in the outer catch (never surface it as an error to the user); (5) make the dismiss function idempotent (cancel → nil → clear state); (6) wrap the SwiftUI `isPresented` binding in a custom `Binding` whose setter funnels `false` through the dismiss function, so all dismissal paths (programmatic, outside-tap, swipe) run identical cleanup. Forgetting any one of these leaks either stale results (stale response wipes fresh state) or runtime warnings (CancellationError bubbling to UI).
- **Hot-path perf: reverse iteration over `liveSegments`**: Any evaluator that fires on every transcript finalize (real-time nudges, monologue detection, filler rate) must NOT call `liveSegments.filter { $0.isFinal }` — that allocates a full copy of the segment array per call, and `liveSegments` grows unboundedly over a long meeting. Instead, iterate `liveSegments.reversed()` with `guard seg.isFinal else { continue }` and `break` on the first segment whose timestamp falls outside the evaluation window. This turns an O(n) allocation per finalize into O(window) with zero allocations.
- **Per-language filler token cache**: `TrainingFillerPreferences.currentFillers(for:)` + `TrainingMetrics.tokenize(...)` are called from the nudge hot path. Cache the tokenized filler list on AppState (`cachedFillerTokensLanguage` + `cachedFillerTokens`) and rebuild only when the meeting language changes; invalidate in `resetNudgeState()` so a new meeting in a different language picks up fresh tokens.
- **Don't clobber JSON-backed SwiftData properties on encode failure**: For computed properties that serialize to an `…JSON` string column (`Meeting.speakerNames`, `Meeting.speakerOverrides`, `Meeting.selfSpeakerIDs`, `Meeting.attendees`, `Meeting.suggestedQuestions`, `Meeting.docTopics`), the setter must only overwrite the backing JSON string when `JSONEncoder().encode(...)` succeeds. An intermediate encoder failure writing `nil` would silently destroy previously-saved data on disk. Pattern: build the cleaned value, early-return with `fieldJSON = nil` if the cleaned value is empty, then write the new JSON only on successful `encode + String(data:encoding:)`. Never use `(try? …) ?? nil`. All six setters follow this; each has round-trip / empty-clears coverage in `MeetingModelTests`.

## Insights + feature flows

- **Generate insights for history**: `generateInsightsForMeeting(_ meeting: Meeting)` generates only the insight view currently selected by the person and writes it directly to the saved `Meeting`. Coaching remains local and Playbook owns its own refresh/lookup controls.
- **Insight apply safety**: `applyInsights(_:segmentCount:mode:)` uses an explicit `mode` parameter to route fields — Summary updates only touch `liveSummary`/`liveActionItems`/`liveTopics`/`liveDiscussionFlow`; Sales updates only touch the eight MEDDPICC fields. Each field is only overwritten if the new value is non-empty, so partial responses don't wipe previously populated data. `stopRecording()` always refreshes Summary and Questions; it refreshes Sales only when `salesInsightsEnabled` is true.
- **Pause/resume stale-final guard**: `generateFinalInsightsAndSave()` now snapshots meeting ID + final segment count and only applies final-standard/final-MEDDPICC responses if the meeting is still stopped and unchanged. If recording resumed (or segments advanced) while a final request was in flight, the stale response is ignored so older/shorter snapshots cannot overwrite live insights.
- **Coaching mode**: The third `InsightsMode` (internal raw value `.training` retained for storage/API compatibility) shows locally-computed speech analytics — no LLM calls are needed for the Coaching UI. `TrainingMetrics.compute(from:duration:language:)` runs a pass over transcript segments to extract filler word counts (language-specific: hard fillers like "um"/"uh" + soft fillers like "like"/"basically" for English, equivalent lists for other languages), talk ratio, speaking pace (wpm), longest monologue, questions asked, and clarity (avg words/turn). Filler lists retain their existing `training…` storage keys for migration safety. When Coaching is active, each new finalized batch snapshots the inputs on main and schedules the exact full computation on a utility detached task; cancellation plus transcript-revision/mode guards make it latest-wins. Mode switch schedules the same path, while explicit final/export refreshes remain synchronous where a result is immediately required. During recording in Coaching, automatic live Summary refresh still computes in the background so it is ready when switching back. Manual generate/update actions are hidden (or no-op guarded) in Coaching to avoid hidden AI calls. For saved meetings, Coaching metrics are computed on the fly from `meeting.segments` using the meeting's stored language in the history views (no extra model fields needed). The Coaching overview makes every meeting row navigable; macOS shows an explicit back-to-Coaching action in meeting detail, while iOS pushes detail on a dedicated Coaching navigation stack.
- **Coaching metric help UI (cross-platform)**: All major Coaching metrics (fillers, talk ratio, pace, longest monologue, questions, clarity) expose the same plain-English guidance/ranges in live + historical views. macOS uses native popovers; iOS uses a custom centered floating popup card with dim backdrop and tap-outside-to-dismiss to avoid `.popover`/sheet full-screen presentation quirks.
- **Coaching clarity helper copy**: The inline clarity helper is intentionally standardized across macOS/iOS live + historical views as `lower = clearer = better` for fast scanning.
- **Questions mode**: `InsightsMode.questions` generates AI-suggested questions focused on gaps, unstated assumptions, and dropped threads. Six question types: `deeper`, `challenge`, `reframe`, `clarify`, `explore`, and `follow_up`. It runs on its own live cadence, refreshes on stop, and updates saved meetings only when Questions is the selected view. Results persist in `Meeting.suggestedQuestionsJSON` and flow to webhooks/exports.
- **Playbook / Docs mode (v1.27.0)**: Specialist `InsightsMode.docs` grounds technical sales help in a user-provided HTTPS Streamable HTTP Docs MCP URL. Configuring a valid URL automatically enables Playbook; otherwise the specialist menu offers **Set Up Playbook…** rather than an empty peer view. Topics refresh only while Playbook is selected, and each topic is looked up independently. Pro/BYOK auto-lookup pending topics; managed-free performs metered manual lookups. Resolved cards and citations persist in `Meeting.docTopicsJSON`; failures never overwrite answered cards. Generic update buttons remain hidden because Playbook owns its refresh/lookup controls. Backend contract: `docs/docs-insights-api-spec.md`.
- **Device-bound managed auth (v2.7.0)**: managed requests carry `Authorization: Bearer <access token>` plus `X-Request-Proof` (ES256 over token hash, method, path+query, body hash, `iat`, `jti`) on non-GET calls; nothing secret ships in the binary. `AppState.ensureManagedEnrollment(trigger:)` runs before `refreshUsage` and `startManagedRecording`: it tries `/api/auth/migrate` (pre-cutoff device record → silent account creation that preserves the `device:{id}` record), falls back to `/api/auth/account/create`, and shares one in-flight task between callers. Failures are logged and retried on the next managed action, never gated. A 401 `token_expired`/`invalid_token` is retried once after a refresh; `installation_revoked`/`device_auth_required` clears local credentials (`ServiceError.authRevoked`) and the Account section offers restore. Restoring with a recovery key onto a device UUID the account already knows re-binds the key (backup / Migration Assistant). A draft (key and recovery key written before the enrollment request, `accountID` empty and no token) is not an enrollment: `isEnrolled`, `status` and `revealRecoveryKey` ignore it, so a refused create never leaves the app signing token grants with an unknown key (the 2026-10-10 iPhone `invalid_proof` lockout). A create answered `device_already_enrolled` (device id item restored from a backup, device-only credentials gone) rotates the device id through `DeviceIdentifier.rotate()` and creates a fresh account under the new id; `performManagedEnrollment` sends a migrate 409 down the same path. Since 2.12.1 the client also re-binds on its own: a challenge grant answered `invalid_proof` (the server holds another key for this device UUID) makes `ClientAuthManager` call `/auth/account/restore` with the stored recovery key and the current key, and `signOut()` clears local credentials on any 401 or refused re-bind, so a device can never be stuck needing a token to sign out. Since 3.3.0 `ClientAuthManager` also reconciles identity on load: the access token's `sub` is the device id the server bound the installation key to, so when the Keychain device id disagrees (3.2.1 deleted it during a Keychain move the release build cannot complete) `DeviceIdentifier.adopt` restores the token's id before the first request. BYOK never enrolls. The recovery key nudge on Home shows until acknowledged (`recoveryKeyAcknowledged` in the Keychain blob) or snoozed for the launch.

## Cloud sync (3.0.0)

- Default off, Pro only, managed accounts only, paused under private mode. `AppState.cloudPauseReason` is the single gate; `CloudSyncEngine.refreshPause()` runs after every setting, mode, enrollment, tier or private-mode change (`setPrivateMode` snapshots and restores `cloudSyncEnabled` like the other nine settings).
- No write path stamps anything: the engine fingerprints finished meetings (`MeetingSyncDocument.fingerprint`, JSON columns canonicalised, no transcript text, `transcriptRevision` covers trims and corrections) after every `commit` (5 s debounce), on activation, and on every fifth 60 s poll; a plain poll only pulls. It sets `updatedAt` when it notices a change; a legacy meeting's first observation keeps its own latest timestamp. Every loop re-checks the pause reason between awaits, so private mode stops a backlog mid-way.
- The engine never touches `currentMeeting` (`liveMeetingID`), never writes a meeting in `deletedMeetingIDs`, and does every model access on the main actor between awaits with a deleted-id check first. Pulled meetings arrive through `commit(.cloudSync)`; inserts post `.minitiMeetingsImported` (now shared with iOS) and follow macOS auto-export; they never enqueue webhooks or CRM sends.
- User deletes write a `MeetingTombstone` in the same save whenever the meeting had a cloud copy or the switch is on (`noteMeetingDeleted(_:createTombstone:)`), so a delete during a first upload still reaches the cloud; a `PUT` that completes for a meeting deleted meanwhile writes the tombstone itself. The engine's own removals pass `false`. A tombstone conflict (edited elsewhere after the delete) retries with the server revision: the delete wins.
- Conflicts: server tombstones win; a lower `transcript_revision` never replaces the server's segments, and a device that renamed on a stale transcript takes the server's transcript, keeps its own scalars, and pushes the merge; otherwise last writer wins on `updated_at` with one retry. Pulled transcripts are applied by segment id (update, delete, insert), never by dropping every row, so a History view holding segments keeps valid objects. `external_duplicate` (the same Granola CSV imported twice) replaces the local copy with the cloud one. `413` marks the meeting `skipped_too_large` and stops retrying until it changes.
- Meetings recorded under private mode are created with `syncExcluded = true` for life; the per-meeting action can change it. Sign out, move to another account, and account deletion call `resetBookkeeping()` (cloud revisions and fingerprints cleared, tombstones dropped, cursor forgotten): local meetings stay and upload to whatever account comes next. A device offline longer than the 30 day tombstone window re-uploads instead of losing a meeting.
- One switch per account (3.3.0): the server keeps `cloudEnabled` and a growing `cloudVersion` on the account (`PUT /api/account/cloud`, mirrored on `/api/usage`); `applyAccountCloudFlag()` runs after every usage check and the pure `cloudAccountFlagAction` decides push (this device's unconfirmed or first "on"), follow (another device flipped it; "on" waits for Pro and the end of private mode), acknowledge, or nothing. A person's flip goes through `setCloudSyncEnabled(_, source: .user)` and is written to the account; a follow uses `.account` and is not. Private mode writes `cloudSyncEnabled` directly and stays a device state. Rules and edge cases: [cloud-sync-plan.md](cloud-sync-plan.md) § "One switch per account".
- Timestamps: cloud stamps carry milliseconds, a local `Date` microseconds. `CloudSyncEngine.stamp` rounds every stamp the scan writes to the millisecond and `isNewer(_:than:)` ignores differences of a millisecond or less in all three conflict comparisons (reconcile, pull, push 409). Without that, a device whose bookkeeping lagged a wave of pushes re-uploaded the whole library as conflicts, bumping every revision (2026-10-21, four waves in five days on one Mac). The test host never starts the engine (`configureCloudSyncIfNeeded` returns under XCTest): it is the real app on the real store and must not sync it from a second process.
- Backend contract and the client protocol: `../miniti-api/docs/agents/08-cloud.md`. Plan and decisions: [cloud-sync-plan.md](cloud-sync-plan.md).

## Settings registry (v2.12.0)

`SettingsGroup` and `SettingsDestination` in `AppState.swift` are the only source of the sidebar and the Settings menu on both platforms. Adding a tab means one enum case with a group, title, subtitle and icon, a `fromLegacyID` entry if an older id pointed at it, catalog items whose ids start with the tab's raw value, and matching `.id(...)` anchors in both settings views; a registry test enforces the first and the id rule. Deep links use `SettingsDestination.x.rawValue`, never string literals, and in-app copy names tabs by their single-word titles.
## Meeting titles + transient flags

- **Meeting titles**: New meetings start with `title: "untitled"`. AI-suggested titles from `applyInsights()` and `generateFinalInsightsAndSave()` set `meeting.title` directly (no timestamp prefix). Calendar-started meetings use the event title. `currentTitleSuffix` tracks the last-applied title for dedup. `parseMeetingTitle()` is kept as a legacy helper for old meetings that have the `yyyyMMdd-HHmmss - Suffix` format. All display surfaces, markdown exports, webhook payloads, and Live Activity use `meeting.displayTitle` which handles both old and new title formats. Title editing in history views (`TextField`) binds directly to raw `meeting.title`.
- **isStartingMeeting**: Transient flag set in `startNewMeeting()`, cleared when `startRecording()` succeeds or on failure. iOS shows a "starting..." spinner during this phase. macOS hides the session view.
- **isResumingRecording**: Transient flag set when resuming a stopped session in managed mode (needs a fresh Deepgram JWT). Cleared when `startRecording()` succeeds, on failure, or on `clearCurrentSession()`. Shows a "starting..." spinner on the resume button and blocks repeat taps. On iOS, managed via local `@State` in `MeetingView_iOS` rather than AppState to avoid cross-view side effects.
- **pendingOpenSavedMeetingID / saveAndOpenCurrentMeeting()**: Done/Open in History stores the meeting UUID in `pendingOpenSavedMeetingID`. During the short Deepgram transcript-finalization phase, navigation remains unavailable and `stopRecording()` is idempotently rejected. After the final transcript is durable, AI work is keyed by meeting ID in `finalizingInsightMeetingIDs` and writes directly to that saved `Meeting`; Back to meetings may then clear the live session immediately and a new recording can start without old responses touching it. Resume of the same meeting stays unavailable until its background insight task finishes.

## Keyboard + focus conventions (macOS)

- **macOS focusability**: Primary actions (start/stop/resume/done, title edit, settings, and shortcuts) remain in keyboard focus order and have explicit accessibility labels where their visible content is ambiguous. Dense sidebar/utility icon controls may opt out of tab focus when an equivalent documented shortcut exists. Keyboard shortcuts supplement rather than replace accessible focus navigation.
- **Semantic control chrome and content accents**: Ordinary controls use `MinitiControlLabel` with a `MinitiControlRole` rather than accepting arbitrary feature colors. Primary navigation is blue, Start/Resume is green, Stop/Discard is red, warnings are amber, and utilities are neutral. Summary/Questions/Coaching are persistent neutral tabs built from `MinitiTabLabel` and `MinitiTabStripSurface`; the shared tab component lowercases product-authored labels, while Sales/Playbook remain in More. Insight-category colors live separately under `MinitiDesignSystem.ContentAccent` and belong in section headers, charts, and content—not tab, sidebar-selection, or utility-button chrome. Coaching uses the stable `ColorPalette.Coaching` mapping across live, history, overview tables, trend sections, evidence cards, and per-metric charts; these metric colors never substitute for CTA or trend-status colors. The shared controls own measurements and Reduce Motion-aware hover emphasis; enclosing native `Button` / `Menu` controls retain actions, shortcuts, focus, disabled state, and accessibility.
- **Dock reopen after close/minimize**: the primary `WindowGroup` has scene ID `main`, and `MainWindowIdentifierInstaller` tags only its `NSWindow` as `miniti.main-window`. Dock reopen, menu-bar Open, notifications, and the floating panel's Open meeting action unhide and activate the app, deminiaturize and order the identified main window front regardless of the non-activating caller, or ask SwiftUI to recreate the `main` scene when it no longer exists. Scene restoration retries briefly because creation and identifier installation are asynchronous. Never infer the main window from title/style because Settings and transient panels can match. OAuth duplicate cleanup uses the same identifier. Privacy-safe unified lifecycle logging records route/outcome only.
- **Escape key routing (macOS)**: Centralized in `KeyboardShortcutsService`. Order: (1) dismiss any active sheet (debug log, CRM send) via `cancelOperation` + `performClose`, (2) close Settings/Preferences window, (3) close help overlay, (4) go home. Sheet dismissal scans both key window and all visible windows as fallback. Settings detection checks window title and `toolbarStyle == .preference`.
- **J/K history navigation vs text entry (macOS)**: `KeyboardShortcutsService` ignores unmodified `j`/`k` and arrow-key history navigation when focus is in an editable text responder (`TextField`/`TextEditor` via AppKit `NSTextView`/field editor). This prevents list scrolling while typing in notes or CRM search fields.

## Audio recovery patterns (macOS)

- **Stop = auto-save + background insights**: `stopRecording()` gracefully asks Deepgram for final results and waits for the final transcript save queue to drain. Slower Summary, Questions, and enabled Sales requests then run against an immutable transcript snapshot and write only to the saved meeting they belong to. The stopped UI offers Back to meetings during this phase; clearing the live session and starting another recording is safe because background responses never depend on `currentMeeting` or live arrays. Short/socket-interrupted meetings preserve visible interim text through the normal deduplicating merge. Deleting or editing the saved transcript invalidates its outstanding response through meeting-ID and transcript-revision checks.
- **Mic restart retry**: If `handleEngineConfigurationChange` fails to restart the mic (e.g. Core Audio format mismatch during Bluetooth device bouncing), `scheduleMicRestartRetry` retries with bounded backoff (0.5s → 1.5s → 3s, max 3 attempts). On success, `restartSystemTapForMixMode()` flips the system tap back to `mixWithMic=true` if it had switched to `directCallback` mode while the mic was dead. `expectsMicAudio` tracks whether the user originally requested mic capture. `handleDefaultOutputDeviceChange` reads `isMicActive` after the settle delay (not at event time) to avoid capturing stale mic state during rapid device bouncing.
- **System tap stall recovery**: `AudioCaptureService` handles two failure modes: (1) silent-stall (callbacks keep arriving but stay near-silent) and (2) callback-stall (callbacks stop arriving). Callback-stall detection belongs to one capture-scoped 2s task—not the mic callback—so system-only recordings are covered too. The pure decision gate requires a 6s callback gap plus prior callbacks or 8s startup grace, shares the 45s restart cooldown, and suppresses overlapping route/retry/full-restart work. Both paths rebuild the system tap with ring-buffer reset, preserve the active mix mode, and retry failed rebuilds with bounded exponential backoff (except explicit permission-denied cases). Both stop paths must cancel the watchdog. See [audio.md](audio.md) for the full recovery state machine including v1.24.1 post-recovery health check and escalation to full capture restart.
- **Session-end robustness**: `MinitiAPIService.endSession` still retries trailing-slash 405 routing edge cases, and now also consumes backend idempotency/session-finalization diagnostics while the app maintains a durable retry queue for failed reports.
