# Account minutes-window transition candidate

2026-11-10. Engineering proposal and offline executable reference for B1/B2, under the confirmed D3/D4/D5/D10 policies. This does not activate account billing or close the account-period gate. The [ownership plan](../plans/account-ownership.md) remains authoritative; [settlement authority](ownership-settlement-design-2026-11-10.md) and [adoption/correction](ownership-adoption-contract-2026-11-10.md) remain separate requirements.

## Separate the three decisions

1. **Ownership:** B1 establishes the immutable owner of each purchase. This model accepts only an already reconciled registry of that account's owned subscriptions. It cannot discover ownership, trust provider metadata, resolve a backfill collision or consume customer-supplied account IDs.
2. **Entitlement:** provider status/grace and consuming-platform eligibility determine the current limit. Apple still does not grant Mac Pro; both rails do not add two 5,000-minute allowances. The model's `eligible` input is account-level provider eligibility, not permission for a particular device to record. Provider status/time validation and entitlement enforcement remain adapters to implement.
3. **Usage window:** all the account's managed minutes share one accounting window identity. A selected subscription supplies its scheduling evidence. Changing the selected subscription is distinct from creating a new allowance.

Candidate precedence preserves the current device-level Polar-first rule and makes the account result independent of member traversal. Among eligible purchases on one rail, use B1's earliest `boundAt`, then the exact opaque purchase ID for equal timestamps. A stale/future period on that winner is unresolved; do not fall through to another purchase or free allowance. A complete, stable registry snapshot produces the same winner in either input order. This does not claim identical history when different incomplete snapshots arrive at different times, nor make local bind timestamps independent of webhook arrival order. Provider/backfill ordering and registry reconciliation remain prerequisites.

## Persisted state and transitions

The candidate adds an immutable accounting-window ID separate from mutable scheduling evidence: selected source, provider start, next boundary, original window opening, observation time and the last period selected for each paid source. The reference state is now version 2; version 1 is rejected rather than treated as having no source history. This is an offline schema change, with no persisted production records to migrate. The account's current-period pointer continues to address `usage:account:{acct}:{period}`. The period segment would be an opaque server-owned window ID, not a value re-derived from whichever rail is currently selected. This revises the plan's proposed rail/start key derivation, not the namespace, and remains a proposal until the integrated period contract is accepted. Adapters must choose an idempotent ID and retain prior IDs, receipts and historical source decisions; the oracle's caller-supplied IDs do not prove that persistence.

| Input / transition | Reference decision | Balance, credit and admitted work |
|---|---|---|
| First migration seed into an already resolved paid/free account | Initialize one window; external seeding supplies existing effective opening | Initialization is not a zero-balance instruction; retain B0/D10 opening and per-device claim |
| Same source and same period | Retain | No reset |
| Add a secondary rail while Polar remains selected | Retain | No second allowance |
| Change paid source into an overlapping period, with no newly detected grant from a returning source | Retain same window ID; schedule from the new source | No copying, zeroing or reseeding; pending admissions still name the same window |
| Change paid source into a non-overlapping later period, or return to a known source that has renewed after this allowance opened | Pending paid-grant classification | Do not carry an expired balance into a possible new paid allowance or infer a second grant |
| Paid to free while the current free month overlaps the old boundary | Retain same ID; schedule the next UTC month boundary | Usage and credit carry until that boundary; current free limit applies separately |
| Paid to a free month whose start is at or after the old boundary | Rollover to that UTC month | An expired October balance does not become December free usage |
| Free to paid | **Pending classification, not implemented** | Distinguish genuine first paid activation from restore/reactivation before deciding whether to open a paid allowance |
| Same paid source, verified later non-overlapping current billing period | Rollover once | New ID starts a new allowance; old window remains for late settlements and correction |
| Same free source, next UTC month | Rollover once | New window, no old migration credit; missed empty months need not acquire balances |
| Same provider start, corrected future end | Retain ID and update boundary | No inferred renewal |
| Eligible but elapsed/future period, stale period or overlapping period correction | Pending reconciliation | No speculative reset or free fallback |

A later verified same-source period may skip cycles with no observed activity. Repeated observation of that period retains the newly opened ID. The model rejects a caller reusing the immediately previous ID, but only storage can reject every historical ID collision or make a lost-response retry atomic. Pending is a refusal to decide, not a new production HTTP response or a guarantee of uninterrupted recording.

Changing scheduling source never changes an existing admission's owner or window. When an overlapping switch retains the same ID, an in-flight charge does not need a second debit or copied carry balance. At a genuine rollover, the required adapter contract routes a later authorized end to its captured old window, under B2's deliberately changed admission-period semantics. The test explicitly supplies that old ID to the journal; it proves isolated balances, not an admission/settlement router. Read/limit checks use the current window; lifetime telemetry remains distinct.

## Preserve the existing first-paid allowance

The shipped `linkDeviceToSubscription` resets minutes when there is no stored Polar period start or when a new start arrives. Apple does likewise for an eligible new Apple period when Polar does not take precedence (`lib/usage.ts`). A generic rule that retained all free usage on first upgrade would therefore change how many paid minutes the buyer receives. This candidate does **not** select that change.

The next extension must model a verified paid grant, including a returning rail after renewal, separately from restoring/reactivating an already applied purchase period. Preserve the first paid allowance, while preventing repeated restore or rail toggling from resetting it again. It needs a durable per-account/purchase/period application receipt under the same revision as the accounting-window transition, including lost reply, first bind during seed, prior cancellation, another active rail and delayed activation. Do not infer a first grant merely because the current scheduling source is free, or bypass classification because the last observed source was paid before a lapse. The corrected rule returns the same classification outcome for a later new purchase with or without an intervening free observation. No product decision is requested by this candidate; preservation of the shipped first-paid outcome is the implementation requirement.

The F1 elapsed-window correction is accepted at backend `cf17e546`, with a residual selection-history gap: a first-seen Apple November 10–December 10 period can extend the October Polar window, then a first-seen Polar December 5–January 5 purchase can extend it again. A source previously selected for an earlier period instead reaches grant classification. Thus overlap retention depends on selection history and can suppress a possible grant across several paid cycles. This is an executed open classification case, not accepted complete billing behavior. Before production, classify first-seen sources starting after the allowance opened and extending its boundary, alongside returning-source renewals; do not infer “covered” from absence of history. The receipt extension below deliberately does not resolve this policy from a snapshot.

The candidate also waits for current provider-period evidence rather than invoking the shipped passive date advancement. This can affect availability during delayed or missing renewal delivery. Before activation, specify authenticated refresh/reconciliation and client error/retry behavior for stale active/grace records; do not ship the pure model's pending states as a blanket new recording block. Neither status eligibility nor a safe availability policy is implemented here. Review F2 also demonstrates that an overlapping same-source period remains pending on November 2, 20 and 30; it has no automatic recovery within that cycle. Whether either configured provider can legitimately re-anchor this product is unverified. Before activation, support a verified re-anchor/correction decision or establish the applicable provider restriction. Do not assume it is impossible or turn this pending state into a cycle-long recording block.

Retained overlapping source changes preserve gross/credit in the same window; a non-overlapping free rollover starts a new window, and possible paid grants remain pending. Corrections continue to replay the original account seed component, not replace an unrelated destination or current-period total. The account transition record must be included in the correction/reconciliation history before a real adapter is accepted.

## Executable scope and remaining gates

Backend `scripts/account-period-reference.mjs` is an offline candidate, with no runtime imports, IO, environment or wall clock. `scripts/account-period-reference.test.mjs` uses synthetic IDs/clocks and composes with the existing journal model for credit and late-charge examples. Both the 64-record registry bound and 64-source history bound are model limits, not production caps. History records only periods adopted for scheduling, not every unselected provider snapshot; otherwise observing an unselected renewal could erase the evidence needed when it returns. History survives window rollovers. Capacity exhaustion fails instead of silently truncating old evidence. Durable application receipts, pruning and resource limits remain adapter work. Amount precision, serialized state decoding and full historical receipt integrity remain outside it.

Required before accepting a production resolver: first-paid activation/restore receipts; complete owner-filtered registry snapshots and provider ordering; actual status/grace/expiry eligibility; safe refresh behavior when period data is stale; fenced revision CAS and before-write validation; historical window-ID uniqueness and atomic replay; counters and state transition committed together; mirrored old-client usage/reset compatibility; real storage concurrency and correction replay. No new endpoint, Redis key, migration, provider request or account state is written by this package. The [release evidence](../releases/3.9.0.md#account-period-transition-reference) owns exact test and review status.

## Classified paid-period application receipts

The next offline layer, backend `scripts/paid-period-application-reference.mjs`, applies a decision already established by an authoritative owner/period classifier. It does not provide that classifier. A request, missing receipt, current selection, or provider delivery ID cannot authorize a grant. `evidenceId` names synthetic classification evidence in tests; this model neither authenticates it nor reads a provider. The implementation must establish immutable purchase ownership, the complete registry revision, current provider evidence, and historical application evidence before choosing an outcome.

| Classified outcome | Application | Retry / correction |
|---|---|---|
| `grant` | Atomically propose one new zero-usage window plus an application receipt. Preserve old gross/credit and lifetime, including captured old-window work. | Within the bounded retained history, the same account/rail/exact purchase ID/provider start returns the original receipt, even after expiry, later charges or another rollover. No second reset. |
| `covered` | Record that this purchase period was included in the migration opening or already covered by the account allowance. Keep the existing balance/window. | Never promote coverage to a grant through an ordinary retry. A mistaken decision needs an explicit correction procedure. |
| `unresolved` | No new receipt, reset, or revision change. A previously recorded decision may still replay. | Includes first-paid versus restore ambiguity, first-seen overlap, returning renewal, incomplete historical receipts, and re-anchor uncertainty. |

The identity excludes end time so a corrected end does not mint an application. It also excludes provider delivery identity, device ID, current membership, and proposed window ID. A corrected start is a different tuple but is **not** automatically a new grant: provider normalization/reconciliation must decide. Rail and purchase spelling remain exact. Another account cannot replay the receipt, including when it supplies the same tuple. The receipt reports only immutable application/window identity and revisions, not a stale usage balance.

Application and journal revisions are checked together for a new decision. Replay of an existing identity precedes the revision/current-time checks so an exact lost-response retry works after later activity. A contradictory classified outcome is rejected; unresolved replay returns the recorded outcome. New classified evidence must describe a current period and supply an evidence ID. The reference accepts no historical-window ID reuse. It reconstructs the bounded usage journal and checks stored receipts before use; each grant receipt must match its reset event, and every reserved paid reset must have an application. This corrects receiptless replay at this new boundary without changing the older journal oracle's independent contract.

A single returned aggregate contains the journal change and application receipt. This models the intended transaction, not real atomic persistence. The adapter must fence **all** writers against account/registry revisions, validate Redis types and complete payloads before writes, persist scheduling, journal, application and response together, retain the proof across membership/restore/expiry, and replay from durable state after lost replies. The tests simulate two callers against one revision sequentially; they do not run concurrent storage. Covered receipts have no reset event, so deletion/rollback of such history cannot be detected from the usage journal alone. Durable history integrity, monotonic revisions, migration completeness and retention remain mandatory.

This layer models one account’s usage with the shared arithmetic journal. The test constructor takes an existing journal; it never zeros migration usage. Any imported device-seed claim must name that same account; a foreign claim is rejected. Stored application times must be nondecreasing, and state/journal/opening/event/application entries reject unknown fields. These checks do not establish authenticity or detect a rollback to an older otherwise valid snapshot. Synthetic tests cover a classified first grant, covered migration/secondary periods, duplicate restore, corrected end, another owner's replay, renewal, old-window charge separation, journal/application corruption, stale revisions and exhausted capacity. Provider decisions are deliberately supplied, not inferred. The 64-application/256-event bounds and whole-journal replay are small-model limits, not production retention or performance decisions. The retry test now succeeds at exactly 256 events and fails closed beyond that bound, including for an existing receipt; production replay retention must not inherit this small-model availability limit. Integer/fixed-precision storage, application correction and expiry/pruning are not implemented.

**Next implementation boundary:** specify and implement the trusted classifier and durable purchase-period provenance. Test the first-seen overlap chain, delayed first bind during seed, Apple already covered while Polar was selected, cancellation/reactivation, provider start correction and incomplete backfill. Then integrate the application receipt with the period scheduler and fenced storage. No passing receipt test closes the full resolver, B1/B2, AO0 or release gates.

It decides the cases the tables above leave pending. It is still a model: no storage, no routes, no provider calls. **Status: not accepted.** Three earlier designs were reviewed and rejected on the same day. The fourth, fifth and sixth reviews kept this architecture and found four, four and six narrow failures, fixed in backend `ao0-period-resolver` (`95a7825`, `eb29678`, then the commit after it). The last fix removed the special paths those failures came from; it has not been reviewed when this is written. The progress row in the 3.10.0 plan carries the review result.

What the three reviews taught, in order: one current window with a flag forgets usage and can be granted twice; an allowance per period is not enough if coverage is decided from what a call happened to see; and assigning periods once by dates is still not enough if time passing (a period ending, a month starting) is only noticed when a call arrives. Each review's counterexamples are tests now.

### The model: an event-sourced ledger

There are two kinds of event. A **registry revision** is the registry passed to a call; it is in force from that call's time until the next call that passes a different one, and the state keeps it. A **time transition** is the start or end of any period, and the start of each UTC month. Before a call applies its registry, every transition since the previous call is processed in order under the registry that was in force then. A call is therefore equivalent to having been called at every transition, and an extra call with an unchanged registry changes nothing: a registry equal to the stored one is not taken in again. Calls are ordered. What becomes true at an instant is decided by the last registry delivered for that instant. To make that hold when a read, or earlier revisions, arrive at the same instant first, the state keeps a copy of itself from before that instant's registry was taken in; a later call for the same instant starts again from that copy, so nothing an earlier registry for that instant did survives. Each window opened at that instant is remembered by what it is for (the free window of a month, or the allowance a particular period opens), and gets the same ID again only for the same purpose. A window therefore never changes meaning: a free month's window is never reused for a paid allowance. A charge made in that zero-length interval to a window the later decision does not use stays on that window; the settlement design owns late charges. The seed is the exception: once the account exists, a later registry for the seed instant is taken in as a revision, not as a second migration. Production must run the resolver, and store its state, with every registry revision.

At each transition the model first works out what every eligible purchase covers at that instant (a known period, an assumed cycle, or a gap) and only then assigns allowances, in selection order. Otherwise a purchase could look selected only because another purchase's coverage had not been written yet.

This replaces one sentence of the first section above: "A stale/future period on that winner is unresolved; do not fall through to another purchase or free allowance." Here selection is among the eligible purchases that have a period at the moment, and a purchase whose period has ended is given an assumed cycle, so the winner never falls through while it is eligible and has ever had a period.

1. **Every paid period the registry has shown is recorded once and assigned once to an allowance**, a window with its own usage. A period is the tuple rail, exact purchase ID, provider start. It is assigned at the moment it starts to matter: its start, or the revision that brings it if it has already started. If its purchase is the one the selection rule (Polar first, then earliest bound) picks at that moment among eligible purchases, it opens a new allowance with zero usage. Otherwise it joins the selected purchase's allowance. A period known before it starts is assigned at its start, with the eligibility of that day; until then any newer report for the same purchase replaces it, including a report of the purchase's current period: the registry shows one period per purchase, and what it no longer shows and has not started is dropped. The same holds when the purchase is reported as not eligible or is no longer in the registry. Evidence means the purchase's eligibility and period dates; a change of bind time alone is not new evidence.
2. **A new start from the same purchase inside its current period is a correction.** It replaces that period and keeps its allowance; the replaced dates no longer cover anything. A start within two days of the period's end, or later, is the next cycle (decision P-C). The same start with a different end corrects the end. A start older than what the purchase has reported is ignored.
3. **While a purchase stays eligible and its period ends with no evidence of the next, the next cycle is assumed by the calendar, month after month**, on the billing day (or the month's last day when the month is shorter). This is the shipped passive reset, which has no limit on how many months it repeats. An assumed cycle is assigned like any other period. Evidence replaces every assumed cycle it overlaps and keeps the allowance of the one most recently in use, with everything charged to it. There is one rule for this, applied to every new real period and to every real period whose end is corrected, whatever its exact start; evidence and assumptions are stored under different keys, so evidence never overwrites an assumption by accident. It takes precedence over the correction rule in statement 2. Assumed cycles that begin after the evidence ends are left as they are, dates included, until evidence for them arrives. If the next period is already known and starts within a cycle, the gap before it stays on the previous allowance and opens nothing, and the reset date shown is that period's start. A gap is only the time before a known next period and is never remembered as a decision: whenever the evidence about that purchase changes, the gap ends at that moment and what follows is worked out again. If the next period was moved, the new gap runs to its new start; if it was withdrawn, or moved beyond the next cycle, an assumed cycle follows instead. A gap never supplies an allowance to evidence that replaces it. A cycle that had wholly passed before a purchase was first seen is treated like a gap: it stays on the previous allowance. Assumed cycles are counted from the end of the purchase's last real period, in whole months on the same day of the month, or on the month's last day when the month is shorter.
4. **Usage is charged to the allowance of the selected purchase's period that contains now**, or to the free month, which has one window per UTC month for good. Every paid allowance that was in use for some time in a month counts against that month's free limit, beside the free window and never copied into it. "In use" means it was the charging window between two transitions, whether or not anything was recorded or read; being selected only at a single instant is not use.

### Decisions for Ian

- **P-A: overlapping rails.** The model follows the shipped asymmetry: a period on the purchase in use opens an allowance; a period on a purchase that is not in use joins the one that is. To accept or change: balances are resumable, so a buyer who adds Polar while an Apple allowance is in use has two allowances that month, and if Polar ends the rest of the Apple allowance is still there (today it is gone); someone who holds both rails all year gets one allowance per Polar month and nothing for Apple; and the abuse path, where a provider allows refunds or cheap repurchases, is that each new period on the purchase in use that is not a correction is a new allowance (today a new Polar start resets; purchase identity alone does not reset today, and here a new purchase identity with a new period does when it is the purchase in use). The alternative is one spendable allowance at a time, with the earlier one forfeited when a new one opens.
- **P-B: unverified allowances while renewal evidence is missing.** (Dates the provider contradicts itself on can also cost a cycle: if a period's end is corrected to a few days later and evidence for the next period then says it began before that, the cycle assumed from the corrected end has already opened. One of the tests shows it.) The model keeps the shipped effect for Polar, a new allowance every month for as long as the provider status says eligible, and applies the same monthly schedule to Apple, which today can reset more often than that against a stale end. When evidence finally arrives it keeps the allowance of the assumed cycle in use; allowances of earlier assumed cycles were already spent or not, and stay in their months. In numbers: with no evidence, 4,900 minutes are used on 29 December in the December cycle and 4,900 more on 2 January in the January cycle; evidence then shows one period from 28 December to 28 January. Both charges stay in the ledger, the confirmed period counts only January's 4,900 and has 100 left, so 9,800 minutes were used inside what turned out to be one paid period. That is the cost of assuming cycles; a cap or a bounded advance (options 2 and 4) is how to limit it. Options: (1) this; (2) at most one assumed cycle per purchase, after which the account waits at its usage until evidence arrives; (3) none; (4) a bounded advance charged against the allowance the evidence later opens, after an authenticated refresh. Under any option: how long eligible status without period evidence is believed.
- **P-C: correction or renewal.** A new start more than two days before the current period's end is a correction; later is the next cycle. Both errors are possible: a correction that lands inside the last two days would open a second allowance, and a real paid renewal reported earlier than that (a plan change that restarts billing mid-cycle) would get no new allowance until its own next cycle. No provider evidence yet says how either rail reports these. The threshold is inclusive: exactly two days before the end is the next cycle. Reconciling evidence with assumed cycles comes first: evidence that reaches into an assumed cycle keeps that cycle's allowance even when its start would otherwise read as a correction of the period before. A report older than a period that has already started is ignored, so two corrections that arrive out of order are not both applied.
- **What counts in a free month.** A paid period's usage returns with the period after free months. In a month with both schedules, every paid allowance that was in use at any moment of that month counts against the free limit, with its whole balance, including what was used before the month began. Example: an allowance in use on the 2nd whose period ended on the 3rd counts all month, even if nothing was recorded on those days. An allowance in use until exactly midnight on the 1st belongs to the month before. The alternative is to count only what was charged inside the month, which needs per-month charge records.
- **Complimentary Pro beside an App Store subscription.** The account has one minutes window. When an eligible paid purchase schedules it (Apple, for the account's iPhone), a Mac on the same account that is Pro by comp charges the same allowance with the Apple boundary. CM1's statement that comp uses the free calendar month then holds only for accounts with no eligible paid purchase. This narrows CM1's wording in the 3.10.0 plan.

### Tests

34 tests. Named timelines cover: first paid activation, restore and reactivation; a paid period and a free month keeping their usage across each other; every paid allowance of a month counting in it; a purchase bound late; migration seed with two rails, and a seed that must wait; a second rail bought while the first is in use; reads between registry changes in three shapes; six months of both rails with the balance checked each time; a Polar purchase while Apple is in use, with the Apple allowance returning; who joins whom with and without a free observation, from migration or activation, and with an older allowance in use; a period known in advance assigned on the day it starts; corrections applied at once, a shortened period, and a current period shortened after the next is known; a gap before a known next period; a returning rail and repeated switching; late evidence joined, and a renewal exactly on time; evidence at eight starts around an assumed cycle; an assumed cycle covering a second rail, surviving another rail in use, and an old end corrected after it was assumed; older starts, a one second correction and both edges of the two day rule; silence for three, thirteen and twenty nine months; paid to free; complimentary Pro; input order and replay; the longest allowed window IDs; the same ID on two rails and a case variant; malformed state; the fourth review's four regressions (a future period replaced and restored with and without a read, Apple starting at the instant Polar's cycle is assumed, a read and a revision at the same midnight, evidence covering two charged assumed cycles); and the fifth review's (a read at the instant a purchase becomes ineligible, evidence with exactly an assumed start covering two assumed cycles, a future period moved earlier during its gap, a report of the current period dropping a future one, a purchase first seen two months late, months replayed under old eligibility, a correction on the rail not in use, evidence across a missed gap); and the sixth review's (three registries at one instant, a free window never becoming a paid allowance, thirty calls at one instant, calls at the seed instant, evidence starting where a gap started, a future period withdrawn or moved later, an end correction reaching into assumed time, a purchase that is not eligible keeping no future period).

In the test harness every call is followed by a second call with the same arguments, which must return the same state and the same answer for the app. Direct calls in a few tests are not replayed.

One random test with a fixed seed (the fourth reviewer's generator, 600 timelines in the suite) has three purchases, two of them on one rail, events on exact period and month boundaries, corrections in both directions, old snapshots replayed, future periods and long gaps. Each timeline runs four ways: as it is; with a read one millisecond before every event and fifteen more at random times; with a read of the old registry at the exact instant of every revision, just before it; and with two other registries delivered at the instant of every revision before it. All must give the same usage and the same answer for the app at every registry event.

Outside the suite, the reviewers' own generators were run against this version: the fourth review's (3,000 timelines), the fifth review's with full ledger comparison in its ordinary, same-instant and reordered-field modes (1,000 to 2,000 timelines each, two seeds), the sixth review's added-purchase and shifted-bind-time modes (1,000 each) and its same-instant burst mode (1,000 timelines at four seeds), with no failure; and the 20 reduced regressions from the three reviews pass. During development these generators found six defects that no named test had, the last two in this version: a later registry at the seed instant being refused, and a change of bind time being treated as new evidence.

What the tests do not show: persistence after a lost reply (they replay a returned state), composition with the receipt layer, migration credit or the usage journal, how a device's entitlement combines with the account window, that inactive allowances' balances are compared between runs in the committed suite (only what counts at each event is; the fifth reviewer's generator, run outside the suite, does compare them), or that the generators reach every interesting shape.

### Not decided or built here

Real storage and concurrency (fenced revisions; ledger, allowance and counters written together; the resolver run with every registry revision); composition with the application-receipt layer, migration credit and the usage journal; retention beyond the model's 512 periods; the App Store path for an Apple refresh when no device is online; refunds, revocations and grace periods as inputs (here they are only "not eligible"); purchase aliases and case variants, which must be resolved before the registry reaches the resolver; provider proof for P-C, and the order of two corrections that arrive out of order (the model takes them in arrival order); annual products; how legacy per-device period starts become ledger entries at adoption for purchases that are not in the registry at migration; and a late charge for a window that is no longer current, which the settlement design owns.
