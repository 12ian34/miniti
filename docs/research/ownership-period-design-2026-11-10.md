# Account minutes-window transition candidate

2026-11-10. Engineering proposal and offline executable reference for B1/B2, under the confirmed D3/D4/D5/D10 policies. This does not activate account billing or close the account-period gate. The [ownership plan](../plans/account-ownership.md) remains authoritative; [settlement authority](ownership-settlement-design-2026-11-10.md) and [adoption/correction](ownership-adoption-contract-2026-11-10.md) remain separate requirements.

## Separate the three decisions

1. **Ownership:** B1 establishes the immutable owner of each purchase. This model accepts only an already reconciled registry of that account's owned subscriptions. It cannot discover ownership, trust provider metadata, resolve a backfill collision or consume customer-supplied account IDs.
2. **Entitlement:** provider status/grace and consuming-platform eligibility determine the current limit. Apple still does not grant Mac Pro; both rails do not add two 5,000-minute allowances. The model's `eligible` input is account-level provider eligibility, not permission for a particular device to record. Provider status/time validation and entitlement enforcement remain adapters to implement.
3. **Usage window:** all the account's managed minutes share one accounting window identity. A selected subscription supplies its scheduling evidence. Changing the selected subscription is distinct from creating a new allowance.

Candidate precedence preserves the current device-level Polar-first rule and makes the account result independent of member traversal. Among eligible purchases on one rail, use B1's earliest `boundAt`, then the exact opaque purchase ID for equal timestamps. A stale/future period on that winner is unresolved; do not fall through to another purchase or free allowance. A complete, stable registry snapshot produces the same winner in either input order. This does not claim identical history when different incomplete snapshots arrive at different times, nor make local bind timestamps independent of webhook arrival order. Provider/backfill ordering and registry reconciliation remain prerequisites.

## Persisted state and transitions

The candidate adds an immutable accounting-window ID separate from mutable scheduling evidence: selected source, provider start, next boundary, original window opening, observation time and the last period selected for each paid source. The reference state is now version 2; version 1 is rejected rather than treated as having no source history. This is an offline schema change, with no persisted production records to migrate. The account's current-period pointer continues to address `usage:account:{acct}:{period}`. The period segment would be an opaque server-owned window ID, not a value re-derived from whichever rail is currently selected. This revises the plan's proposed rail/start key derivation, not the namespace, and remains a proposal until the integrated period contract is accepted. Adapters must choose an idempotent ID and retain prior IDs, receipts and historical source decisions; the oracle's caller-supplied IDs do not prove that persistence.

| Input / transition | Reference decision | Balance, credit and admitted work |
|---|---|---|
| First migration seed into an already resolved paid/free account | Initialize one window; external seeding supplies existing effective opening | Initialization is not a zero-balance instruction; retain B0/D10 opening and per-device claim |
| Same source and same period | Retain | No reset |
| Add a secondary rail while Polar remains selected | Retain | No second allowance |
| Change paid source into an overlapping period, with no newly detected grant from a returning source | Retain same window ID; schedule from the new source | No copying, zeroing or reseeding; pending admissions still name the same window |
| Change paid source into a non-overlapping later period, or return to a known source that has renewed after this allowance opened | Pending paid-grant classification | Do not carry an expired balance into a possible new paid allowance or infer a second grant |
| Paid to free while the current free month overlaps the old boundary | Retain same ID; schedule the next UTC month boundary | Usage and credit carry until that boundary; current free limit applies separately |
| Paid to a free month whose start is at or after the old boundary | Rollover to that UTC month | An expired October balance does not become December free usage |
| Free to paid | **Pending classification, not implemented** | Distinguish genuine first paid activation from restore/reactivation before deciding whether to open a paid allowance |
| Same paid source, verified later non-overlapping current billing period | Rollover once | New ID starts a new allowance; old window remains for late settlements and correction |
| Same free source, next UTC month | Rollover once | New window, no old migration credit; missed empty months need not acquire balances |
| Same provider start, corrected future end | Retain ID and update boundary | No inferred renewal |
| Eligible but elapsed/future period, stale period or overlapping period correction | Pending reconciliation | No speculative reset or free fallback |

A later verified same-source period may skip cycles with no observed activity. Repeated observation of that period retains the newly opened ID. The model rejects a caller reusing the immediately previous ID, but only storage can reject every historical ID collision or make a lost-response retry atomic. Pending is a refusal to decide, not a new production HTTP response or a guarantee of uninterrupted recording.

Changing scheduling source never changes an existing admission's owner or window. When an overlapping switch retains the same ID, an in-flight charge does not need a second debit or copied carry balance. At a genuine rollover, the required adapter contract routes a later authorized end to its captured old window, under B2's deliberately changed admission-period semantics. The test explicitly supplies that old ID to the journal; it proves isolated balances, not an admission/settlement router. Read/limit checks use the current window; lifetime telemetry remains distinct.

## Preserve the existing first-paid allowance

The shipped `linkDeviceToSubscription` resets minutes when there is no stored Polar period start or when a new start arrives. Apple does likewise for an eligible new Apple period when Polar does not take precedence (`lib/usage.ts`). A generic rule that retained all free usage on first upgrade would therefore change how many paid minutes the buyer receives. This candidate does **not** select that change.

The next extension must model a verified paid grant, including a returning rail after renewal, separately from restoring/reactivating an already applied purchase period. Preserve the first paid allowance, while preventing repeated restore or rail toggling from resetting it again. It needs a durable per-account/purchase/period application receipt under the same revision as the accounting-window transition, including lost reply, first bind during seed, prior cancellation, another active rail and delayed activation. Do not infer a first grant merely because the current scheduling source is free, or bypass classification because the last observed source was paid before a lapse. The corrected rule returns the same classification outcome for a later new purchase with or without an intervening free observation. No product decision is requested by this candidate; preservation of the shipped first-paid outcome is the implementation requirement.

The F1 elapsed-window correction is accepted at backend `cf17e546`, with a residual selection-history gap: a first-seen Apple November 10–December 10 period can extend the October Polar window, then a first-seen Polar December 5–January 5 purchase can extend it again. A source previously selected for an earlier period instead reaches grant classification. Thus overlap retention depends on selection history and can suppress a possible grant across several paid cycles. This is an executed open classification case, not accepted complete billing behavior. Before production, classify first-seen sources starting after the allowance opened and extending its boundary, alongside returning-source renewals; do not infer “covered” from absence of history. The receipt extension below deliberately does not resolve this policy from a snapshot.

The candidate also waits for current provider-period evidence rather than invoking the shipped passive date advancement. This can affect availability during delayed or missing renewal delivery. Before activation, specify authenticated refresh/reconciliation and client error/retry behavior for stale active/grace records; do not ship the pure model's pending states as a blanket new recording block. Neither status eligibility nor a safe availability policy is implemented here. Review F2 also demonstrates that an overlapping same-source period remains pending on November 2, 20 and 30; it has no automatic recovery within that cycle. Whether either configured provider can legitimately re-anchor this product is unverified. Before activation, support a verified re-anchor/correction decision or establish the applicable provider restriction. Do not assume it is impossible or turn this pending state into a cycle-long recording block.

## B0, correction and lookup boundaries

The selected B0 opening remains gross sum minus the smaller current contribution. Free 200 through December 1 plus active paid 400 through November 14 yields gross 600, credit 200 and effective 400. A verified November 14 renewal opens a fresh paid window and clears the credit; the free snapshot does not add 200 back. The test now supplies both dated twins to the opening oracle and explicitly observes December 1 after the November 14 renewal, retaining the new zero-credit window. It composes period and journal decisions; it does not execute device adoption. No claim is made that this chooses the B0 boundary for ambiguous competing active twins; B0 field conflicts/source proof still require resolution before adoption.

Retained overlapping source changes preserve gross/credit in the same window; a non-overlapping free rollover starts a new window, and possible paid grants remain pending. Corrections continue to replay the original account seed component, not replace an unrelated destination or current-period total. The account transition record must be included in the correction/reconciliation history before a real adapter is accepted.

The 100 free docs lookups use their independent account/UTC-month ledger and selected activation credit. This minutes model neither seeds nor resets lookup counters. Pro/BYOK lookup eligibility and tier-at-admission remain with the lookup contract.

## Executable scope and remaining gates

Backend `scripts/account-period-reference.mjs` is an offline candidate, with no runtime imports, IO, environment or wall clock. `scripts/account-period-reference.test.mjs` uses synthetic IDs/clocks and composes with the existing journal model for credit and late-charge examples. Both the 64-record registry bound and 64-source history bound are model limits, not production caps. History records only periods adopted for scheduling, not every unselected provider snapshot; otherwise observing an unselected renewal could erase the evidence needed when it returns. History survives window rollovers. Capacity exhaustion fails instead of silently truncating old evidence. Durable application receipts, pruning and resource limits remain adapter work. Amount precision, serialized state decoding and full historical receipt integrity remain outside it.

Required before accepting a production resolver: first-paid activation/restore receipts; complete owner-filtered registry snapshots and provider ordering; actual status/grace/expiry eligibility; safe refresh behavior when period data is stale; fenced revision CAS and before-write validation; historical window-ID uniqueness and atomic replay; counters and state transition committed together; mirrored old-client usage/reset compatibility; real storage concurrency and correction replay. No new endpoint, Redis key, migration, provider request or account state is written by this package. The [release evidence](../releases/3.9.0.md#account-period-transition-reference) owns exact test and review status.

## Classified paid-period application receipts

The next offline layer, backend `scripts/paid-period-application-reference.mjs`, applies a decision already established by an authoritative owner/period classifier. It does not provide that classifier. A request, missing receipt, current selection, or provider delivery ID cannot authorize a grant. `evidenceId` names synthetic classification evidence in tests; this model neither authenticates it nor reads a provider. The implementation must establish immutable purchase ownership, the complete registry revision, current provider evidence, and historical application evidence before choosing an outcome.

| Classified outcome | Application | Retry / correction |
|---|---|---|
| `grant` | Atomically propose one new zero-usage window plus an application receipt. Preserve old gross/credit and lifetime, including captured old-window work. | Within the bounded retained history, the same account/rail/exact purchase ID/provider start returns the original receipt, even after expiry, later charges or another rollover. No second reset. |
| `covered` | Record that this purchase period was included in the migration opening or already covered by the account allowance. Keep the existing balance/window. | Never promote coverage to a grant through an ordinary retry. A mistaken decision needs an explicit correction procedure. |
| `unresolved` | No new receipt, reset, or revision change. A previously recorded decision may still replay. | Includes first-paid versus restore ambiguity, first-seen overlap, returning renewal, incomplete historical receipts, and re-anchor uncertainty. |

The identity excludes end time so a corrected end does not mint an application. It also excludes provider delivery identity, device ID, current membership, and proposed window ID. A corrected start is a different tuple but is **not** automatically a new grant: provider normalization/reconciliation must decide. Rail and purchase spelling remain exact. Another account cannot replay the receipt, including when it supplies the same tuple. The receipt reports only immutable application/window identity and revisions, not a stale usage balance.

Application and journal revisions are checked together for a new decision. Replay of an existing identity precedes the revision/current-time checks so an exact lost-response retry works after later activity. A contradictory classified outcome is rejected; unresolved replay returns the recorded outcome. New classified evidence must describe a current period and supply an evidence ID. The reference accepts no historical-window ID reuse. It reconstructs the bounded usage journal and checks stored receipts before use; each grant receipt must match its reset event, and every reserved paid reset must have an application. This corrects receiptless replay at this new boundary without changing the older journal oracle's independent contract.

A single returned aggregate contains the journal change and application receipt. This models the intended transaction, not real atomic persistence. The adapter must fence **all** writers against account/registry revisions, validate Redis types and complete payloads before writes, persist scheduling, journal, application and response together, retain the proof across membership/restore/expiry, and replay from durable state after lost replies. The tests simulate two callers against one revision sequentially; they do not run concurrent storage. Covered receipts have no reset event, so deletion/rollback of such history cannot be detected from the usage journal alone. Durable history integrity, monotonic revisions, migration completeness and retention remain mandatory.

This layer models one account’s usage with the shared arithmetic journal. The test constructor takes an existing journal; it never zeros migration usage. Any imported device-seed claim must name that same account; a foreign claim is rejected. Stored application times must be nondecreasing, and state/journal/opening/event/application entries reject unknown fields. These checks do not establish authenticity or detect a rollback to an older otherwise valid snapshot. Synthetic tests cover a classified first grant, covered migration/secondary periods, duplicate restore, corrected end, another owner's replay, renewal, old-window charge separation, journal/application corruption, stale revisions and exhausted capacity. Provider decisions are deliberately supplied, not inferred. The 64-application/256-event bounds and whole-journal replay are small-model limits, not production retention or performance decisions. The retry test now succeeds at exactly 256 events and fails closed beyond that bound, including for an existing receipt; production replay retention must not inherit this small-model availability limit. Integer/fixed-precision storage, application correction and expiry/pruning are not implemented.

**Next implementation boundary:** specify and implement the trusted classifier and durable purchase-period provenance. Test the first-seen overlap chain, delayed first bind during seed, Apple already covered while Polar was selected, cancellation/reactivation, provider start correction and incomplete backfill. Then integrate the application receipt with the period scheduler and fenced storage. No passing receipt test closes the full resolver, B1/B2, AO0 or release gates.

## Provider evidence and current-writer boundary

Static trace at backend `ca8c8c28`: Polar signed webhook subscription fields and the restore lookup supply a provider subscription ID and current start/end; neither path proves a new account-level grant. `linkDeviceToSubscription` resets when the device has no stored start or a changed start. Polar downgrade clears the device’s subscription ID and stored start, so absence can also mean lost historical evidence after cancellation. Apple verified JWS supplies original transaction ID, transaction purchase date (falling back to original purchase date), expiry, product and environment; the current link writer resets an eligible new start only when Polar does not take precedence. The verify route does not distinguish restored transaction delivery from a new purchase merely by receiving another signed JWS. None of these device mirrors is a durable grant history.

The current-writer correction compares valid parsed start instants rather than timestamp spelling when deciding whether to reset. It preserves stored provider strings, stale-start rejection, genuine renewal and first-link behavior, Polar priority, CAS retries, exact purchase IDs and response shape. This is an inherited device-accounting fix, not account ownership activation or a complete restore-idempotency rule. Matching unparseable strings retain their prior equality behavior; date validation and canonical provider-start decoding remain separate gates. The comparison uses the existing JavaScript millisecond time representation, not a new sub-millisecond provider contract.

Purchase identity reconciliation belongs to the trusted classifier: preserve authoritative provider spelling, do not apply device UUID lowercase rules to purchase IDs, and never infer an alias or fresh grant from a case-only difference. Before binding/applying, resolve any case-variant candidate against provider-authenticated identity and retained aliases/history, or leave it unresolved. The same requirement covers corrected provider starts. The existing exact-case oracle intentionally remains unchanged; its ability to apply two caller-classified case variants is not proof that either deserves a grant. Provider round-trip and alias guarantees remain unverified.
