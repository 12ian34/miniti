# Implicit state machines in the Apple apps

Dated source audit: 2026-11-08. Baseline: working tree on `63bccf4`, including the uncommitted 3.8.0 candidate. This is an architectural inventory, not a release-readiness verdict or a list of confirmed defects. No application behavior was changed.

The largest implicit machine is the meeting lifecycle in `AppState`. More importantly, it coordinates several independently progressing machines: capture, transcription, durable saving, final AI, accounting, delivery and sync. A single replacement `AppState` enum would conflate those lifecycles again.

## Scope and interpretation

Surveyed first-party Swift source under `Miniti`, `MinitiMobile`, `MinitiWatch`, `MinitiLiveActivity`, `Shared`, and root `UpdateService.swift`. Used a repository-wide scan of stored state, enums, tasks, timers and mutation entry points, followed by targeted tracing of transitions and representative regression tests. Third-party package internals, generated builds, test fixtures, secrets, the backend, website and Linux client are outside this audit. References point to the current working-tree source; line numbers are dated navigation aids and symbols are the durable identifiers.

A machine is included when earlier events change what a later event may do: pending work, retries, acknowledgement, ownership, cooldowns, recovery, editing or input parsing. Ordinary preferences, immutable response models, one-shot pure calculations, simple show/hide toggles, hover effects and cosmetic animations are not individually enumerated. Repeated instances of the same workflow are grouped and named. This is a broad static inventory, not a formal proof that every possible runtime state has been enumerated.

- **I, implicit:** state is encoded by optional values, flags, collection membership, timestamps, files or task existence, without a complete named lifecycle.
- **M, mixed:** some states/events are named, but significant legal transitions depend on additional state outside that model.
- An enum of outcomes, such as `AutoStartDecision`, does not itself own the subsequent lifecycle.
- Implicit does not mean broken. Several small machines are already well contained and have tests.

The arrows below summarize observed paths. They are not exhaustive transition tables, and labels such as “awaiting durable save” are inferred names unless shown as code symbols. Entries overlap where one workflow coordinates another; they are not a count of independent machines. For example, the recording lifecycle coordinates the separately listed stop, save and accounting workflows.

## Already explicit or well-contained pieces

Do not count every enum as a missing abstraction or rewrite these automatically:

- [`PurchaseReturnController.State`](../../Miniti/Services/PurchaseReturn.swift#L14) already names idle/checking/ready/retry/sign-in, owns polling and timeout, and checks operation/account authority. Its checkout/operation/retry metadata is normal extended state for a contained machine.
- [`SpeakerRestoration`](../../Miniti/Services/DeepgramService.swift#L462) names its phases and guards transitions. S4 identifies the remaining cross-service orchestration, not an absence of a restoration model.
- [`PersistentStoreState`](../../Miniti/Services/PersistentStore.swift#L163) explicitly distinguishes ready from failed with optional read-only recovery. U1 concerns the surrounding gate order.
- [`MainNavigationHistory`](../../Miniti/Views/MainWindow.swift#L36) owns its current/back/forward transitions. V2 concerns the state mirrored around it.
- `CallLifecycleEngine` is already a pure event-producing owner with focused tests. Its state representation is implicit, but its boundary is much better contained than the equivalent AppState workflows.
- `WatchImportJob.Status`, `WebhookCompletion.Phase`, `DeliveryOutbox.State`, `CloudSyncEngine.Phase`, model-preparation statuses and StoreKit `PurchaseState` are useful partial models. Keep them while addressing the additional dimensions described above.
- `UpdateService` delegates the update lifecycle to Sparkle and mirrors `canCheckForUpdates`; Sparkle internals are not an app-authored implicit machine in this scope. `DataFlowSummary` and most display/status helpers derive projections rather than own transitions.

## Where making the model explicit would help most

These are architectural priorities inferred from coupling, persistence boundaries and authority checks, not severity-ranked bugs or changes to the product roadmap.

1. **Recording session, R1–R3.** Introduce a session lifecycle owner carrying the meeting identity and start attempt. Keep capture phase separate from saved processing. The current concrete example is `isFinalizingMeeting == false` while the meeting remains in `finalizingInsightMeetingIDs`; that is a valid state permitting the user to start another meeting, not a contradiction to “fix.” Model it deliberately.
2. **Stop-to-durable-save-to-delivery, R2/R4/D3/D4.** Name the milestones: capture stopped, transcript durable, AI settled, delivery staged, handoff acknowledged, delivery released. An exported marker does not mean a remote CRM received the payload. Preserve the two-store hold/release protocol and the stable first-completion identity.
3. **Recording/account authority, R11–R13/U5/U6/W4.** Treat owner, credential generation, recording ID and accounting version as immutable authority attached to work. Distinguish token renewal, account mutation, pending billing and paid-result recovery. Centralize admission and invalidation without allowing an account switch to rebind old usage.
4. **Recovery, R6–R10/S3/S4.** Separate hardware health, capture delivery, transport connection, transcription evidence and speaker availability. A single `healthy` flag cannot express “socket connected but no words yet,” “diarizer timed out but worker still retiring,” or “hardware quarantined until relaunch.”
5. **Per-meeting replication, D5–D9.** Replace scattered raw sync strings and inferred fingerprint combinations with typed projections/transitions. Keep local-edit state, remote-copy state, exclusion/removal intent and folder-baseline knowledge distinct. An excluded meeting with a pending tombstone is a legitimate transitional state.
6. **AI request ownership, I1–I6.** Standardize an operation context containing meeting, mode/scope, input revision/fingerprint, request sequence and account authority. Busy flags are presentation; authority decides whether a late response can apply. Reuse the existing saved-request guards instead of replacing them with cancellation alone.
7. **Calendar automation, A2–A6.** Give each offered decision an owner and deadline, and make cancellation reasons explicit. Preserve the distinction between waiting for a call, ending grace, quiet prompt, and committed meeting handoff. They have different reversibility and speech-reset rules.

Small UI forms, parsers and one-way completion gates can remain local. A contained struct with guarded methods is often enough; this audit does not imply adopting a state-machine framework.

The recurring invariant across the app is: **finishing asynchronous work does not automatically grant permission to apply its result**. Permission also depends on the current meeting, recording attempt, account, credential generation, content revision, durable checkpoint or user decision. Most of the important implicit machines exist to enforce that distinction.
