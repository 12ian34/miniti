# Ownership admission and settlement design, 2026-11-10

AO0 design within the existing [ownership plan](../plans/account-ownership.md), complementing the [adoption/correction contract](ownership-adoption-contract-2026-11-10.md). This specifies a proposed server-owned continuation for **already authorized, frozen usage reports**. It changes no running service or client. Review of this design is not authentication, storage, migration or AO0 acceptance. The selected UI1–UI3 and B0–B5 scope is unchanged.

## Source findings that constrain the design

Backend source at `a5c93d8c` and Apple at `c937876e`:

- `clientAuth.checkClientAuth` requires the access token's account and key thumbprint to match the current installation, with proof validation for writes. After A→B, A's old token cannot authorize a normal request. Do not weaken this shared check to make late accounting work.
- `/api/session/end` constructs v2 accounting identity using the **currently authenticated account**, then locates that account's root. Both v2 `OWNER_LUA` and authenticated legacy finalization require current active membership in that owner. Retaining `accountId` in a root therefore does not let B submit or inspect A's result.
- `revokeInstallation` deletes v2 accounting roots through `removeAccountingIdentity`. A retained client report alone cannot undo this deletion. B3 must distinguish retaining authorized server work from restoring a revoked installation's general authority.
- Apple's `beginManagedAccountTransition` blocks recording/start/resume/finalization and active Watch processing, flushes pending managed reports, and blocks a healthy move while owned reports remain. Credential repair may proceed with pending reports. `ManagedSessionJournal.flush` only sends reports whose `accountID` matches the current account and retains the others within 30 days / 200 entries. These guards are useful and remain; a transfer must not start or continue an active recording on the old account.
- Ordinary recovery-key `ClientAuthManager.attachToAccount` replaces account/tokens while retaining the signing key. `clientAuthStore.attachToDestination` uses ordered account leases, writes destination membership then installation account then source removal, revokes the old refresh family and currently tombstones an empty source. There is no existing durable settlement handoff or ownership-revision field. Lease expiry and partial writes remain implementation gates.
- The inspected Linux API still sends the legacy `session/end` shape (`src-tauri/src/api/mod.rs`). A tracking fixture does not establish native v2 queue/handoff support. Record its exact supported pending-work behavior before declaring a compatible Linux version.

## Separate three identities

| Identity | Captured when | What it authorizes |
|---|---|---|
| Admission | Server admits recording/prerecorded/lookup operation | Original account, installation, operation/root, kind, resolved usage period/policy epoch and duration/reservation bounds. It grants no later general account access |
| Frozen settlement intent | Source-authorized server accepts the exact final report | One validated operation payload and its accepted charge semantics. It cannot request another provider grant, revise duration later or move the charge to another account |
| Client acknowledgment access | Membership transition commits, bound to its destination lineage | Only this operation's terminal status and accepted duration. No source usage totals, remaining quota, subscription, email, meeting content or receipt enumeration |

Deduplicate by the server accounting identity: v2 source account + installation + recording root (with matching session ID), or legacy source account + installation + session ID. A client report UUID only correlates its local queue; changing it must not buy another charge. Digest the versioned, validated semantic payload with a specified canonical encoding, not arbitrary JSON whitespace or field order. Preserve legacy versus v2 numeric/zero rules.

An installation UUID or a client-supplied old `accountID` is not any of these authorities. A root ID is an identifier, not a bearer credential. Same-account credential repair can restore normal authenticated delivery under the existing proof/recovery rules; destination ownership cannot stand in for source authorization.

## Proposed continuation: accept the exact report before membership changes

Prefer ordinary synchronous settlement first. When it succeeds, the existing receipt is enough. To avoid inventing a reusable cross-account reporting permission, use a durable **server-owned settlement intent** for a known, finalized report that has passed source authorization and validation but whose accounting completion must be retried. This is an internal storage object, not a secret capability issued to a client.

1. The compatible client freezes the pending report's owner, stable operation identity, session/recording identifiers, accounting version/kind and final duration. Persist that frozen report locally before preparing the account change. No active/interim duration may enter the handoff. No transcript, audio, recovery key or provider credential is needed.
2. While A's proof is still valid, the server validates the report using A's admission/root and the unchanged version-specific duration rules. Freeze the admitted period, requested payload digest and accepted duration/bounds. Capture both the v2 `min(requested, now − startedAt)` clamp and any legacy live-zero elapsed fallback **at this validation time** so a delayed worker cannot inflate it using its later clock. Prerecorded audio duration is not capped by elapsed grant age. V2 zero remains zero and v2 retains the approved beyond-four-hour behavior.
3. Persist the intent and its source/root references with operation identity, schema/policy version, authorization evidence references, sequence and durable status. The exact same payload converges; a changed duration/kind/owner/period is a conflict. Retain sufficient attribution and terminal receipt state for at least the existing 35-day replay margin. Initial acceptance cannot extend an already-invalid/missing admission by inventing a new start time. Missing pre-migration attribution remains unresolved under the selected B2 contract.
4. Link the prepared intent set to the account-transition record. Do not consume an enrollment approval or change membership merely because the client claims a handoff succeeded. The final transition commit rechecks source/destination authority, expected ownership revision, B1/B2/B4/B5 prerequisites and that every referenced intent is durable and belongs to this source/installation. Empty or incomplete preparation must not erase pending work. Bound payload size and cardinality, and use resumable preparation if the client queue exceeds a measured per-request budget; no unbounded journal scan in the commit.
5. The server can finalize an accepted intent before or after the move using the **captured server authority**, not B's credentials. Its transaction compares the immutable intent/root, account-deletion state, policy version and operation receipt, then commits the charge, journal/ledger entry and terminal result together. Exactly one side wins if ordinary end and the worker race. The new worker is not allowed to call the existing general route pretending to be A, or bypass its auth check for arbitrary payloads.
6. A move may proceed only once the server has reconciled its bounded source/installation root index (currently at most 4096 v2 roots), not merely the client's report list. Each open admitted root must be finalized, durably accepted, or assigned an explicit server-owned terminal disposition under the outcome table below. A client omitting a report or declaring it abandoned does not satisfy the gate. Legacy/prerecorded admission needs a bounded equivalent index before this gate can cover those paths. Close further source admission at the transition boundary and recheck the index revision during commit. A failed/cancelled transition does not invalidate an already authorized usage report: server settlement may still finish for A. Normal source receipt access remains authenticated. Destination acknowledgment access is enabled only by a committed transition and bound to that transition's destination installation lineage.

Existing legacy receipts may contain only cumulative usage and finalization flags, with no payload digest or accepted-duration value. Do not promote them into invented exact-duration evidence. Resolve them through the existing source-authenticated replay path before the move, or keep their handoff unresolved until a compatible legacy receipt adapter is specified and tested. Never charge them again to manufacture a stronger receipt. New receipt fields cannot be assumed present on historical records.

This allows a report accepted before A→B to finish or have its acknowledgment retried twenty days later against A's captured period. It does **not** allow B to introduce a previously unknown A report twenty days later. Without a source-authorized frozen intent, the report must await valid source-account repair/return or remain unresolved; no generic “old account id plus current B proof” exception is added.

The client removes a pending report only after an acknowledgment matches its exact operation/payload and accepted-duration contract, and the local removal persists. An accepted-but-pending intent is not a successful charge and must not update usage UI or discard the report. The destination acknowledgment response deliberately has no `minutes_used`/`minutes_remaining`; the client obtains B's balance through its ordinary current-account read. Old clients never receive the new acknowledgment shape on their existing end path.

## Outcomes and activation prerequisites

| Server outcome | Move allowed? | Local pending report | UI / operational meaning |
|---|---|---|---|
| Charged with valid terminal receipt | Yes, subject to other transition gates | Remove only after matching acknowledgment and durable local write | Usage saved |
| Accepted-pending with durable frozen intent | Yes, once server index/transition checks pass | Retain report or a durably recoverable handoff record until terminal acknowledgment; do not treat acceptance as a charge | Usage is being saved; no source balance shown on B |
| Terminally rejected, confirmed no charge | Yes only with a durable server disposition tied to operation and source authority | Remove after matching terminal acknowledgment is persisted; retain bounded diagnostic outcome | Explicit failure/expiry, never success or accepted duration |
| Unresolved, including missing/corrupt receipt or incomplete legacy evidence | No ordinary move while a live admitted root remains unresolved | Retain within the documented queue bounds; expiry/capacity is not proof of settlement and cannot silently release the server gate | Retry or same-account repair; operator investigation for irrecoverable records |

A client cannot request terminal abandonment to bypass quota. Only the server's validated terminal condition (for example expired admission under the existing retention rule or explicit account deletion) or a reviewed, audited correction procedure can close an unresolved root without a charge. Record the root, disposition reason and zero-charge result without fabricating accepted duration. Expiry is finite, but a transport error alone is not terminal. The precise disposition/retention adapter remains a readiness gate; until it exists, do not activate a flow that strands users behind irrecoverable records. Local 30-day/200-entry pruning must produce an observable unresolved outcome and reconcile with the server index; accepted handoff recovery metadata must remain available through its server receipt window. Test overflow and expiry, not just successful queue removal.

Activation requires B3's stop-tombstoning-on-move behavior in the same coordinated stage. The current last-device attach marks A deleted with a 30-day TTL; that cannot coexist with a worker that rejects charges to deleted accounts. Dormancy's “holds anything” check must count accepted intents, retained root/receipt obligations and transition evidence, so a 30-day empty-account cleanup cannot destroy the 35-day continuation window. Explicit user account deletion remains distinct and takes the ordered rejection path below. No standalone settlement activation ahead of these prerequisites is permitted.

## Revocation, repair, deletion and replay boundaries

| Event | Required outcome |
|---|---|
| A→B commit, response lost | Durable transition outcome and intent identities support the existing narrow exact-request replay design. No second move, charge or approval consumption. Credential/token replay mechanics still need implementation tests |
| A→B→C or B→A→B | B's old acknowledgment grant does not become valid in C or on a later B membership. Add a monotonic ownership revision/lineage, distinct from a token refresh; same key/account spelling alone is insufficient |
| Same-account key repair | Existing valid recovery/proof can restore ordinary delivery. If an acknowledgment binding survives same-owner repair, prove the same ownership lineage; a reused/re-created installation starts a new lineage and receives no old grant |
| Revoke after a frozen intent was accepted | General credentials and future admission are revoked. The server may complete the previously authorized frozen charge; it grants no client right to read A. Cleanup must retain only the required intent/root evidence, not resurrect account access |
| Remote removal before intent acceptance | No new intent can be prepared with the revoked key. Retain the client report within its bounds for valid source repair where permitted; never silently charge the destination |
| Source account explicitly deleted before charge commit | Reject further settlement without recreating its account/period. Preserve only the deletion-compatible audit outcome and required retention. If the charge committed first, deletion must not cause a second charge or revive credentials on replay |
| Source goes dormant after last-device departure | Dormancy is not deletion. Accepted work keeps its source account, and paid ownership remains there. D6 notice delivery is a separate outbox/transition concern |
| No source signing key and cross-account restore | Destination recovery proves only B. It cannot authorize A's pending report. Preserve the existing same-account-repair route; no new capability can be minted from client-stated ownership |
| Worker crash, duplicated wake-up, failed reply | Retry the same intent; atomic receipt/charge commit and ownership-safe fencing decide once. A worker lease alone is insufficient |
| Receipt expired, missing or corrupt | Reject replay as unresolved rather than infer success, rerun a charge or return an undefined acknowledgment. Keep client queue/receipt lifetime semantics explicit |

The acknowledgment binding requires a durable ownership revision that ordinary refresh does not change. Define how it is compared by the route and transition transaction, including same-account repair versus revoke/re-create. This design does not establish a signed claim format, endpoint name, storage key layout, worker runner or retry schedule. Those are implementation contracts to pin with real wire/storage fixtures before activation. No change to existing request-proof cryptography is proposed.

## Period boundary constraints and unresolved resolver

Shipped 3.8.0 v2 and legacy ends charge the device period at **finish time**: the route re-reads after a reset conflict, and `resetDate` in Lua is a concurrency check, not captured-period attribution. B2 deliberately changes this for its new attribution policy epoch. Old-epoch completion behavior and new-epoch behavior must be distinguished in mixed-version fixtures; this is not unchanged metering semantics.

For the new B2 epoch, capture the resolved minutes period at admission, independently of the consuming platform's entitlement check. Do not recompute it from the device's reset date at completion, a different member returned first by Redis, or whichever provider callback arrived last. Lookup admission separately captures UTC month, tier and the lookup policy epoch. An operation completing after rollover retains its captured period; it must not clear the new period or create another allowance.

Current `computeEntitlementState` prefers active Polar on one device, otherwise Apple, otherwise a UTC-month free reset. `findSponsor` returns the first eligible member from an unordered membership traversal. Neither is a deterministic account-period algorithm. Polar eligibility across platforms and Apple eligibility on iOS remain unchanged; allowing both rails does not imply two additive 5,000-minute allowances or a second reset for the same consumption.

The [account-window candidate](ownership-period-design-2026-11-10.md) now supplies executable source-switch/renewal cases while retaining first-paid activation and stale-provider availability as unresolved boundaries. It proposes a stable balance identity across source changes; no production resolver is activated.

The resolver must explicitly decide first seed, a second active rail, renewal, expiry, cancellation/grace, reactivation and free↔paid transitions. Preserve an already admitted operation's period and distinguish provider entitlement status from allowance-window allocation. Choose a stable account state and monotonic transitions, not a request-dependent platform winner. These are engineering rules still to finalize under the confirmed product policies.

B0's selected rule remains: use the active-subscription holder's reset boundary, otherwise the later boundary, and clear migration credit at the next genuine reset. The earlier design wording that prohibited resetting the other twin's contribution contradicted that rule and is withdrawn. Retain original contribution boundaries for audit/correction and any later free fallback, but provenance retention does not mean charging those contributions again in a renewed paid period. A no-subscription later-date fallback is not a delay of an active paid renewal. Grace/expired-provider eligibility and any later free fallback still need explicit resolver cases.

- Free twin 200 through December 1 and active paid twin 400 through November 14 at November 10: opening gross 600, credit 200, effective 400. At a genuine November 14 renewal, the new paid period starts at zero and the old credit clears. Do not carry the free twin's 200 into that renewed paid period merely because its original timestamp was December 1. Preserve its original snapshot for provenance; later downgrade handling must not reseed the same usage.
- Both rails active with different starts/ends, in either callback/member order: the same account gets the same period selection; an Apple-only consuming Mac still fails Apple eligibility even if that subscription supplies account-period evidence.
- An added or cancelled rail halfway through a period does not reopen an empty balance or reassign existing session attribution; ordinary genuine renewal behavior is stated and tested explicitly.
- A late completion, correction or held provider callback after rollover updates only its intended history. A missing interval/source boundary is unresolved, not guessed from the current installation.

No two-rail resolver is selected by this document. There is no pending policy question for Ian; design/review and synthetic timelines must settle the remaining engineering tradeoff. If that requires changing the agreed allowance or billing-cycle behavior, stop and expose that concrete policy change instead of calling it normalization.

## Watch admission boundary

The Watch has no standalone backend/account identity. `WatchImportService` chooses `job.managedOwner ?? currentAccount` when beginning processing and persists `managedOwner` with the successfully returned prerecorded grant. `WatchRecordingManifest` carries recording/segment metadata, not a miniti account grant. Therefore audio recorded offline before A→B but never admitted for processing on A is first admitted under B when the phone processes it there. This preserves existing behavior; physical recording time is not billing admission.

A job with persisted A ownership, a paid full/part checkpoint, or queued A settlement retains A. The importer rejects processing on a different current account and requests return to the original account. These states must not be grouped with unadmitted Watch audio. Existing active-import guards stay. Add fixtures for offline-untransferred audio first admitted under B, an A-owned dormant job refusing B, and a paid A result retained across the move without a second upload/charge. No physical Watch execution was performed for this source finding. Absence of local `managedOwner` is not proof that the server never admitted the job: the grant reply can be lost, or the account can change before the post-grant guard persists owner/session ID. Add both fixtures, with B retrying after the unrecorded A admission, to the bounded legacy/prerecorded admission-index gate. That gate must reconcile server evidence; the local nil field cannot authorize treating the old admission as nonexistent.

## Required implementation evidence

Use the existing metering/root, request-proof, account-attach, enrollment-link and client-journal suites. Add real isolated Redis tests for intent/normal-end races, authorization-to-commit revocation/deletion, prepared/committed transition crashes, stale fences, key rotation and acknowledgment lineage. Add Apple/Linux wire fixtures for pending versus terminal status and for old endpoint compatibility. Hold a source-authorized frozen report across A→B and twenty days, and assert exactly one A-period charge with no source totals exposed to B. Repeat with missing source authority: refusal, no charge to either account, no queue deletion.

Exercise both legacy live-zero and v2 zero, >4h v2, prerecorded duration, wrong payload, wrong root/owner, forged period, revoked/reused ID, lost local queue persistence and source deletion. Verify active recording/Watch guards through real client entry points. The server's bounded worker and retention/resource cost require measurement; no storage/crypto/transport tests ran for this design. D6 notice idempotency, provider first-bind evidence, deterministic period resolution, private inventory/D9 and the complete AO0 readiness gate remain open.
