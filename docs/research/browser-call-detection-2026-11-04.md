# Browser call detection research, 2026-11-04

Research for [CD1](../plans/browser-call-detection.md). Read-only source, SDK, public documentation and installed-bundle inspection. No app runtime changes, hardware capture, Arc reproduction or deployment. The reported Arc failure remains unresolved; this document narrows the investigation rather than claiming a fix.

## What is established

`CallActivityMonitor.captureSnapshot` polls once per second. It requires `kAudioProcessPropertyIsRunningInput == 1`, then a nonempty `kAudioProcessPropertyBundleID` accepted by `CallApplicationDirectory`. Missing input properties, unknown identities and empty identities are skipped. Only process-list query failure marks the snapshot unreliable. Arc is already registered as `company.thebrowser.Browser`; known helper prefixes are accepted. There is no PID-to-running-application ownership fallback. This is an input-stream detector, not a Meet membership detector.

Apple's installed Xcode SDK `AudioHardware.h` documents IsRunningInput as IO running with an active input stream. Its bundle-ID property describes the process identity, not the web page. See [Apple API](https://developer.apple.com/documentation/coreaudio/kaudioprocesspropertyisrunninginput). Input and output device lists are selected by property scope; miniti currently reads process devices globally. Verify direction-specific scopes when using device evidence. This does not by itself explain missed starts because device IDs are not required for a process to enter activeCalls.

The [W3C Media Capture specification](https://www.w3.org/TR/mediacapture-streams/#life-cycle) allows a live track without active device capture and recommends relinquishing the device when all tracks using it are muted/disabled. Therefore joining muted can defeat microphone-only detection. This is a standards-level possibility, not a measured claim about the affected Arc/Meet version. Speaking is not a prerequisite for an input stream; a quiet but unmuted microphone may remain active. Reported speech before ten minutes means mute alone is insufficient as a diagnosis.

The calendar gate treats a reliable snapshot as detection availability, with no coverage or age check there. It auto-starts only in T-5 through T+10. After T+10 even positive activity produces a no-show prompt, pinned by `AutoStartPolicyTests.testNoShowAsksOnceThenStaysQuiet`. If detection becomes unavailable after the separate two-minute clock grace, the fallback can return none. A stopped current meeting also blocks ordinary checkAutoStart and routes into calendar transition logic; this is another regression case, not the explanation for the supplied no-show screenshot.

`AutoStartBanner` in `MeetingView.swift` already provides Join, Start now and dismissal while waiting. Earlier statements implying no manual action exists anywhere before ten minutes were too broad. Verify floating panel/menu-bar parity and discoverability. The later prompt's claims that the meeting has not started and nobody joined remain unsupported.

## Granola comparison

Current [notifications documentation](https://docs.granola.ai/help-center/taking-notes/notifications) says ad-hoc prompts detect microphone use. Its [transcription documentation](https://docs.granola.ai/help-center/taking-notes/transcription) distinguishes user-opened notes and calendar-time starts from automatic meeting detection. A calendar reminder alone is not proof of successful live-call detection. The customer report remains valuable; the exact Granola path used is unknown.

A broader [Granola troubleshooting article](https://www.granola.ai/blog/granola-integration-troubleshooting-common-issues-solutions) mentions browser tab URLs as well as microphone activation. This does not specify its current browser/permission matrix or prove which mechanism handled this incident. Prefer the concrete help-center behaviour over inferring private implementation.

Read-only strings inspection of the locally installed Granola 7.469.1 `macos_mic_apps_with_devices.node` found `getActiveInputProcesses`, `runningApplicationWithProcessIdentifier:` and `bundleIdentifier`. These show a process-to-application lookup exists in that module; they do not establish its control flow, fallback order or current released behaviour. It is an older local installation and was neither launched nor used to capture customer data. The existing August archive inspected a different version and is historical.

[Chromium's helper plist](https://chromium.googlesource.com/chromium/chromium/+/refs/heads/main/chrome/app/helper-Info.plist) uses a helper bundle identifier derived from its configured browser ID. This supports testing helper attribution but does not reveal Arc's actual HAL identity. No verified Arc helper mismatch was found in this pass.

## Recommended implementation sequence

1. **Observe before guessing.** Add an injectable snapshot reader and bounded local diagnostic trace of process read results, input/output flags, resolved known owner, snapshot age and calendar decision reason. Exercise a signed sandboxed candidate with Arc/Meet, muted join, unmute, background, device switch and leave. Keep raw process observations local to explicit QA; exported support fields must remain bounded and consent-governed. Do not infer root cause from a generic backend success event.
2. **Repair process attribution and sensor health.** Try verified HAL identity, then a public PID-to-running-application/bundle lookup when needed. Validate sandbox behaviour and helper ownership; cache by process lifetime, not PID alone. Do not map generic WebKit processes to Safari without checking ownership when ambiguous. Read failures and unresolved active inputs remain unknown, not reliable absence. Retain polling until measurements justify a different mechanism; listener registration alone does not prove notifications arrive.
3. **Repair calendar policy.** Remove the unconditional T+10 rejection of newly positive activity for a still-eligible selected event. Continue bounded observation until event expiry or explicit Skip, preserving overlapping/back-to-back event decisions and one start owner. Make failure/unavailable transitions explicit at every elapsed time. The scheduled clock alone must not silently start empty recordings, the prior regression that introduced this gate.
4. **Separate corroboration from proof.** Evaluate output activity from the same resolved browser as supporting evidence for muted calls, combined with calendar/join context. Browser audio alone can be music and cannot authorize an automatic start. A reliable fully muted/no-audio joined state cannot be inferred from Core Audio flags alone. If that state must auto-start without a user Join action, evaluate an explicit meeting-state browser integration as a bounded design decision, not a guessed audio heuristic.
5. **Preserve accurate completion.** Loss of input during mute is not a hang-up. Keep end decisions conservative with continued output/reconnection evidence and a reversible grace. Ensure one recording/save/usage owner and test miniti/Granola running together so a note taker's mic never becomes evidence for the call.
6. **Verify every browser claim.** Run the selected inventory from CD1 against real OS/browser versions, including negative controls: pre-join lobby, dictation, music, an unattended calendar event and two meetings in one browser. Record false negatives and false positives. A populated allowlist and pure policy tests are insufficient.

A browser extension can exchange state with a native app via [native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), but packaging, browser support, meeting-page state, installation friction and the existing Mac sandbox require a separate design. A meeting URL alone proves neither joining nor leaving. Accessibility/UI scraping, camera monitoring and a new extension are not selected implementations in this research pass.
