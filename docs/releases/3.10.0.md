## Decisions

### Confirmed and carried forward

### Engineering choices to record before the slice that needs them

- **E-1 `appAccountToken`** (AO2.6): recommended for new iOS purchases. Map the miniti account ID to a stable UUID (UUIDv5 over the account ID in a fixed miniti namespace), store the mapping server-side, verify it in `/api/apple/verify`. Never treat it as proof for old receipts or as an automatic account switch.
- **E-2 Two-rail period resolver** (AO0.1): extend the accepted offline references to first-seen overlap, paid-grant vs restore classification, a returning rail after renewal and stale provider periods. Must be accepted before AO2/AO3 writers.
- **E-3 Delayed first bind** (AO0.2): if a Polar sandbox round trip proves `miniti_checkout_account` metadata arrives on the subscription webhook and survives, use provider metadata after the seven-day `checkout:return:` record expires. If not, design durable pre-bind capture with explicit retention before AO2.2. Absent proof means `unresolved_owner`.
- **E-4 B5 adoption timing** (AO5.2): adopt legacy tokens eagerly inside the transfer/re-enrollment precondition (source-ownership step), not lazily on first status after transfer, so a move before first status cannot misattribute (audit P8).
- **E-5 One SwiftData schema step** (AO6.2 + CK1): CK1 is a cadence change and should need no schema change. If it turns out to need one, it joins B4's single schema version and migration review. Either way, the faster checkpoint must be tested running on the first launch after the B4 migration, against a real 3.9.0 store fixture.
- **E-6 One content form for sync baselines** (SM1.2): the content identity used by the three-way merge comes from one function for local and remote documents, where an absent key and a null value are equal, defaults are filled and keys are sorted. Only the content baseline gets a version prefix; the folder baseline has no form problem and stays as it is, so the legacy folder refresh rules (`pending_folder_refresh`, the `legacy-content-unverified` marker, the nil-baseline predicates) keep working unchanged. A stored content baseline without the prefix is the old hash of either the local or the server form, so it is compared with the old function over both forms, which merges dirty meetings exactly with no timestamp guess, and is then replaced by a current one. Baselines live in the existing optional string columns: no SwiftData schema change, E-5 unaffected. A 3.9.0 build run later on the same store does not recognise a prefixed baseline and falls back to its timestamp rule for that meeting; nothing is lost, it merges as 3.7.0 did. The server-side fill (SM1.5) is judged separately.
- **E-7 Sign-in failures keep their cause** (SE1.2): a failure while refreshing the sign-in token carries its cause (transport, rate limit, key not usable right now, key unusable, server error, other) to cloud calls. Whatever shape carries it, the six sites that act on `ServiceError.serverError` today behave exactly as before for these failures (a seventh match, the `errorDescription` formatter at `Miniti/Services/MinitiAPIService.swift:1212`, only builds text and gets a wording check, not a behaviour guard): `Miniti/Models/AppState.swift:10464`, `:10975`, `:11555` (`deliveryOutcome`, which must keep returning retry so a webhook or CRM send tried just after wake is never rejected for good), `Miniti/Views/MainWindow.swift:4176`, `Miniti/Services/AIRequestDiagnostics.swift:28` and `Miniti/Services/MinitiAPIService.swift:1423`. A guard test pins each. No new retry loop.
- **E-8 Stall evidence signals** (TG1.2): bounded numbers only. The Deepgram service gains two small pieces of state it does not have today, the time of the last socket message of any kind and a count of `SpeechStarted` events, beside the empty-result and audio-sent counters it already keeps. All of them reset on every connect today, and the detector itself reconnects at each step, so the evidence is accumulated across forced reconnects for the life of one gap. Each event names the transcription engine, because the on-device path has no socket and no speech events. No audio levels per sample, no transcript text, no new timers on the audio path.

### CS1: the account cloud switch is read back (confirmed)

**Cause (finding N22).** `setAccountCloud` stores the switch as the text `'1'` or `'0'` (`lib/clientAuthStore.ts:181`). ### SM1: sync merge compares like with like (confirmed)

**Cause (finding N24).** The three-way merge added in 3.8.0 (`mergeComponents`, `Miniti/Services/CloudSyncEngine.swift:1229`) decides which side changed the content by comparing hashes of the local document, the remote document and a stored baseline (`:1240`). The local document of a recorded meeting always carries `external_source: null` and `external_id: null` (`Miniti/Services/MeetingSyncDocument.swift:113`). The server deletes both keys when they are null before storing (`lib/syncDocument.ts:88`, since 3.0.0), so the document that comes back never has them, and the hash (`contentFingerprint`, `MeetingSyncDocument.swift:355`) differs for identical content. The baseline is taken from the local document after an upload (`CloudSyncEngine.swift:778`, `:792`) and from the remote document after every merged download or refused upload (`:1263`). Whichever form the baseline has, one side always looks edited when it is not: after a merge, untouched local content reads as "edited locally"; after this device's own upload, every remote document reads as "edited remotely". The existing test transport keeps the null keys, which is why the tests pass.

**Consequences.**

1. *Re-upload (observed).* A device whose baseline came from a merge receives a folder-only change from another device, keeps its "edited" content, marks the meeting dirty and uploads it again with a new timestamp. Observed: 26 of 26 on a 3.8.0 Mac on 2026-11-10, and 74 of 80 on the iPhone on 2026-11-12 (6.3 MB, during a recording). Of the 6 the iPhone did not re-upload, 4 are the account's only 4 imported meetings, the one kind of document that keeps both keys. 280 of Ian's 284 cloud documents lack the keys.
2. *Older content replaces a newer edit, first direction (derived).* Device B has merged the meeting once before. Device A edits content (a new summary, a renamed speaker). Before downloading it, B makes a later folder move. B's merge sees both sides "changed", takes the newer timestamp, and uploads B's older content over A's edit. The right result is A's content with B's folder.
3. *Older content replaces a newer edit, second direction (derived, found in review).* Device A, the recording device, edits content at one moment. Before A's upload lands, another device uploads a folder-only change with a later timestamp; a re-upload from consequence 1 is exactly that. A's upload is refused, A's merge sees the remote content as "changed" although it is not, the remote timestamp is newer, and A discards its own edit. This needs no earlier merge, so it applies to any meeting on the device that recorded it.
4. *No settling with three devices (derived).* With one device in the local form and two in the server form, and each new revision seen separately, every upload can trigger exactly one more. Separate sightings are likely while a device records, when passes run often. Not observed; Ian's third device was offline during both bursts.

Consequences 2 to 4 follow from the code and have not been seen in production data.

**Related (finding N25).** A sync pass uploads before it downloads (`CloudSyncEngine.swift:513`, then `:517`). A Mac that stopped mid-upload on 2026-11-10 with 50 folder edits pending came back on 2026-11-14 and sent 50 full documents against old revisions. All were refused with 409 and resolved correctly to the cloud copy, because the other Mac had filed the same meetings on 2026-11-11. Correct result, wasted work, and "Uploading 1 of 50" for uploads that could not succeed.

### TG1: transcript gap evidence, alerts and detector (confirmed)

**How it works today (findings N26, N27).** Every 4 seconds while recording, `checkTranscriptHealth` (`Miniti/Models/AppState.swift:3888`) asks whether no transcript text has arrived for more than 20 seconds while "audio activity" was seen in the last 60 (`evaluateTranscriptHealth`, `:3806`). Audio activity is loudness only: microphone level above 0.008 or system audio above 0.006 (`:2151`). True silence never triggers it. A fan, typing, hold music, a video, or a room before anyone speaks can. When it triggers, the app sends `transcript_starvation_detected` and reconnects to Deepgram (`scheduleDeepgramReconnect`, `:2895`). The reconnect drops the socket without asking Deepgram to finish pending words (`DeepgramService.disconnect`, `Miniti/Services/DeepgramService.swift:1089`), audio sent while disconnected is dropped, and on Mac with both sources the speaker identity resets. After each reconnect that brings no words, the wait before the next one doubles: 60, 120, 240 seconds. So detections land at about 20, 80, 200 and 440 seconds without words. The backend emails when a reported gap is at least 120 seconds (`lib/clientIncidents.ts:17`, `:156`), and the first detection past 120 is always the third, at about 200. That is why so many alerts say 200: it is a step, not a measurement, and the real gap was between 200 and about 440 seconds.

**Field sample, 2026-11-12 17:00 to 2026-11-13 21:17 UTC** (33 finished recordings, 13 devices, 21.5 recorded hours, from the admin client-events read):

- 17 of 33 recordings had at least one detection; 146 detections, each one a forced reconnect. 108 of the 146 reported a gap under 30 seconds.
- 14 of 33 recordings were reconnected in their first 90 seconds, before or just as anyone spoke. The clock starts at Record (`AppState.swift:8879`).
- 8 stretches reached 200 seconds or more, in 4 recordings: 2 at the start of a recording, 2 in its last 5 minutes, 4 in the middle (3 of those in one recording of 3 hours 41 minutes). All 4 recordings have words.
- 3 recordings ended with speech seen and no words at all. That is the "lost meeting" signal, which uses Deepgram's own speech detection and is the alert worth keeping.
- Ian's flagged call of 13 Nov has words only from 5:40 to 36:14 of its 41 minutes, with a line about every 12 seconds in between and no detection there. All six detections were before the call started or after it ended. His 3 hour 41 minute recording of 12 Nov has 17 quiet stretches of 90 seconds or more, and its four flagged moments sit inside four of them. (Segment times and lengths only; no transcript text was read.)
- After 15 of 107 forced reconnects with a measured outcome, words came back within 2 seconds of the new connection, and after 46 within 5 seconds (33 of 41 on iPhone). Words that fast mean someone was talking as the socket was dropped. Reconnects took 0 to 1 second and dropped a median of 0 audio packets, so what a reconnect costs is the unfinished sentence, not the gap.

**Experiment, 2026-11-14.** Deepgram was streamed directly with the app's own listen settings (`DeepgramService.makeListenQueryItems`), about 14 minutes of audio. Script, method and full numbers are in [scripts/stall-probe](../../scripts/stall-probe/README.md).

- *A healthy socket never goes quiet.* Over 60 seconds each of digital silence, pink noise just above the app's loudness threshold, steady tones and speech, Deepgram sent a message at least every 1.13 seconds. For non-speech audio they are empty results.
- *Speech events separate speech from noise.* No `SpeechStarted` event in 3 minutes of silence, noise and tones; 15 in 60 seconds of speech. The event arrives 0.08 seconds after speech starts and the first words 0.5 to 1.2 seconds after.
- *A forced reconnect during speech costs a sentence.* Replaying the app's sequence (keep sending for 1 second, drop the socket without finishing, reconnect) at five points in 70 seconds of continuous speech lost 7, 4, 12, 13 and 12 words, against a reference that repeated word for word (168 of 168). The lost words are the unfinished line, up to 5 seconds before the drop; the app shows that line but saves only finished lines. Had the unfinished line been kept, the loss would have been 1 to 3 words.
- *Today's rule can fire exactly when someone starts talking.* After 20 quiet seconds the first loud sample satisfies it, and words take 0.5 to 1.2 seconds to arrive, so a 4-second check lands in that window roughly one time in three to eight.

**Conclusions (decision TG-2).**

1. A dead socket shows directly and sooner: no message for 10 seconds, against today's 20 seconds of loudness without words.
2. Noise shows directly: messages keep arriving and there are no speech events.
3. The loudness rule finds nothing those two signals miss in any case measured, and it costs about a sentence whenever it fires during speech. No reconnect in the field sample is known to have fixed anything.

So the detector changes in 3.10.0. One thing stays unproven: whether a socket can stay alive, still sending empty results, while failing to hear real speech. TG1.4 keeps a slow fallback for that, and TG1.2's evidence measures whether it ever happens. One speech source, one network and one day were tested; TG1.3 checks the result on real recordings before release.

**What counts as an incident (decision TG-1).** An email is for something the operator can act on now. Everything else is a trend for the weekly digest.

| Email | Why it is a real problem | Signal |
