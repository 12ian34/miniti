# 3.8.0 release retrospective

2026-11-06. Written for Ian by Claude (reviewer) and Astra (implementer). Claude drafted it, Astra corrected and extended it, and Claude folded in the points both agree on. Astra's own view is kept unedited in its section. Ian approved it for the public repo. It names no customers.

## Summary

- 3.8.0 changed too many risky areas in one release, and we had no rule for when to stop reviewing. Preparation spanned 4 to 6 November, ten review rounds and seven build numbers (150 to 156). Ian repeatedly had to coordinate the work. We did not measure his active hours.
- About ten findings across the rounds would genuinely have hurt users (see the table below). Holding the release for them was right, whichever round they arrived in. Many smaller findings could have shipped as known issues, but only after a stated harm and likelihood, not because of their label.
- Most of the repeated findings came from three weak spots in the code: recording state spread across `AppState`, older clients dropping sync fields they don't know, and device IDs stored in two spellings.
- The tests are real but leave important gaps between components and in signed, physical and mixed-version environments. Several missed races and compatibility rules can be tested without real hardware. Passing hosted tests cannot establish physical or signed-upgrade behavior.
- For 3.9.0: release one or two risky areas at a time, write the rules before the code, review each piece as a diff, and separate "blocks release" from severity. Aim for two full reviews and one final package. These are targets: a confirmed blocker still gets fixed after round two. Usability builds Ian asks for are fine, labelled separately from the release candidate.

## What went wrong

### Findings that justified holding the release

| Finding | Found | Harm if shipped | How we could have caught it earlier |
|---|---|---|---|
| Folders erased when 3.7 and 3.8 devices share a cloud account | Build 154 review | Data loss on upgrade | A test running a 3.7.0 build and a 3.8 build against one test account. A server contract that older-client writes preserve fields absent from their schema. |
| Watch import charged twice when all parts were already saved | Build 154 review | Wrong billing | A randomized test checking the rule "each session is billed exactly once" across retries, cache states and relaunches. |
| Legacy migration could miss a record stored under the other device-ID spelling | Field report and source review, already in production | Lost access or a replacement account | Contract fixtures with both cases and explicit recovery before replacement. The exact cause of the reported account replacement remains unproven. |
| Audio hardware calls could hang the app | Field report and source review, already in production | App freeze mid-call | Fault injection for a hardware operation that never returns, plus physical route-change testing. The specific field hang's root cause remains unproven. |
| One unreadable meeting blocks all cloud sync during the folder refresh | Build 155 review | Sync stops for that device | A design rule that one row's failure never blocks a batch, plus tests with corrupt and missing rows. The bug came from the fix for the folder-erase bug. |
| Pro usage settlement broke on a timestamp-format mismatch | Earlier rounds | Wrong billing for Pro | Contract fixtures for every timestamp format the clients and backend exchange. |
| Managed starts could stay stuck until relaunch after a failed start | Earlier rounds | Can't record | Rule tests for recording admission: every failed start returns to a startable state. |
| Connector refresh used up OAuth credentials before taking the account lock | Earlier rounds | Connector disconnected | A design rule: take the lock before using a single-use credential. |
| Automatic CRM delivery could run twice | Earlier rounds | Duplicate records in a customer's CRM | A rule test for "delivered at most once automatically". |
| Exports could overwrite files, including folder-only changes reaching Markdown export | Earlier rounds and build 155 | Lost edits made outside miniti | One export entry point with a rule for which changes rewrite a file. |

Claude's first draft listed only the first five. Astra pointed out the later five also justified holds. Claude agrees: they were real defects with concrete harm, not cleanup.

### Churn that didn't justify itself

- Many Lows were fixed in the same pass as blockers, increasing the validation surface. Not every Low was accepted. The 120-second account lease and bounded migration preflight were retained deliberately. Corrupt Watch checkpoint recovery was initially deferred rather than risking another paid upload. Full suites and signing were batched, not performed for every fix.
- Repeated broad reviews reopened the uncommitted tree. Fresh reviewers found issues in previously reviewed code, including after a pass reported no remaining High or Medium findings. Closure was temporary rather than tied to an agreed coverage boundary.
- Scope grew after the original four-workstream plan. Ian explicitly requested browser detection, folders, completion changes and setup refinements. Field incidents added audio and migration work. These were authorized changes, but we did not consistently reset the readiness estimate and validation plan when accepting them.
- The release state was copied into AGENTS.md, the checklist, the evidence record and the planning audit, and every round updated all four.

## Root causes

1. **Too much risky scope at once.** Five areas where a bug costs money, loses data or locks someone out: billing, sign-in, mixed-version sync, Watch billing and audio hardware. This draft does not establish a measured comparison with earlier releases.
2. **Some fixes created new bugs.** These areas have many states: upgrades, mixed versions, relaunch mid-operation, retries. Several fixes added guards or retry state without covering their effects on other work. Later reviews found those interactions.
3. **No commits, no diff-only reviews, no stop rule.** The review process made the second cause worse.
4. **The foundations make every change harder.**
   - `AppState.swift` is 14,207 lines and `MeetingView.swift` 3,800, so features interact through shared state.
   - Recording, per-meeting sync and Watch jobs have state and policy helpers, but lifecycle rules remain distributed across flags, counters, marker strings and callers. Reviewers reconstruct the interactions each round. The audio Mediums in build 155 exposed one "audio unavailable" state that did not reach every button, prompt and post-await check.
   - Older clients cannot preserve fields they never decoded. Server retention protects some fields, but upgrade baselines and later writes also need explicit compatibility rules.
   - The backend builds `device:` keys by hand in 36 places across 13 files, and only about 8 of those visibly handle both spellings.
5. **Stronger reviewers with no severity bar.** Better models find more issues. Without a bar for what blocks a release, finding more just means more rounds.

## Test suite assessment

- **Real:** the final build-156 hosted runs executed 1,350 Mac tests and 1,284 iOS tests, with 9 and 5 intentional skips, plus 20 passing iPhone UI journeys. The two hosted bundles share sources, so these are not distinct-test totals. Claude's source inventory counted 1,392 test declarations and about 5,400 assertions; that is a different measure. The suites exercise real logic, but we have not established that every assertion is meaningful.
- **Weaker than their names:** "there is a test for X" doesn't always mean X is protected. Reviews found tests that wire callbacks by hand instead of running the real path, and earlier folder tests that called a helper instead of the sync engine. The final folder regressions do go through the real engine.
  - Example: `testIdleHardwareTimeoutExplainsFailureAndBlocksStartBeforeGrant` (`MinitiTests/MeetingJourneyTests.swift:66`) wires `onHardwareFailure` by hand. Its "no grant" check, `XCTAssertNil(state.managedSessionJournal.active)`, looks like it would pass even without the gate, because nothing in that fixture would request a grant. This came from the build 155 audio review and hasn't been confirmed by breaking the gate and rerunning.
- **Copy tests:** about 80 tests are named after copy, labels or text. Names alone don't show their value. Some protect accessibility, recovery instructions or required choices, and those stay. Tests that only mirror incidental wording break whenever copy changes and should go.
- **Gaps by type.** None of these past incidents was caught before shipping, and they fall into two groups:
  - Testable as contracts without hardware: the device ID case mismatch, Deepgram returning 200 then 402, a Polar env value with a stray newline, and the timeout and recovery policy for the audio hang (a fake hardware call that never returns).
  - Need signed-install or physical testing: the codesign history wipe, keychain error -34018, the Migration Assistant Secure Enclave key, the silent first-recording tap, the dead mic after switching output, and the hang's real driver cause.
  - The first group is a test-design gap we can close cheaply. The second needs scheduled signed and physical QA.
- Nobody has audited all 1,392 test declarations one by one.

## Things we may still be missing

- Launch-time work on the main thread with large histories. Two full scans were found this release, so there are probably more.
- The other `device:` key reads in the backend.
- SwiftData store migrations from 3.5, 3.6 and 3.7 data.
- Behaviour on a clean macOS user account with a signed build, including the keychain.

## What we change for 3.9.0

### The short version

1. Plan names at most two risky areas. Scope freezes at approval; additions come with a swap and a revised QA cost.
2. Write the states and rules ("billed once", "no field lost with an older client", "one bad row never blocks the rest") before code, and review them once.
3. Every review and test run names the exact source it covers. Review each package as a diff, then one integrated pass.
4. Every finding says Blocker, Follow-up or Question, with trigger, harm and confidence. Only blockers hold the release.
5. Close each review batch in writing: fixed, deferred, disputed, unverified.
6. Freeze the patch set before the final full suites, then package once.
7. Start signed-upgrade, Sparkle, browser and physical audio checks as soon as a stable package exists, not at the end.
8. Agents hand findings to each other directly. Ian gets one QA list, then only the checks a new build changed.
9. Add the missing test types: real old-version stores, mixed-version sync, rule-based random tests, fault injection, and recovery tests that check healthy items still progress.
10. One checklist and one blocker register. No release status in AGENTS.md.

These rules replace hard review and build counts with a bounded workflow. One new blocker can legitimately require another package. What matters is that every review and every test run names the exact source it covered. A clean Git tree is one way to get that, but not required when other authorized work is in progress.

## Astra's perspective

The hardest work was preserving one operation across several owners. Recording admission crosses enrollment, billing, audio capture and UI state. A Watch import crosses paid provider responses, checkpoints, cancellation, account changes and delivery. Folder sync crosses old clients, server retention, local baselines, restore choices and Markdown export. A locally correct helper did not prove that the whole sequence was correct.

I made that worse in places. My first folder-recovery fix protected unknown remote membership but stopped the entire sync pass when one row was unreadable. The test asserted that no requests occurred during backoff, so it reinforced the wrong global behavior. The rule should have required both safe retention and continued work for healthy rows. The later real-engine tests cover both. I also missed the separate cloud callback that could export a folder-only change. Fixing the completion fingerprint did not protect every export entry point.

I started broad validation while the last build-156 refinements were still in progress. The runs passed, but did not represent the final source. I then interrupted the intermediate UI run, froze source and repeated the final suites. That was honest evidence handling, but avoidable work. A stable patch batch before full validation would have saved time. Repeated compilation, simulator runs, signing, notarization and Apple processing made each premature package expensive.

The reviews were valuable. Billing settlement, stuck recording starts, unsafe identity replacement, mixed-version folder loss, consumed OAuth credentials and Watch receipt ownership were worth investigating and fixing. Folder-only export rewrites were also real, even though the separate callback made the defect less obvious. I would not ship those merely because they arrived in a later round.

The noise was the lack of separation between confirmed defects, hypotheses and acceptable tradeoffs. A shorter account-lock lease would have weakened correctness. Moving proof before migration preflight would not prove ownership of the queried legacy identity. Some copy and internal cleanup could have waited. A Low label did not always mean low consequence, and a severe-sounding hypothesis was not automatically a release blocker.

Claude's source locations, triggers and suggested regression cases helped. Repeated whole-tree reviews made closure harder because a fresh review could reopen the entire candidate without distinguishing new regressions from inherited risks. I needed an explicit blocking decision and confidence level alongside severity. I also needed to challenge findings before implementing, rather than treating a list of small fixes as a small change overall. These are shared process failures, not a reason to ask Claude to look less carefully.

The codebase slowed us through distributed state and hidden side effects, not just file length. The same tests compile for two Apple hosts, and neither proves signed keychain or physical audio behavior. Five repositories carry related contracts and documentation. Updating all of them was sometimes necessary; copying readiness prose among them was not. No unit-test count should have been used as shorthand for release confidence.

Ian's additions were legitimate product requests. My responsibility was to make their cost visible and propose a new boundary when the original candidate changed. I should have said that a feature addition reopened implementation and validation, rather than continuing to describe successive passes as final. Likewise, local automated completion and a private package were never equivalent to public release readiness.

For 3.9.0 I want one agreed scope, one blocker queue, early product decisions, reviewable package diffs and explicit ownership of the physical checks. Reviewers should verify the changed boundaries after each fix, followed by one integrated pass on stable scope. We should maintain the handoff ourselves so Ian spends time on product judgment and useful testing, not moving messages between agents. If a late blocker appears, fix it and explain the changed gate plainly. Do not restart every unrelated review by default.

These corrections use the [development evidence](3.8.0-evidence.md) and [current checklist](3.8.0.md). They do not constitute another code review or a new validation run.

## Decisions

- Publication: Ian approved committing this retrospective publicly, alongside the 3.8.0 release records it links to.
- Canary users: Ian has identified the outside testers. External distribution still needs his explicit go-ahead for each build.
- Foundation work: undecided. Ian floated folding it into 3.8.0. Claude and Astra recommend against that:
  - 3.8.0 is at build 156 with physical, upgrade and rollout gates still open.
  - Refactoring recording admission, sync retention or device lookups now would invalidate most of that evidence and repeat the scope problem this retrospective describes.
  - Recommended instead: ship 3.8.0 as it is once its gates pass, then make the bounded foundation packages the first work of the next release.
  - One read-only exception fits 3.8.0: audit the backend's 36 hand-built `device:` key reads before the 3.8.0 backend deploy. Fix only confirmed live case bugs, and do it as a targeted backend change with its own tests.
  - Audit result, 2026-11-06 (Claude, read-only): no change needed before 3.8.0.
    - Most sites are consistent. They use the spelling the app sends, read stores filled with that same spelling, or already read both spellings.
    - One deployed guard doesn't work: the attach check that refuses two subscriptions on one rail in one account reads lowercase records, so it never fires for Apple app devices.
    - A spelling-only fix is unsafe: devices sharing one Apple ID or one restored Polar licence would start being refused. The real fix compares subscription identity as well as both spellings, so it's a follow-up, not a 3.8.0 change.
    - Revoke and attach also leave small lowercase `device:` hashes. They are only cosmetic, but they inflate the admin device count.
