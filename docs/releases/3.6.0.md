## Device and receiver QA

Use test accounts and a controlled webhook receiver. Preserve identifiers/timing needed to compare outcomes, without recording customer content or secrets. Record actual build/platform, expected and observed behavior for every line. A successful helper test does not replace device checks.

- [ ] Mac: record, stop and remain on the finished screen. Without opening Settings or pressing Sync, verify the actual remote meeting and later AI revision, then its count/status.
- [ ] iPhone: repeat stop/stay, background/foreground and reconnect. Explain suspension limits honestly; no claim of continuous background execution.
- [ ] Two devices: one meeting created, edited, made Local and restored to Cloud. Compare remote contents and authoritative account-wide count with each device's pending state. No duplicate count on an edit.
- [ ] Return Home and start another recording while the first final AI is held. The first completion webhook contains settled saved data; second meeting is unaffected.
- [ ] AI failure, disabled AI and interruption produce accurate processing metadata. A valid AI run lasting more than five minutes still commits; there is no new global cutoff. Cloud off and permitted private-mode exports still deliver without waiting for cloud.
- [ ] History Update followed by trim/undo/template change or deletion: old AI never returns as current, including exported Markdown and webhook JSON.
- [ ] Hold webhook v1, create newer data, then accept/fail v1. Observe the successor and stable retry IDs at the receiver. Lost responses never produce a false exactly-once claim.
- [ ] Force terminal webhook failure; edit the meeting; Resend current meeting sends a new ID with current permitted data. Deleted meeting/removed endpoint/pending AI have useful action states. CRM behavior is unchanged.
- [ ] Offline completion and relaunch recover pending work; forced termination at the staged handoff does not silently lose work or recreate an acknowledged handoff. Expired work offers manual recovery.
- [ ] Switch accounts, resume or delete during held requests. No stale mutation, cloud cursor, delivery completion or UI status crosses authority boundaries.
- [ ] Render Cloud status and delivery controls on Mac, compact iPhone and regular iPad, including accessibility sizes/VoiceOver. Counts, last-known timestamps and disabled reasons remain understandable.

## Rollout and release gates

1. **Backend:** obtain deployment authorization, run backend validation, deploy alert clarity when ready, independently of the app schedule. Only genuinely required additive client contracts must precede their app consumers. Record revision and deployment. Inspect a normal hourly run and last-notified evidence; do not force production email or clear state to manufacture a pass. Preserve existing UptimeRobot coverage and provider checks.
2. **Shared contract/docs:** update current-behavior reference docs, operations, user-facing docs and concise per-platform release notes only to describe built behavior. Add the Linux tracking commit/issue for applicable payload/UX changes. The roadmap remains the sole priority index.
3. **Build metadata:** choose a build greater than the latest uploaded build at release time; do not assume 143 is free. Set 3.6.0 consistently using the release runbook. Confirm the supported upload Xcode version before iOS packaging.
4. **Release candidates:** build signed/notarized Mac and iOS candidates and complete the device checks above against those candidates. If a fix changes tested behavior, rerun affected checks and required suites on the final combined tree.
5. **macOS:** with release authorization, publish the DMG/appcast/site; verify live bytes, signature/notarization and Sparkle update from the shipped version. Record release asset, build, time and checks.
6. **iOS:** with submission authorization, upload and submit. Record upload, review and App Store availability separately. Update `IOS_LATEST_VERSION` only after availability is confirmed. Never change Linux version constants as part of this release.
7. **Observe and close:** verify ordinary sync/diagnostics and hourly alert evidence, distinguish failures from historical reports, and record unresolved checks or explicit waivers. Close each complete plan only with its own implementation/test/deployment evidence; move durable gotchas into reference docs.

Rollback is per component. Preserve notification identities and pending work; do not reset evaluator history and resend old alerts. Preserve completion-marker/outbox data and cloud exclusions. If a downgraded binary would discard new successors or replay handoffs, use a forward patch instead. No rollback may restore trimmed content or remove account fences.
