## Isolated hosted tests (3.7.0 work, 2026-11-03)

Use the schemes' `Testing` configuration (`fastlane mac test`, `fastlane ios test`, or `xcodebuild test -configuration Testing`). Debug and Release are normal app configurations. Hosted test sources intentionally fail compilation without `MINITI_TEST_HOST`. Testing uses `com.miniti.app.testhost` / `com.miniti.mobile.testhost`, separate extension IDs/defaults, process-local credential storage and an in-memory launch store. AppState uses temporary delivery paths and isolated diagnostic preferences. It does not seed real API keys or start Sparkle/Watch launch services. A crash no longer requires restoring the installed app's defaults or credentials.

Ordinary suites skip hardware capture/device switching. An explicit hardware run uses `MINITI_HARDWARE_TESTS=1` as an xcodebuild setting and still needs microphone permission and suitable devices. Most capture-policy tests inject startup callbacks and remain ordinary tests. The native silent-tap rebuild test is hardware-only. These skips do not validate live capture.

`StubURLProtocol.Context` binds scripts/request capture to a session; `ResponseGate` suspends replies for controlled cancellation/order tests. Prefer those gates to time-based race guesses. `scripts/check-coverage-runner.py` proves xcodebuild failures propagate. Canonical synthetic wire fixtures live in `test-contracts/v1`; regenerate Swift only with `scripts/check-test-contracts.py --import-fixtures`. The backend's `scripts/test-wire-exchange.py --apple /path/to/miniti` runs the separate Swift/backend/Swift exchange. Its two I/O cases intentionally skip in ordinary suites and must execute in that lane. See [foundation evidence](../releases/3.7.0.md#local-foundation-evidence) for current counts and limits.

## Running tests

Use the fastlane lanes or explicitly pass `-configuration Testing`. The isolated host uses process-local credentials and its own defaults/container. A Keychain permission dialog is not expected in ordinary tests: investigate an incorrect configuration or a dependency bypassing test injection rather than granting access to the installed account.

Historical pre-isolation note: October Debug-hosted runs could block on a login-Keychain dialog and shared the installed app's defaults. The old Always Allow and in-memory preference-restoration workarounds are superseded by T01. Production `KeychainSlot` still uses its documented login-Keychain fallback on Developer ID macOS; test that contract with `FakeKeychain`, not the personal credential.

GitHub Actions (`.github/workflows/tests.yml`, `macos-26` runners, Xcode 26.6) runs both bundles on every push. The workflow uses `Testing`. Hardware cases require `MINITI_HARDWARE_TESTS=1` and microphone authorization, so ordinary CI skips them; and the notification-category test skips when the host's notification center returns no categories right after registering (the runner's host has no team signature; an ad-hoc signature validates, so the signature itself is no signal); everything else must pass. Until 2026-10-21 the workflow's success check matched any suite line with 0 failures, so a run with 15 failing tests (2026-10-19, 3.2.0) showed green; it now fails on xcodebuild's own exit status and reads the bundle total. The local lanes remain the release gate (`RELEASE.md` step 2), because the runner cannot run the hardware tests and its Swift 6.3.3 compiler crashes now and then in the SendNonSendable pass on `CloudSyncEngine`'s commit closures (three times on 2026-10-21, never with the local Xcode 27.1); the workflow retries xcodebuild once when the log carries `Stack dump`, and nothing else. The image has no Xcode 27, and the frontend flag that used to turn the pass off no longer exists.

Two more runner-only failures showed up on the iOS job (2026-10-19, 10-22 and the 3.4.0 release run on 10-27), both fixed in the 3.5.0 tree on 2026-10-30. First, the simulator host aborted with `SwiftData ... destroyed by calling ModelContext.reset` for a `Meeting` right after `MeetingModelTests`: work a finished test leaves behind (the end-of-meeting naming pass that `stopRecording` does not await, with a save after it) still held a model whose in-memory container the test's tearDown had released, so the bundle reported a partial count with 0 failures and TEST FAILED. Test containers now stay alive for the whole process through `TestSupport.retain(_:)`, which `makeInMemoryContainer` and the suites that build their own container go through. Second, `AccountEmailStateTests` paused a fixed 120 ms in `makeApp` for the account-changed read that `refreshClientAuthStatus` spawns; the runner was still mid-read, so the next scenario's slow read was merely queued and the state stayed loading. `makeApp` now polls until no read is in flight. Do not add fixed sleeps to tests; poll a condition with a cap, as `TestSupport.waitUntil` does.

- Run macOS tests: `fastlane mac test` (or `xcodebuild test -configuration Testing -scheme Miniti -destination 'platform=macOS' -derivedDataPath DerivedDataLocal -only-testing:MinitiTests`)
- Run iOS tests: `fastlane ios test` (or `xcodebuild test -configuration Testing -scheme MinitiMobile -destination 'platform=iOS Simulator,name=iPhone 16' -derivedDataPath DerivedDataLocal -only-testing:MinitiMobileTests`)

Two destination gotchas on the iOS side, both of which surface as "Unable to find a device matching the provided destination specifier": pin `OS=` to the version of the *installed simulator runtime*, not the SDK version (`xcodebuild -showsdks` can report a point release ahead of any runtime you have), and prefer `id=<udid>` over `name=` when several simulators share a name. `xcodebuild -showdestinations -scheme MinitiMobile` lists exactly what resolves. `fastlane ios test` handles both by resolving a UDID itself — see [../fastlane/RUNBOOK.md](../../fastlane/RUNBOOK.md).

## Launch smoke gate

`scripts/screenshots/smoke.sh [ios|mac|all]` builds the Debug apps and runs every screenshot scene (Home, recording in each insights mode, Coaching focus and stats, History, saved meeting, Settings, Account & Plan, the P0.2 recovery screen, the P0.3 banner). A scene passes only if the macOS app opens its window, renders, writes its PNG, and exits 0, or the iOS app reaches first layout and writes `<container>/tmp/miniti-screenshot-ready-<scene>` (a crash behind a blank capture fails). It is the launch/Home/Settings/history-navigation smoke the roadmap asked for, without an XCUITest target; it cannot exercise record → stop (covered at the `AppState` level in `MeetingJourneyTests`) or trackpad gestures (manual). Quit the installed Miniti first on macOS.

## Manual / live testing

- **Manual-only hardware boundaries (P0.6)**: microphone and system-audio capture, Bluetooth route changes, echo suppression between mic and system channels, the live Deepgram WebSocket (connect, reconnect ladder, CloseStream), iOS background audio and the Live Activity, macOS trackpad back/forward gestures, and the floating recording surface. Some downstream paths have automated coverage; this does not establish exhaustive managed API or post-audio journey coverage. See the audit disposition for gaps.

- **Store recovery drill (P0.2)**: with the installed app quit, use a scratch path the sandboxed macOS app can write, `D=~/Library/Containers/com.miniti.app/Data/tmp`, then `head -c 4096 /dev/urandom > $D/bad.store` and launch the Debug build with `-MinitiStoreURL $D/bad.store` (macOS: `open -n DerivedDataLocal/Build/Products/Debug/miniti.app --args -MinitiStoreURL $D/bad.store`; iOS simulator apps are not sandboxed the same way, so `xcrun simctl launch <udid> com.miniti.mobile -MinitiStoreURL /tmp/bad.store` works). A path outside the container such as `/tmp/x.store` makes the app report `category=io` (sandbox denial), which is itself a useful check. Expect the "can't open your meetings" screen with the corruption copy, a working "export diagnostics", "show database folder" (macOS), and "get help"; "try again" must stay on the screen. Then `cmp` the scratch file against a copy taken before launch (it must be identical), relaunch without the flag, and confirm real history is intact. Repeat once with a valid scratch store to see "try again" fall through to the normal app.
- **Persistence banner (P0.3)**: no launch flag forces a save failure in a shipping build; the automated `PersistencePolicyTests` cover the state machine.
