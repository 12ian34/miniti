# Cloud sync and account boundaries

Shipped baseline: 3.0.0 sync/API/MCP, 3.3.0 account switch, 3.4.0 account-email UX and in-flight generation fences. The authoritative backend wire/storage contract is [08-cloud.md](../../../miniti-api/docs/agents/08-cloud.md); [patterns](patterns.md#cloud-sync-300) covers client mechanics.

## Current behavior

Cloud is optional, default off and managed Pro only. Its switch belongs to the account; another device observes changes on its next usage check. Private mode pauses only this device and excludes newly private recordings; deliberately configured exports remain allowed. Email recovery/management is available without Pro/cloud and is distinct from data/API/MCP rollout guards.

`MeetingSyncDocument` carries an additive versioned document; the engine fingerprints finished meetings and preserves unknown fields. Released 3.6.0 separates outgoing upload eligibility from incoming replacement protection as described below; deleted meetings remain excluded from uploads. Pulls commit locally and may auto-export Markdown, but do not enqueue CRM/webhooks. Local deletes persist tombstones; server tombstones win. A 413 marks an oversized meeting skipped until changed. Sync uses millisecond-normalized stamps to avoid repeated revision churn. Old rows/store migrations must retain data.

`CloudSyncEngine.PassContext` captures account and generation. Check after every await before applying responses, statuses, errors or cursors. Cursor writes use the captured account. Reset, account change and credential replacement invalidate outstanding passes; stale work hands over without pausing the new account. Cancellation alone is not the fence.

Account changes clear revisions/fingerprints/tombstones and the old cursor before status refresh. Local meetings stay, and a later pass can upload them to the next account under today’s behavior. This is a remaining provenance problem, not an R3 regression: [meeting ownership](../plans/meeting-ownership.md) adds explicit copy authority. Never infer old ownership from revision counters.

3.5.0 adds Cloud/Local controls in live and saved meeting views plus calendar-title rules. There is no Home checkbox. [Selective cloud privacy](../plans/selective-cloud-privacy.md) retains the delivered contract.

## Operational gotchas

- Redis caches sequence values using Lua; durable meetings, changes, links and tokens live in Postgres. Do not assume a Redis pre-check and a Postgres write form one transaction.
- Tests must not start the app’s real sync engine against its real store or Keychain. Attach an isolated test host without starting it when testing bookkeeping only; use held transports for actual pass races.
- Tombstone retention is 30 days; an older offline device may re-upload. Do not silently purge local history to reconcile it.
- Unknown 409s in old clients become revision-conflict retries, and fixed oldest-first batches can starve newer work. A different error can fail the whole pass. Future ownership enforcement must be gated by tested platform versions.
- Keep per-account imports’ external-source/id deduplication; no global cross-account merge. Voice embeddings never enter cloud documents.
- Generic web/email link consumption has the R8 race; [reliability](../plans/reliability.md) owns it. Device-enrollment bind/consume has different cross-store retry requirements.
- Known defects, found 2026-11-14, not fixed (3.9.0 and backend `196fe8d`). (1) The account switch is not delivered: the backend stores it but reads it back as unset, so a device never follows another device's change and every device with cloud on rewrites "on" after each usage check. Behind it, the switch write is not atomic and a device that disagrees at an already-applied version never heals; both matter once the reader is fixed. "Another device observes changes on its next usage check" above is the design, not today's behavior. (2) After a merged download, the three-way merge treats untouched content as edited locally, because local documents carry null `external_source` and `external_id` and server documents omit them; a folder-only change from another device is then uploaded again, and in two edit sequences older content can replace a newer edit. (3) A sign-in refresh that fails during a pass shows "Sync failed" with the detail "ServiceError". (4) A pass uploads before it downloads, so a device that was away sends uploads that get refused. The [3.10.0 plan](../releases/3.10.0.md#cs1-the-account-cloud-switch-is-read-back-confirmed) owns all four as CS1, SM1 and SE1; its [audit](../releases/3.10.0-planning-audit.md#field-investigation-2026-11-14) holds the evidence.
- Account switch fix, step 1 deployed 2026-11-14 (backend `be6d6e7`): the server reads the stored switch correctly and writes value and version in one step, but tells devices only when `ACCOUNT_CLOUD_READBACK=on`. The flag is on in production since 2026-11-15 (backend `0333d19` records it), so defect (1) above is closed for devices that read the switch. Every version sent is the stored one plus 1,000,000, so once readback is on each device compares itself with the stored value once. Review follow-up, deployed with the work on backend `main` before the flag was turned on: the offset starts at activation and must never drop afterwards, so the flag gains a third value, `paused`, which stops sending the switch and keeps the offset. Once the flag has been `on` it is never unset, and going from `paused` back to `on` raises `ACCOUNT_CLOUD_READBACK_GENERATION` by one. The same work lets a device number its switch writes so one that timed out and lands late is refused (`409 stale_intent`).
- Account switch writes in the app (3.10.0 CS1.4, released on Mac 2026-11-16, iOS in App Review): a device's choice is marked pending at once, with the account and credential it was made under. `AccountCloudSwitchWriter` sends writes one at a time in the order the choices were made and keeps only the latest waiting one, so the server cannot apply an older choice after a newer one; a write whose account or credential has changed is dropped before it is signed (`setAccountCloud(enabled:accountID:credentialGeneration:)`). A usage answer for a previous account is ignored whole: neither its plan, its switch nor a "disabled" answer is applied.
- Sync failure wording (3.10.0 SE1, released on Mac 2026-11-16, iOS in App Review): a failure while signing a cloud request in keeps its cause. `MinitiAPIService.send(_:preservingSignInCause:)` gives cloud calls a `SignInFailure`; every other caller still gets `ServiceError.serverError`. Not reaching the server becomes the offline pause; a device key that is locked for now and a server fault during refresh (`CloudSyncError.signInDelayed`) pause the same way ("Waiting for a connection") and retry on the next poll. A rate limit uses the rate-limited line. A key that can never sign again shows "This Mac can no longer sign in. Open Settings, Account to sign in again." Everything else, including server-coded failures, shows "Could not sync. Trying again." Type names and internal codes go to the debug log and the diagnostic timeline only.
- Mixed versions and the no-change upload count (3.10.0 SM1.4, released on Mac 2026-11-16, iOS in App Review): a 3.8.0 or 3.9.0 device still re-uploads a meeting after a folder-only change from another device and can still replace an edit; its code is unchanged. A 3.10.0 device only downloads that echo, so one folder change costs at most two uploads with one device of each version, and a 3.10.0 device keeps its own newer edit when the echo lands first. If the older device replaces a newer 3.10.0 edit with its stale content, the 3.10.0 device takes that copy, because it cannot tell it from a real edit, sends nothing in answer, and both ends then stay the same. The tests stand in for the older device by sending what it was observed to send; a run with a real 3.9.0 build is still owed. No server-side change covers older devices: serving the two external keys as explicit nulls was measured on the real 3.9.0 engine and rejected on 2026-11-15, because changing the served form loses an edit waiting to upload on a 3.8.0 or 3.9.0 device ([scripts/sync-fill-eval](../../scripts/sync-fill-eval/README.md)). `CloudSyncEngine.unchangedUploadCount` counts accepted uploads whose content and folder both equalled the last agreed copy: the stored baselines, written by this device's last accepted upload or its last merge. An upload that leaves the folder fields out (a device-only folder, where the server keeps its shared folder) counts as changing no folder. First uploads and restores are not counted. An accepted upload is counted even when its pass is superseded before the answer returns. Each pass that has any writes a warning to the debug log and `unchanged_uploads` to the diagnostic timeline. In the tested sequences between two 3.10.0 devices it stays 0; three legitimate actions do count: hiding a meeting in a device-only folder, editing only the part of a title past the server's 500-unit limit, and undoing an edit whose upload is already queued. A count above 0 is something to look at, not proof of a sync loop. It observes only and never changes what is uploaded. Help reports carry the timeline, and the backend refuses a report with a field it does not know, so the backend had to accept `unchanged_uploads` before a 3.10.0 client ships; it does on `main` (checked 2026-11-15). Ian accepted the older-device limit above for the changeover period on 2026-11-15. A conflict retry inside a pass is skipped once cloud has been switched off, so nothing uploads after the switch (final review, `120b3f93`).

## Intentional limits and future choices

Foreground polling is the current delivery mechanism; APNs, web History, API write scopes and server-side Coaching are not built. They are candidates in the roadmap, not unfinished core sync. Linux parity has its own implementation status. Live connector and copied-old-store checks must have actual evidence, not inferred passes.

Original schema/design, cost snapshot, nuanced delivery notes and regression matrix are retained in [the archived cloud record](../archive/cloud-sync-plan.md). Costs and open questions there are dated; revalidate before making capacity decisions.

## 3.6.0 implementation

Released on macOS on 2026-10-31 and iOS on 2026-11-01. The release record owns submission and device-waiver evidence.

In 3.4.0 and 3.5.0, automatic passes can refresh the successful-pass timestamp while leaving cached server count/bytes stale, and a stopped `currentMeeting` remains excluded until the session clears. The released 3.6.0 S1/S2 implementation separates three things:

- **Outbound eligibility:** `cloudUploadProtectedMeetingID` protects starting, recording, resuming and final transcript commit. Once the stopped transcript is durable, that meeting may upload while still selected and while final AI runs. Later durable AI updates dirty it again. A failed stop save retains protection and exposes persistence retry.
- **Inbound authority:** `cloudProtectsIncoming` still protects the selected meeting and every meeting with final AI running from pulled documents/deletes and conflict replacements. The engine remembers genuinely newer incoming rows skipped by protection; release coalesces their reconciliation. A protected local row missing from the manifest also retains a release-time recheck. Credential/account invalidation requests a manifest under the replacement authority before clearing old deferred IDs. Echoes of its own accepted uploads and lifecycle notifications with no skipped rows do not trigger extra manifests. This is intentionally stricter than outbound eligibility.
- **Status freshness:** successful pass time and successful count-fetch time are separate. Content changes mark status dirty; explicit refresh, missing/dirty status or a five-minute age trigger a read. A failed count read preserves accepted uploads and the previous count with a stale indication. An unsaved model edit discovered after a pull, manifest or batch await aborts that pass with “Waiting for local edits to save”; it preserves the prior completed-check time and cursor, emits no success, and retries after a durable save or poll. A held response invalidated by an already-committed edit likewise preserves the completed-check time and immediately reruns; a failed rerun cannot leave a false successful check behind. Pending uploads/removals, protected meetings, local-scan failure and oversized rows also prevent a misleading all-clear label. Pending captions omit zero-count operations.

An expired change-feed cursor gets one immediate manifest recovery per sync invocation. If the recovered cursor also expires, the engine retains reconciliation for the next poll or explicit action and shows an unfinished check; it does not chain automatic retry runs.

Completion-marker-only commits do not dirty cloud content or schedule scans. Real transcript/AI commits still do.

Settings says Last checked for the last completed pass and Cloud count checked for the count; neither is proof that a particular meeting uploaded. Webhook delivery remains independent of cloud acknowledgment and contains the transcript and available summary itself. [The 3.6.0 plan](../plans/sync-and-delivery-reliability.md) owns acceptance; [release evidence](../releases/3.6.0.md) owns test/device gates. These changes do not alter account ownership, privacy choices, tombstone authority or the backend sync schema.

Local QA correction, 2026-10-31: the save debounce clears its task handle before starting a sync pass. Later saves schedule another pass without cancelling an active upload. URLSession cancellation (`-999`) remains cancellation, leaves work pending for retry and does not publish a failed or successful check. A cancelled count read also preserves its prior freshness timestamp. Cloud-copy removal text distinguishes automatic retry from settings/account gates that need action; it never turns cloud on or changes privacy choices.

Handoff review correction, 2026-10-31: the local-only webhook marker stores a temporary destination fingerprint, removed after release, rather than the URL. Held deliveries also expire after 24 hours and no longer block updates to the current destination. None of this changes cloud fields or makes delivery depend on sync. Marker-only cleanup still avoids cloud-content notifications. The handoff and rollback details remain in [patterns](patterns.md#saved-ai-and-webhook-delivery-local-360-not-released).

3.8.0 local folder extension: [backend contract](../../../miniti-api/docs/agents/08-cloud.md#folder-catalogs-380-local-not-deployed) adds an independent account catalog with revision CAS and durable tombstones, before app rollout. Existing meeting schema stays v1 with optional `folder_id`/`folder_manual`; unknown-field echo preserves old clients. Local/private-derived folder content stays off the wire. Catalog sync shares all existing mode, account, private-mode, Pro and cloud gates, with owner/credential checks around each await. Failed sync preserves local edits and exposes Retry in Folders. Disabling filing/cloud keeps local folders; deleting the cloud copy removes the remote catalog too.

3.8.0 second review: optional folder fingerprint material is omitted for untouched legacy/default and device-only membership, preserving pre-folder fingerprints exactly. Explicit manual Unfiled remains meaningful shared metadata. Identical folder catalog polls do not rewrite disk or publish UI changes. Account purge tolerates a missing folder table, and deletion propagates purge errors before revoking the account so the user can retry. Migration 002 still precedes folder rollout.


Review follow-up (2026-11-05): Folder fields cached in pre-3.8 sync extras are promoted on model-context setup. Folder-only edit baselines preserve unseen remote content during conflict resolution. Overflow folder additions remain recoverable conflicts rather than invalid uploads.


3.8.0 fourth-review contract (local, 2026-11-05): folder extra-field promotion rebases only matching clean fingerprints, never content dates or pre-existing dirty edits. Promotion consumes its own legacy keys and is safe to revisit per store. Folder-only dirty edits preserve remote content in push conflicts, change-feed pull and manifest reconciliation, including beyond the 200-upload batch. Overflow resolution retains IDs unless recreating an actual tombstone. Backend account-lock contention is retryable 503, never the meeting 409 conflict shape interpreted by 3.7 clients. See the [release disposition](../releases/3.8.0-evidence.md#fourth-review-corrections-2026-11-05) for evidence and mixed-binary limits.


3.8.0 account contention is HTTP 503 `busy` with `Retry-After`. The client treats it as transient, retries at most twice per sync run with a 1–30 second bounded delay, and then retains dirty work for the normal poll without a Sync failed banner or failure diagnostic. A 409 remains a document conflict. The [fifth review](../releases/3.8.0-evidence.md#fifth-review-corrections-2026-11-05) records tests; installed 3.7 clients retain their next-pass retry behavior.


3.8.0 sixth-review contract (local, 2026-11-06): clean sync checkpoints now retain separate content and folder baselines. Push conflicts, feed pull and manifest reconciliation merge these components independently; a remote folder move and local notes edit survive in either order. Timestamps resolve only concurrent edits to the same component. Baselines track the actual uploaded snapshot, including when the user edits during an upload. Account resets clear both baselines. Existing clean rows are seeded without inventing a base for already-dirty legacy rows. A folder-edit marker is not authority without an actual dirty fingerprint; Undo cannot preserve a stale assignment. Folder catalog busy/CAS responses reread and merge with two bounded retries, then wait quietly for the next pass. Cross-account folder migration and tombstone compaction remain separate work, as recorded in the release disposition.


3.8.0 seventh-review mixed-version protection: known pre-3.8 Apple meeting PUTs have echoed folder fields omitted before the atomic store update, preserving server membership when an old client wins a content conflict. Current Apple clients retain intentional folder assignment/clearing. Linux's separate version line and unknown-version clients are unchanged. This backend compatibility change must deploy before the app rollout.

## Legacy folder refresh on upgrade (3.8.0 local)

Promoting pre-3.8 folder extras does not prove that cached membership is current. Previously synced rows enter `pending_folder_refresh`; reconciliation fetches the current server document even at the same revision before ordinary uploads. Separate content baselines preserve local notes while taking remote membership. A dirty legacy content baseline remains unverified rather than being marked clean. Local-only, never-synced rows need no remote refresh. Explicit Put on Cloud restore retains its existing authority and can upload the chosen local copy; successful writes clear the refresh marker. Regression coverage uses the actual engine with same-revision stale membership and subsequent local edits.

This refresh includes every previously synced row without a folder baseline, even when an old client never cached folder extras. Pending folder refresh has a separate status count and is not classified as oversized. A listed but missing/unreadable batch document holds only that meeting’s upload. Other meetings continue to upload and download. Settings names affected meetings; each row retries after five minutes, stopping after three failures per engine lifetime. Foregrounding does not reset that limit; Sync now explicitly retries. Successful refresh clears the row’s retry state. Folder/baseline-only merges refresh UI without invoking Markdown exports, and Put on Cloud still resolves unknown remote folder membership before uploading the chosen content.


### Cloud exclusion undo, local 3.8.0 correction (2026-11-07)

Put on Cloud cancels any queued cloud-removal tombstone in the same persistence commit as restoring upload eligibility. The engine also discards stale removal records when the meeting still exists locally and is no longer excluded. A true local delete retains its normal tombstone semantics. This fixes the inherited offline/debounce race where a restored upload could be followed by a stale delete. Folder reconciliation uses a predicate/one-row local lookup instead of fetching all history for each ID. The release record owns regression and 1,000-meeting fixture evidence; backend contracts are unchanged.
