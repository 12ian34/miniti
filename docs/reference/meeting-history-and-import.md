# Meeting search, imports and saved results

Current baseline, reconciled through released 3.6.0. [Patterns](patterns.md) owns persistence; [cloud](cloud-sync.md) owns sync deduplication. Large-history optimization is a [separate plan](../plans/history-and-session-performance.md).

## Search

Shared query grammar supports AND words, quoted phrases, person/title/date/range and field operators; unknown operators stay plain text. Use local-calendar date boundaries. Search projections/cache are keyed by meeting and transcript revision. Optional calendar event title is populated for new records, not invented for old ones. Preserve ranking/snippets/pins/grouping while optimizing. Semantic search, saved searches and Spotlight are not implied. [Shipped search design](../archive/meeting-search-plan.md) retains detailed grammar; its “today” paragraph describes the old implementation. The weeks-old meeting manual check has no recorded completion.

3.9.0 local correction: applying a custom date range inserts both after:/before: tokens in one query update. Existing date filters are replaced once while words, phrases, people and devices remain. Single-date presets still replace the previous date selection. Both platform controls use the same batch insertion contract.

## Granola

3.4.0 accepts the current emailed ZIP or CSVs, column aliases and duplicate protection. Unlabelled exports do not contain speaker identities or word timings: keep one S1 and sentence turns, estimate duration at 150 words/minute and say it is estimated. Never infer speakers by alternating lines. Preserve summary cleanup and explicit external-source/id keys.

ZIP supports stored/deflate entries, not encrypted/ZIP64; unsupported archives should ask the user to unzip. A real 33-meeting export was parsed in the standalone harness; sandbox-host file access can hang on permission UI, so this is not equivalent to a full import interaction test. Mac/iPhone picker, repeat-import and cloud duplicate checks remain evidence tasks. Linux parity is separate. [Import record](../archive/granola-import-plan.md).

## Saved results and exports

User edits, transcript trims, deleted meetings and template changes must retain current data. R7’s late History result fences shipped in [3.6.0 sync/delivery](../plans/sync-and-delivery-reliability.md): request, transcript, account and template authority reject stale results without clearing newer work. Custom templates persist a per-meeting definition snapshot so editing/deleting a template does not break old exports. Cloud pulls do not trigger CRM/webhook sends. R5/R6 also shipped in 3.6.0: released webhook bodies have immutable delivery IDs, and terminal failures can resend current saved data with a new ID. Device/receiver waivers remain in the release record.

## Folders (3.8.0 local candidate)

History on Mac/iOS has All meetings, Unfiled and flat editable folders. Each meeting has one optional primary assignment; a manual move stays authoritative until explicit regrouping. Folder names, descriptions and title rules participate in bounded local matching after final AI settlement. No new AI request, transcription upload or model consent is involved. Automatic filing and creation are separate switches. Creation suggests broad purposes from repeated title evidence, not a folder per repeated title. Since 3.9.0 meetings learn from their series. A folder chosen by hand for an earlier meeting in the same calendar series, or with the same title once dates and numbers are removed, wins over every other rule, so hand moves teach later meetings. Then come custom folder rules and evidence, then the folder other meetings in the same calendar series were filed into automatically, which also keeps a meeting there on later passes. Title series learn only from hand moves, and generic titles such as Weekly sync, Demo or Interview form no series. Last come broad title keywords and strong summary evidence: three or more different terms of one broad category, with singular and plural counted once and two clear of any other category. Summary evidence only files into a broad folder that already exists, never creates one. Preview groups proposed moves by folder, with counts, descriptions and expandable meeting titles. Existing custom folders, manual moves and renamed identities remain authoritative. Existing history changes only through an explicit preview/apply, at most 1,000 recent finished rows; Undo reverses the latest move/batch in the current session. Folder deletion retains meetings and resolves memberships to Unfiled.

`MeetingFolderStore` owns an atomic, account-scoped catalog file and three-way sync; optional SwiftData membership columns preserve legacy stores through additive migration. Shared catalogs sync independently of meetings so empty user-created folders can travel. Local/private-derived folders and their membership never upload. Same-folder conflicts preserve the local proposal for an explicit choice. Tombstones cannot be silently resurrected. The [folder plan](../plans/folders-and-meeting-completion.md) owns bounds, compatibility and rollout.


Mac 3.8.0 local export setup: the optional Markdown folder and AGENTS index can also be configured during first-use/Home setup. App history remains in its local database. Bookmark/path replacement is atomic from the user's perspective. AGENTS updates replace only the `miniti:meetings` comment block, appending it to existing unmarked content and preserving outside text; malformed markers stop the index write. This does not enable cloud sync, change private-mode export permission or backfill history automatically.

Second review, 2026-11-05: automatic Markdown eligibility is snapshotted at Stop; enabling it later never backfills completed history on launch. Explicit bulk export remains available. Filename collision lookup is bounded to one same-minute meeting. The exact old miniti-generated AGENTS header/list migrates into the maintained block, preserving appended human notes; arbitrary instructions remain untouched. Folder batches precompute custom match tokens; a broad-folder rename retains title-based purpose matching unless its rule/description is explicitly customised.


3.10.0 folder matching and Preview (FO2, local, not released). Broad folders have one-word names: Team, Customers, Product, Hiring, Investors, Partners, Intros, Learning and Planning (`FolderMatcher.Category`; raw values and folder IDs are unchanged from 3.9.0). An automatic folder still carrying its untouched 3.9.0 name ("Product & engineering", "Partners & suppliers", "Business planning") is renamed once by `MeetingFolderStore.renameLegacyDefaults`; each folder is checked once, so any name chosen afterwards is kept. Evidence for a broad folder, strongest first: a hand-filed meeting in the same series, a custom folder's rule or words, an automatic series folder, a title phrase, strong summary vocabulary (three terms of one category, two clear of any other), then who was there. Participant evidence uses calendar attendee and speaker email domains on the device only: everyone else on the user's own company domain is Team, any other company domain is Customers, and webmail domains never count as a company. A meeting is read against the address it names for the user; otherwise the usual domain is the verified account email's plus the one the calendar most often marks as the user's. Summary evidence outranks who was there: with a broad folder for the summary's category the meeting files there; without one, a summary that disagrees with the participants leaves the meeting unfiled, and the participants are not used as a fallback. Investor and board titles keep filing into an existing Planning folder until an Investors folder exists. Automatic filing of a new meeting never creates a folder from summary words; Preview may propose one when two meetings agree, still behind Apply.

Preview (`MeetingFolderManager`) shows "N meetings will be filed, M stay unfiled", one disclosure per proposed folder, and a Still unfiled section with a folder menu per meeting (existing folders, folders proposed in this Preview, "New folder…"), 200 rows at a time. A choice is captured when made and applies with Apply as hand-filed (`FolderProposal.manual`), so later meetings in the same series follow it. `applyFolderPreview` reuses a live folder of the same name, and returns what was refused (changed since, folder limit, save failure), which stays on screen. Undo restores every moved meeting; folders created by Apply remain. The 1,000-meeting Preview test takes about 0.5 s in a debug build (0.82 s on 3.9.0 rules).

AI folder suggestions (3.10.0 FO2.4, local, not released; the backend mode is deployed since 2026-11-15, `07916e4`). For meetings the rules leave unfiled, miniti can ask for a suggestion from the title and the summary it already holds, never the transcript. Nothing is sent unless the person asks (Ian, 2026-11-15). In Preview that is the button "Suggest folders with AI", with a line under it saying how many meetings' titles and summaries it sends; opening Preview sends nothing. For newly completed meetings it is the setting "Use AI to file new meetings" (`folderAISuggestions`, off by default), under More options on the organise screen and in Settings, Privacy. `AppState.folderSuggestionBlock` says why a request the person asks for may not be sent: private mode is on (Preview then says so and shows no button; the toggle shows as off with the reason and keeps the person's own choice), AI processing is not allowed, or there is no provider. `automaticFolderSuggestionBlock` adds the setting, for the automatic request only. `folderSuggestionItems` is the only place that decides what may be sent: finished, unfiled, not hand-filed, with a summary, and never a meeting with `syncExcluded` set. One request per 100 meetings (`FolderSuggestions` in `MeetingFolders.swift`): managed mode posts `mode: "folders"` to `/api/insights`; BYOK sends the backend's two prompts, copied verbatim and pinned by a test, with the person's own key. An answer can only name a folder that was sent or one of the nine categories, once per meeting; everything else is dropped. In Preview the answers join the proposals marked "Suggested by AI" and still need Apply; each meeting is asked about once per Preview, and a failed or refused request leaves the rules' proposals untouched. A suggested category with no folder yet becomes a new folder only through Preview and Apply. Automatic filing of a newly completed meeting asks at most once per meeting, only when the rules found nothing, and only among folders that exist. It never runs on upgrade.

3.8.0 folder navigation: History → Folders opens three journeys: Organise existing meetings (preview then Apply), Create a folder, and Manage your folders (select one to edit or delete). Automation stays on the overview. Matching rules and device-only creation are optional editor controls. Home offers the same manager through an optional setup task.
