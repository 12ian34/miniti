# Audio flow

3.8.0 local Mac candidate: failure of an enabled local diarizer during cloud transcription requests one provider-diarization transition through the existing reconnect owner (three attempts, 45 seconds). An in-flight handshake is allowed to settle before replacement. Connection alone is unconfirmed; actual provider speaker IDs confirm recovery. Silence causes no second restoration. Stop fences late results. This does not switch a local transcription recording to a cloud provider or recover missing audio. See [3.8.0 evidence](../releases/3.8.0-evidence.md#local-implementation-evidence).

Signal path, mixing, diarization, recovery. For the cross-file audio patterns (watchdog, save queues around recording) see [patterns.md](patterns.md).

## macOS audio flow (mic + system)

1. `AudioCaptureService.startCapture(microphone:systemAudio:)` starts AVAudioEngine (mic) and/or Core Audio process tap + AVAudioEngine (system)
2. Mic audio: converted to 16kHz mono PCM16 via AVAudioConverter, level via `vDSP_measqv`
3. System audio: `AudioHardwareCreateProcessTap` → `CATapDescription(stereoGlobalTapButExcludeProcesses: [])` → aggregate device → IO proc callback → direct vDSP conversion (mono downmix via `vDSP_vadd` + decimation via stride + `vDSP_vsmul`/`vDSP_vclip`/`vDSP_vfix16`) into reusable scratch buffers → 16kHz mono PCM16. The aggregate device's IO format is read from `kAudioDevicePropertyStreamFormat` (input scope) to handle cases where it differs from the tap format. RMS is computed directly from PCM16 without a float-array conversion.
4. **Process Tap setup**: Creates a `CATapDescription` (global stereo, captures all processes), then an aggregate device with the tap as a sub-tap. The aggregate's main sub-device provides the clock — always the built-in output device (shares the same hardware oscillator as the system mixer, guaranteeing zero drift). The default output device is never used as the clock because external/Bluetooth devices can run at different sample rates (e.g. AirPods HFP at 24kHz vs tap at 48kHz), causing drift compensation to fail and the tap to deliver silent buffers. Falls back to default output only if no built-in device exists. IO proc callback runs on a custom DispatchQueue (not RT thread). Cleanup: stop IO proc → destroy aggregate device → destroy process tap.
5. **Stereo interleave (mic+system)**: When both sources are active, system audio PCM16 goes into a pre-allocated Int16 ring buffer (8000 samples, ~500ms at 16kHz, NSLock-protected). The mic callback drains the ring and **interleaves** stereo PCM16 directly into owned `Data` for Deepgram multichannel — ch0 = mic, ch1 = system (remote speakers). System underruns are padded with silence so the channel layout stays stable for the whole socket. Since the 2026-10-27 capture fix, if the mic has never delivered PCM or has delivered none for 500 ms, the system callback drives that same stereo stream with silence on ch0. Callback delivery and source-clock updates are serialized; the mic takes over again when it delivers PCM, and old ring contents are discarded rather than replayed. System-tap restarts derive channel layout from the session's requested sources, never from whether the mic happens to be active. No mix and no dual AGC on this path. Single-source capture still sends mono (`channels=1`).
6. **Deepgram multichannel attribution**: Dual-source sessions connect with `channels=2&multichannel=true`. Streaming results include `channel_index` (`[0,2]` mic / `[1,2]` system), which is retained on both transcript updates and finalized speaker segments, and every response carries an explicit `TranscriptSource` (`microphone`/`system`/`unknown`). Per-channel diarization is preserved on **both** channels: `SpeakerIdentityState` maps Deepgram's channel-local, socket-local speaker numbers to collision-free app IDs — system speakers keep low IDs (provider-identity on the first socket, fresh sequential IDs after reconnects), microphone speakers occupy `1000 + n` by first-seen ordinal (`1000` reserved for the first mic speaker and all legacy meetings; single-mic continuity keeps `1000` across reconnects). The mic channel is **no longer flattened** to one speaker; mic segments are still subject to the playback-echo reconciliation below. **Billing note**: Deepgram bills each multichannel stream independently (~2× minutes vs mono mix).
7. **Mic playback-echo reconciliation and final ordering (macOS dual source)**: System playback can be captured cleanly on ch1 and acoustically leak through speakers into ch0. Treating every ch0 transcription as "You" creates the alternating false-self transcript shown by YouTube/talk-radio playback. `AppState` accepts system finals and clearly mic-dominant finals immediately into a bounded 350ms ordering buffer, while holding only ambiguous mic finals as the system channel catches up. A mic final is suppressed only when its word sequence closely matches a time-overlapping system final; source energy relaxes the text threshold for imperfect ASR variants but never suppresses unrelated overlapping speech. One- or two-word matches additionally require system dominance to protect genuine interjections. If the system channel finalizes past an unmatched mic segment, that genuine local speech is released immediately; otherwise a four-second fallback prevents it from being stranded when the system channel is silent or delayed. Committed finals use Deepgram's precise word start time plus a per-WebSocket meeting offset; reconnect offsets use the wall-clock recording duration because the one-second UI timer is too coarse. The 350ms buffer sorts ordinary nearby channel callbacks before display, and a genuinely later release is inserted at its chronological position. Equal channel timestamps receive an invisible microsecond tie-break so save/reload order is deterministic without a SwiftData migration. System-dominant mic interims are hidden so playback does not flash green as "You" before reconciliation. The source-energy log is reset on every new connection/reconnect, pending genuine mic text and the ordering buffer are flushed before a reconnect or stop, and suppressed echoes never enter `liveSegments`, saves, speaker naming, Coaching, or insights.
8. **Diarization stabilization (both platforms)**: Final speaker segmentation now uses stricter switch confirmation (minimum run length + duration — `minWordsForSpeakerChange=4`, `minDurationForSpeakerChange=0.85s`), applies `speaker_confidence` gating for uncertain boundaries, and uses a new-speaker promotion stage so brand-new speaker IDs only appear after sustained evidence. Interim updates are also gated so unconfirmed speaker guesses don't immediately pollute speaker lists. **Known tradeoff**: the switch thresholds deliberately drop short interjections ("yeah", "right", "wait what?" — 1-2 words, ~0.3s) because loosening them re-introduces the v1.12.4-era false-new-speaker flipping at every turn boundary. If this is ever revisited, the safest direction is confidence-gated relaxation: allow 1-word switches only when `averageSpeakerConfidence >= ~0.85` AND the target speaker is already in `confirmedSpeakerIDs` — never for brand-new IDs.
9. `onAudioBuffer` callback → DeepgramService (nil during monitoring)
10. Levels flow independently: AudioCaptureService → Combine → AppState → SwiftUI views (coalesced to one atomic snapshot at ~20Hz; waveforms at 16Hz while active and 8Hz while quiet, with animation disabled for Reduce Motion)
11. Deepgram JSON decode + speaker segmentation run off-main in strict receive order. Only the processed transcript/state delta is applied on the main actor, and reconnect generations discard stale results from an older socket.
12. **Level display**: `SourceWaveform` uses `pow(level, 0.2)` power curve (not linear) so quiet mic signals (~0.003 RMS) show visible bar movement.

## macOS hardware lifecycle isolation (3.8.0 candidate)

`AudioCaptureService` retains published state on the main actor. Its serial `AudioHardwareExecutor` owns engine creation, format/device queries, start/stop, process-tap setup/destruction and device-listener registration. UI and DSP logs do not query HAL. Input-list refresh is coalesced, with a follow-up pass for changes received during a query. A 15-second deadline begins when each operation starts executing, excluding queue wait. Timeout fails all waiting capture requests and quarantines the worker until relaunch; this cannot cancel a blocked operating-system call. The message asks the user to quit and reopen miniti, including when an idle query times out, and explains that macOS may show capture until quit. Cleanup stays queued, and no new capture work may race the stalled worker.

Mic route events settle for one second. Missing input/rate/channels do not create an engine; existing bounded retries can recover when a valid input returns. Events during an in-flight mic restart request one later settled check instead of cancelling that start. Source delivery gates close before asynchronous teardown, wait only for the current DSP buffer, and reject late audio and queued recovery callbacks. Capture generations prevent delayed permission/start results from reviving a stopped recording. Gates must never contain HAL or engine lifecycle calls.

On hardware timeout, AppState stops through normal finalization, keeps received transcript, freezes/enqueues the managed usage checkpoint, and presents a restart instruction. Stop does not wait for engine teardown. A timed-out worker stays unavailable even if its OS call eventually returns. This protects UI responsiveness for this failure path; it is not a general app watchdog or a guarantee against every system hang. Tests simulate stalled hardware and route races. Physical AirPods/profile changes, permission prompts and sleep/wake still need device QA. See the [incident follow-up](../releases/3.8.0-evidence.md#audio-route-hang-follow-up-2026-11-06).

## iOS audio flow (mic-only)

1. `AVAudioSession` configured with `.playAndRecord` category, `.defaultToSpeaker` + `.allowBluetoothA2DP` + Bluetooth call-profile option (implemented with `.allowBluetooth` for toolchain compatibility)
2. `AVAudioEngine` with input node tap → AVAudioConverter → 16kHz mono PCM16 (same format as macOS mic path)
3. `onAudioBuffer` callback → DeepgramService
4. No system audio, no mixing, no ring buffer, no source dominance tracking (all stubs)
5. iOS is always the mono microphone path — every response carries `TranscriptSource.microphone` and speakers map into the mic app-ID range (`1000 + n`). A solo recording therefore shows "You"; multi-speaker recordings show neutral per-speaker labels until naming or manual marking resolves identity. (The legacy energy-based `sourceLookup` rewrite has been removed entirely.)

### iOS mic recovery

Three notifications drive recovery, all registered in `startMicrophoneCapture` and torn down in `stopMicrophoneCapture`:

- `AVAudioEngineConfigurationChange` — hardware/codec change, restarts the tap. **An AVAudioEngine stops itself on every configuration change and does not restart** (verified 2026-10-02: an input-only engine posts the notification and `isRunning` flips to false when only the default *output* device changes, with the input device and format untouched). `handleEngineConfigurationChange` therefore restarts when the input changed **or** `audioEngine.isRunning == false` (`shouldRestartMicAfterConfigChange`); before 2.10.0 it compared only the input device/format and logged "skipping mic restart", which left the mic dead until stop/resume. In mic + system mode the mic tap drives the interleave, so a dead mic engine means *no* audio reaches Deepgram while `isCapturing`/`isMicActive`/`isRecording` all stay true and the transcript health check sees no audio activity (so it never reconnects). Call apps switch the output device/profile at call start and end, which is exactly when an "End & start next" / "Join next" handoff is recording — the 2026-10-02 field report.
- `AVAudioSession.routeChangeNotification` — restarts when the input identity changes, and also when the mic is currently inactive (a dead mic still needs recovering, so this path must not gate on `isMicActive`).
- `AVAudioSession.interruptionNotification` — a phone call, FaceTime, Siri, or an alarm suspends the engine and nothing restarts it for us. `.began` marks the mic inactive, `.ended` restarts it regardless of the `shouldResume` hint (that hint is advisory, and a recorder that never comes back is worse than one that retries).

All three funnel through `scheduleMicRestart` (250ms debounce, 0.5s minimum spacing) → `restartMicrophone`. On failure, `scheduleMicRestartRetry` retries with the same bounded backoff as macOS (0.5s → 1.5s → 3s, max 3). `isCapturing` is the "mic is expected" gate — on iOS it is only true once mic capture has started, so it can be used where macOS uses `expectsMicAudio`. Never latch recovery off by leaving `isMicActive == false` behind a guard that also requires `isMicActive`: that combination is what previously killed the mic for the rest of a meeting after one failed restart.

## System Audio permission (macOS only)

- Uses `AudioHardwareCreateProcessTap` (Core Audio, macOS 14.2+) instead of ScreenCaptureKit. This lands the app in **"System Audio Recording Only"** permission category (like Granola) rather than "Screen Recording".
- ScreenCaptureKit was previously used but **always** triggers Screen Recording permission — even with `.audio`-only output — because `SCShareableContent.excludingDesktopWindows()` itself requires screen recording TCC access.
- Info.plist key: `NSAudioCaptureUsageDescription` (not `NSScreenCaptureUsageDescription`)
- No public API to check audio capture permission status; the system prompts on first use of `AudioHardwareCreateProcessTap`
- Minimum macOS bumped from 14.0 to 14.2 for process tap API availability

## System tap recovery state machine (macOS, v1.24.1)

Three failure modes are handled. All paths preserve `expectsMicAudio` / `expectsSystemAudio` and the active mix mode; all bounded by cooldown + attempt count so we can't loop.

- **Silent-stall** (callbacks arriving but RMS≈0): detected when `(now - lastSystemNonSilentAt) > 8s` AND `sysNonSilentCallbacks >= 40` AND `(now - lastSystemAutoRestartAt) > 30s`. Tightened from 18s threshold in v1.23.1 so the transcript gap on Bluetooth connect is ~half. Rebuilds the process tap + aggregate device + ring buffer.
- **Callback-stall** (no callbacks at all): a capture-scoped main-actor task checks every 2s, allowing 8s startup grace or requiring more than 10 prior callbacks, then triggers after a callback gap exceeds 6s. It runs whenever system audio was requested, including system-only capture where there is no mic callback to host the check. `shouldRecoverSystemCallbackStall(...)` also enforces the shared 45s restart cooldown and suppresses decisions during route-change/full-restart/retry work. The watchdog is cancelled by both synchronous and async stop paths and re-armed whenever the process tap is rebuilt.
- **Mic liveness watchdog (v2.10.0)**: `startMicLivenessWatchdogIfNeeded` ticks every 2 s while capture expects the mic. `shouldRecoverMicStall(expectsMicAudio:isMicActive:isRecoveryInProgress:bufferGap:timeSinceLastRecovery:)` fires when no mic buffer has arrived for more than `micStallGap` (6 s) and no restart is already running, with a 15 s cooldown; recovery rebuilds the mic engine in place (`Mic engine silent for Ns … — restarting mic tap`, `Mic stall recovery complete`) and falls back to `scheduleMicRestartRetry` on failure. Belt and braces for the configuration-change rule above and for any other way the engine can stop silently. Regression tests: `MeetingHandoffTests` (real-HAL output switch during a recording, plus the two pure rules).
- **Microphone selection (v2.10.0)**: `AudioCaptureService.preferredInputDeviceUID` (fed from `AppState.preferredInputDeviceUID`, `@AppStorage("preferredInputDeviceUID")`, empty = system default) is applied to `inputNode.audioUnit` with `kAudioOutputUnitProperty_CurrentDevice` before the engine reads its format in `startMicrophoneCapture`. `resolveInputDevice(preferredUID:devices:systemDefault:)` is the pure resolver: a preferred UID that is present wins, an absent one falls back to the system default with `isUsingFallbackInputDevice = true` and a log line. `availableInputDevices()` enumerates input-capable devices and skips aggregate and virtual transports (the app's own system-audio tap is an aggregate). The device-list listener refreshes `inputDevices` and re-runs the resolver; a changed selection, or the preferred device appearing after a fallback, restarts the mic through `handleEngineConfigurationChange`, which now compares the engine's device against the resolved device rather than the system default. Home mic pill (`MicrophoneSourcePill`) and Settings → Recording (`MicrophoneDevicePicker`) both bind to the same preference. Motivation: macOS moves the default input to AirPods on connect, which swapped a desk mic for the HFP AirPods mic during a demo (2026-09-28).
- **Default output change** (AirPods connect, etc.): `handleDefaultOutputDeviceChange` schedules a debounced restart (300ms settle delay). Runs AudioObject property listeners on the default input/output devices + the whole device list (v1.24.1 added the device-list listener to catch Bluetooth connects that don't flip the default).
- **Post-recovery health check (v1.24.1)**: after any of the three recoveries complete, `beginPostRecoveryHealthCheck(reason:)` arms 3 heartbeats (~30s) of observation. Each heartbeat computes `(deltaNonSilent / deltaCallbacks)` since the baseline. If 2 out of 3 heartbeats show the tap is "alive but silent" (callbacks firing, no audio), `escalateFullCaptureRestart` tears down both mic + system and calls `startCapture` again — matching what user-triggered stop/continue does. 60s cooldown on full restarts prevents loops.
- **Retry on failed rebuild**: up to 4 attempts with exponential backoff, except for explicit permission-denied errors (no retry).
- **Silent-from-birth tap (2.12.2)**: a tap created while macOS is still showing the system-audio permission prompt fires callbacks but never carries audio, even after Allow; only a fresh tap does. That is the first recording of every new install, and the silent-stall detector cannot see it because it requires prior signal. `shouldRebuildSilentFromBirthSystemTap(...)` fires from the same 2 s silence check when the tap has 60+ callbacks and zero non-silent ones for more than 10 s, at most twice per capture, 30 s apart, and rebuilds through `recoverSystemTapAfterSilentStall(isSilentFromBirthRebuild: true)`, which skips the post-recovery health check so ordinary silence (nothing playing) is not escalated to a full capture restart, and abandons the rebuild if a non-silent callback arrived while it was queued so a call that starts at that moment loses nothing. Log line: `System tap has never carried audio (silent Ns since start, callbacks=N, rebuild 1/2)`. Rule tests in `MeetingHandoffTests`.

Debug log lines to look for when diagnosing:

- `Default OUTPUT device changed → <Name> (..., bluetooth)` — device transport type printed since v1.24.1
- `Audio device list changed — output=..., input=...` — v1.24.1 added device-list listener
- `Engine config changed with mic input unchanged, but the engine stopped — restarting mic tap` / `Mic engine silent for Ns (isRunning=false, buffers=N) — restarting mic tap` / `Mic stall recovery complete` — v2.10.0 dead-mic recovery
- `Mic input device set to preferred: <Name> (id:N, transport=usb)` / `Preferred microphone not available (uid=...); using the system default` / `Microphone selection changed — restarting mic tap` — v2.10.0 microphone selection
- `System tap appears stalled (silent Ns after prior signal, output=...)` — stall detection fired
- `System tap appears callback-stalled (Ns without callbacks)` — the recording-scoped watchdog detected that the IO proc stopped firing
- `System tap recovery starting after Ns near-silence` / `System tap recovery complete`
- `Post-recovery health check armed (reason=..., output=...)` — confirms v1.24.1 guard is armed
- `Post-recovery health: deltaCb=N, deltaNonSilent=M, degraded=true/false`
- `Post-recovery health: degraded 2/2 heartbeats — escalating to full capture restart`
- `Full capture restart complete` / `Full capture restart FAILED: <err>`

## Initial microphone failure, 2026-10-27 (shipped in 3.4.0)

**Release status, 2026-10-27:** delivered in macOS 3.4.0 build 141 (`28d247b`). The legacy anchor is retained; [release QA](../releases/3.4.0.md) records the actual device evidence and unchecked scenarios.

A macOS 3.3.0 field report showed AirPods Max input startup failing with Core Audio `-10868` (unsupported format), while system capture remained active and Deepgram connected but sent zero packets. Production diagnostics matched the report at 12:58–13:03 UK time. The original dual-source ring waited forever for the absent mic callback; the active-mic watchdog did not cover a failed initial start.

The fix keeps the socket's channel layout stable and allows system PCM through independently (see stereo interleave above). A failed initial mic start tears down the failed engine and uses the existing three retries at 0.5, 1.5 and 3 seconds. Permission denial does not retry. Stop cancels the pending retry. The selected input is not silently changed. The recording shows a microphone-specific warning with the built-in-mic recovery step; retry exhaustion keeps that warning. System-only capture remains mono, ending-grace suspension drops fallback output, and mic recovery cannot replay previously sent system samples.

`AppState.updateAudioRecoveryState` now requires converted buffers from every requested source within two seconds before considering capture healthy. Silent PCM counts as healthy; an active engine or socket alone does not. A microphone failure is degraded, a missing-buffer startup uses the internal recovering state, then degraded after 12 seconds. The presentation distinguishes normal startup from repair. The transcript watchdog leaves zero-flow failures to capture recovery rather than reconnecting Deepgram repeatedly. `microphone_capture_failed` is an error diagnostic; `audio_recovery_healthy` is emitted only when the delayed UI transition actually commits.

Regression coverage: `CaptureFailureTests` exercises the actual PCM delivery and injected hardware startup boundaries, including initial failure, retry success/exhaustion, permission refusal, stop during retry, channel preservation, recovery, silence and suspension. `MeetingHandoffTests` checks the AppState recovery status and real capture handoffs/output switching. No backend contract change.

Validation on 2026-10-27: 99 targeted tests passed (capture, recording handoffs and all 84 auth tests, including the two `051fe88` completion regressions). Full macOS bundle: 1,037 tests, three skipped, zero failures. Full iOS bundle: 976 tests, three skipped, zero failures.

Device QA still required before release: on a Mac with AirPods Max, select its microphone and start with mic + system audio while a call app also uses the headset; switch output between Mac speakers and AirPods. Confirm remote speech continues if the mic fails, the warning names the microphone, and recovery restores own speech on ch0 without doubling remote speech. Select the built-in mic and verify both sides transcribe. Repeat system-only, mic-only, stop during recovery, and ending grace. An injected format error proves the fallback contract, not that every Bluetooth driver refusal can be repaired automatically.

## On-device speaker separation (v2.10.0)

Off by default (Settings → Transcription, Speakers: This Mac; "Separate speakers on this device" until 2.12.0). When on and the model is loaded, `AppState.makeAudioBufferHandler` feeds every PCM16 packet to `OnDeviceDiarizationService.ingest` before `DeepgramService.sendAudio`. Dual capture is de-interleaved (channel 0 mic, channel 1 system) into one Nemotron-3 streaming diarizer per source; iOS runs the mic one only. The diarizer's 10 ms speaker-activity frames land in an `OnDeviceSpeakerTimeline`; the Deepgram socket is opened without `diarize_model`, and the off-main transcript parse takes each word's speaker from the timeline over the word's timestamps (majority dominant speaker, confidence = agreement after the 50% coverage gate). A word's confidence is the share of its diarized frames that agree with the chosen speaker; a word less than half covered (the diarizer runs about 1.3 s behind live audio) borrows the last active speaker at confidence 0.3, below the segmentation switch gate, so a borrowed label can continue a turn but never start one. A speaker slot must have 3 s of dominant speech before any word can switch to it (`slotMaturitySeconds`); short-lived slots are Nemotron churn on changing acoustics and never surface. Additional mic speakers from the on-device timeline are promoted under the standard policy even when the meeting looks remote: the strict clone guard exists for Deepgram's per-socket diarizer churn, which Nemotron's stable, voice-based slots do not have (found in the first live test on 2026-09-26, when the guard kept a second in-room person on "You"). Each final logs a content-free `On-device speakers` line: slot histogram, borrowed words, horizon.

Reconnects inside a meeting keep the same diarization session and timeline; `markSocketStart()` re-pins socket time 0 at the start of the first packet of the new socket (the packet is ingested first, then the mark is taken, and the origin subtracts that packet), and words the diarizer has not reached continue the last diarized word of the same response rather than the timeline's last-heard speaker, and `SpeakerIdentityState` treats on-device sources as stable across generations. `stopRecording` ends the session after capture stops; the timeline stays alive for parses still in flight.

The model ships inside the app (`Miniti/Resources/NemotronDiarizer`, filled by `scripts/fetch-nemotron-model.sh` as the first build phase, pinned revision, SHA-256 verified); a HuggingFace download into the app container is only the backup for a bundle built without that folder. Fallbacks, all of which keep Deepgram diarization on the socket: not Apple silicon, setting off, model failed to load, or the session could not start. In released 3.7.0, an inference or lag failure mid-session invalidates the timeline and voice evidence, and later words use Unknown speaker with a visible unavailable state. That released baseline has no mid-session provider-speaker restoration. The local 3.8.0 Mac transition is described at the top of this reference; iOS behavior is unchanged. Lag preserves ready models; actual load/inference errors require retry. See the [failure contract](../plans/local-speakers-default.md#local-failure-handling-implementation-2026-11-03).

Cost: Deepgram bills streaming diarization at $0.0020 per channel-minute (measured 2026-09-25); on-device sessions do not carry it. Evidence and the eval harness: [../scripts/diarization-poc/RESULTS.md](../../scripts/diarization-poc/RESULTS.md); current contract: [local models](local-models.md); [original implementation record](../archive/on-device-diarization-plan.md).

## On-device transcription (v2.12.0, macOS)

Off by default (Settings → Transcription, Transcription: This Mac; Privacy → Private mode forces it). When on and the model family for the meeting language is loaded, `AppState.startRecording` decides once (`sessionTranscribesOnDevice`) and `connectTranscription` opens the local engine instead of the Deepgram socket: `OnDeviceTranscriptionService.beginSession` builds one `StreamingNemotronMultilingualAsrManager` per capture source from the shared Core ML weights (NVIDIA Nemotron 3.5 ASR Streaming Multilingual 0.6B, int8, 1120 ms chunks, personal dictionary and calendar keyterms as vocabulary biasing) and `DeepgramService.connectLocal` activates it. The same `makeAudioBufferHandler` callback runs: the diarizer ingests first, then `sendAudio`, which now hands the PCM16 to the session (`splitPCM16` de-interleaves dual capture) because there is no socket task. Each worker drains a stream of samples through its manager, reads the new token timings after every chunk, and a `LocalUtteranceAssembler` groups them into words (SentencePiece `▁` marker) and utterances: a final on sentence punctuation, on 1 s of silence measured at the decoded horizon (not the fed audio, so a word split across chunks is never cut), or at 12 s; otherwise an interim. `makeLocalResponse` shapes each event like a Deepgram message (channel 0 mic, 1 system) and `processTranscriptResponse` runs the usual speaker mapping, so on-device speaker separation labels local words exactly as it labels Deepgram words; without it every local word is provider speaker 0 for its source ("You" on the mic, one remote speaker on the system channel). Timings are session-relative seconds like socket timestamps, so `deepgramTimelineOffset`, `markSocketStart`, and chronological insertion are unchanged.

Session end since 3.7.0: `gracefulDisconnect` allows up to 30 seconds for the workers to finish (manager tail decode and assembler flush), followed by the 0.8-second receive window, then disconnects. The [lifecycle reference](recording-lifecycle.md) records the measured basis and separate speaker-settlement bound. A transcript stall goes through the same watchdog as Deepgram and restarts a local session with identities preserved; a local engine that cannot restart leaves transcription stopped with a visible message and never opens a socket. Managed mode requests no Deepgram `/api/session` for a local meeting. Local 3.7.0 reports enrolled managed capture duration separately through `/api/recording-usage`, including private recordings; it does not reduce the Deepgram allowance. BYOK needs no Deepgram key and sends no recording-usage reports. A start with the setting on, the language supported, and the model neither loaded nor on disk is refused with a message (a model on disk that is still loading is awaited for up to 30 s) unless "If the model is not ready, use Deepgram for that meeting" is on; cloud-only languages (Greek, Polish, Swedish) keep Deepgram and the setting says so.

Private mode (Settings → Privacy, 2.12.0) forces both pickers to This Mac and switches every cloud AI feature off (`AppState.setPrivateMode`), so a private meeting opens no transcription socket and requests no cloud meeting insights. Configured integrations, account/version checks and local 3.7.0 managed duration reporting remain separate; the pickers under Transcription show as set by private mode until it is off.

Models: downloaded on demand through FluidAudio's Hugging Face client into Application Support/FluidAudio/Models/nemotron-multilingual inside the sandbox container (about 590 MB for the `latin` family, 640 MB for `multilingual`), never bundled; the Settings row shows progress and a remove button. Not pinned to a revision yet; see the plan's status table. Evidence for the engine choice and the language tiers: [local-transcription-research.md](../research/local-transcription-research.md), `scripts/transcription-poc/RESULTS.md`.

## Known limitations

- **Echo reconciliation is intentionally conservative**: long near-verbatim playback duplicates are removed; short matches need system-dominant energy, and unrelated simultaneous local speech is preserved. Very distorted leakage whose mic and system transcripts no longer share enough words may still appear as "You". This avoids destructive acoustic cancellation and keeps genuine interruptions.
- **Dual-source final settling delay**: macOS mic+system finals may remain in the ordering buffer for up to 350ms. Interim text is still immediate, single-source macOS and iOS do not use this buffer, and ambiguous mic speech may already wait up to four seconds for echo reconciliation. The short final delay keeps the common path append-only; unusually late genuine mic speech can still appear in the middle of finalized text, where the macOS renderer applies a localized paragraph mutation rather than replacing the document.
- **Multi-speaker diarization on both channels**: within each channel, Deepgram's native diarization assigns separate per-channel IDs and the identity allocator keeps them distinct app speakers (system → low IDs, mic → `1000 + n`). The system channel is never automatically mapped to "You". The primary mic identity (`1000`) is implicitly "You" only while it is the sole mic speaker; once a second mic speaker is confirmed, everyone gets neutral labels until automatic naming or manual rename / `mark as you` resolves identity.
- **Short interjections sometimes lost or misattributed**: a side effect of the strict diarization gating above. Single-word backchannels ("yeah", "right", "mm-hmm") fall under the switch threshold and get absorbed into the previous speaker's segment. This is a deliberate tradeoff, not a bug — see the confidence-gated relaxation note in the Diarization stabilization pattern for the safe path forward if we ever revisit.
- **Nova-3 under-transcribes filler words**: `filler_words=true` is set, but Nova-3 still drops most hesitations — measured across ~46k words of real transcript history, hesitation markers land around 3 per 1000 words against an expected 15–25, and "uh" outnumbers "um" roughly 5:1 where the two should be comparable. Deepgram acknowledges this as model "shyness" (Nova-2 marginally better, Flux much better). Coaching filler counts are therefore a floor, not a true count. **Flux is not a viable swap**: `/v2/listen` has no `diarize`, `diarize_model`, `multichannel`, `channels`, or `language` parameter, and its `TurnInfo` words carry only `word`/`confidence`/`start`/`end` — no `speaker`. It is mono, English-or-multi only, and Deepgram explicitly directs meeting transcription back to Nova-3. The only Flux-shaped option would be a mic-only sidecar connection used purely as a filler counter, at the cost of a second socket and double mic-stream billing.
- **English filler list must track Deepgram's vocabulary**: Deepgram emits `uh`, `um`, `mhmm`, `mm-mm`, `uh-uh`, `uh-huh`, `nuh-uh` and nothing else in that family — notably never `hmm`, `hm`, or `er`, which sat in our defaults for months matching zero occurrences. Note that `countPhraseOccurrences` runs each phrase independently, so overlapping entries double-count: "uh huh" is currently scored as both `uh` and `uh huh`. Adding more hyphenated `uh`-containing variants would compound this — fix the overlap first.
- **Deepgram features enabled but not consumed**: we pass `vad_events=true` and `utterance_end_ms=1000` in the query string but ignore the resulting `SpeechStarted` and `UtteranceEnd` frames (both are in the `ignoredTypes` list in `parseTranscriptResponse`). `speech_final` *is* consumed — we promote `speech_final || is_final` to a final transcript for segmentation. `UtteranceEnd` remains unused as a ~1s-latency fallback for when endpointing doesn't trigger.
- **Deepgram live query params (current)**: `model=nova-3`, `smart_format=true` (implies punctuation — do not also send `punctuate`), `filler_words=true`, `diarize_model=latest` (streaming currently resolves to v1; preferred over deprecated `diarize=true`), `interim_results=true`, `utterance_end_ms=1000`, `vad_events=true`, `endpointing=300`, `encoding=linear16`, `sample_rate=16000`, `channels=1` (or `channels=2&multichannel=true` for macOS mic+system), plus `keyterm` list (system + personal dictionary + session calendar terms, capped at 100).
- **KeepAlive**: while the WebSocket is connected, `DeepgramService` sends `{"type":"KeepAlive"}` every 5s. Deepgram closes idle sockets after ~10–12s with no client messages; KeepAlive is unbilled and protects mic/system restart gaps (e.g. Bluetooth A2DP↔HFP flip). Harmless while audio is also flowing.
- **Multichannel billing**: dual-source macOS sessions roughly double Deepgram minutes vs the old mono mix. Single-source (mic-only / system-only / iOS) stays mono.
