## Problem and evidence

The [3.7.0 publication record](../releases/3.7.0.md#publication-2026-11-04) reports a 74-minute managed meeting metered at about five seconds after a late reconnect. This undercounts usage; it does not establish transcript loss or authorize back-charging historical meetings.

Read-only source check on 2026-11-04:

- `AppState.refreshManagedDeepgramCredential` calls `/api/session`; `applyManagedSession` replaces both `currentSessionId` and the meeting's stored session reference.
- Stop computes active duration but reports against that last session. `/api/session/end` caps the report at elapsed time since that session's `startedAt`.
- `/api/session` creates a new record with a four-hour TTL on every grant. `/api/session/end` has a four-hour duration cap and accepts missing session records. It checks a replay key before incrementing usage and writes the key afterward. Sequential replay protection alone does not prove concurrent exactly-once charging.

## Outcome and exclusions

Renewing a short-lived Deepgram credential must preserve all reportable active time in the same recording and its original owner while it remains authorized. Stop, interruption recovery and retries must charge each interval once. Keep pause semantics, elapsed-time bounds, quotas, model routes and BYOK behavior. Ian approved extending accurate accounting beyond four hours for 3.8.0. Leave prerecorded Watch duration based on recognized audio, not grant age.

Exclude retrospective usage corrections, pricing changes, account-ownership migration, a universal recording ledger, local transcription accounting redesign and audio buffering/replay. The existing local-duration queue remains separately owned by the [usage plan](on-device-usage-tracking.md).

## 3.8.0 decisions

Ian confirmed on 2026-11-04 that 3.8.0 must also account for recordings beyond four hours without stopping the recording. Use one stable version-2 accounting session per continuous recording, independently of provider-token renewal. Remove the four-hour *total* charge cap only for this explicit new contract; bound accepted duration by server-observed elapsed time and client active capture time. Existing legacy request semantics and prerecorded Watch semantics remain compatible. No allowance or price change follows.

## Version-2 wire contract

Proposed field names below are the implementation contract, to be captured in Apple/backend/Linux fixtures before source changes. Extra response fields are additive.

| Operation | Request | Response / rule |
|---|---|---|
| Start | Existing `/api/session` body plus `accounting_version: 2` and `recording_id` (random UUID, never a meeting title/content ID) | Existing token/session fields plus `accounting_version: 2` and `session_started_at` (UTC). Deduplicate starts by enrolled owner + recording UUID. A lost response must not create another billed session or recording count. |
| Renew | `/api/session` with `accounting_version: 2`, `renew_session_id`, same `recording_id` | Fresh provider token, same accounting session ID/start. Never increment session count, reset duration, silently create a replacement session or reopen a finalized one. |
| Finish | Existing `/api/session/end` plus `accounting_version: 2`, `session_id`, `recording_id`, `duration_ms` (finite nonnegative safe integer) | Existing response keys plus `accepted_duration_ms`. Exactly one accepted duration and replay receipt. Reject ambiguous v2 bodies also supplying `duration_minutes`. |
| Legacy | No accounting version | Existing start/end request and response behavior, including existing duration cap. Preserve prerecorded Watch audio-duration handling. Atomic replay protection must still cover concurrent legacy finalization where compatible. |

Reject unknown accounting versions rather than interpreting them as legacy. The client must require the echoed version before using v2 finish fields. A complete valid old-backend grant selects legacy before capture; it never establishes v2 support. Roll out backend support first to obtain full-duration accounting. Keep pending legacy reports explicitly tagged by their legacy format, rather than upgrading them by guesswork. Do not adopt an old meeting's last grant into a new v2 session.

Implementation decision, 2026-11-04: Ian authorized the reviewed package including a positive, whole-recording legacy fallback. A complete valid legacy grant may select legacy before capture. `MANAGED_ACCOUNTING_V2=off` selects legacy only when the atomic start finds no v2 root; existing roots continue accepting renewals/finalization. Review correction, 2026-11-05: an ambiguous uncaptured start retains its recording UUID and may accept a complete successful legacy response on retry. The server retains any existing v2 root; a persisted client journal never downgrades. Authentication, quota, malformed responses and transport failures are errors, never fallback signals. The accounting version remains immutable in the durable journal. Optional diagnostics record only the fixed version 1 or 2. Legacy coverage retains reconnect undercounting and the four-hour cap; v2 counts the full active recording.

### Identity, storage and retention

Persist version, recording UUID, original enrolled account/device, exact selected existing usage-storage key, original start time and active/finalized state. Compare device identities case-insensitively, but preserve the existing hash spelling: auth IDs are lowercase while Apple usage keys can be uppercase. Do not create a lowercase shadow counter or merge existing twins as part of this work; B0 remains separate. Renewal/finalization must check the current installation owner and active state in the same Redis operation that changes session state/counters. Apply the same authorization fence before returning a replay receipt containing usage totals. Capture the existing monthly usage-period identifier for compare-and-retry protection against period reset. Enrollment proof remains required; a random session ID is not authorization.

Keep active records and start-dedup records for 35 days after start/latest authorized renewal, and final receipts for 35 days after finalization. Client pending reports expire after 30 days; the five-day margin permits bounded retries without duplicate charging. Use a bounded queue, at most 200 pending end reports per installation; count expired/capacity drops and expose incomplete coverage in admin diagnostics without content. Do not evict an active recording or silently claim all usage was delivered. No heartbeat loop is required just for accounting; credential renewal refreshes retention. A missing/expired v2 session is terminal and never falls through to the permissive legacy missing-session path.

Error contracts: malformed/unsupported v2 input is 400; a live owner mismatch is 409 `report_owner_mismatch`; expired/unknown v2 record is 410 `accounting_session_expired`; a renewal after finalization is 409 `accounting_session_finalized`; disabled/revoked installation follows existing 403/401 semantics. A duplicate finish with the same owner/recording/duration returns its receipt; a different final duration is 409 `finalization_conflict`, with no additional charge. Request throttling remains 429 with Retry-After. Provider/transport failures remain retryable within the existing recovery policy. Never log credentials, recording content or personal device names.

MT1 inventories every new session, start-dedup, receipt and lookup/index key with its TTL and removal hook. Device removal or account deletion first invalidates authorization, then deletes that owner's new v2 sessions, start-dedup records, receipts and lookup/index entries, with retryable cleanup if interrupted. No new v2 tombstone retention exception is required: a missing v2 session is already terminal, and only an authorized start can create one. Preserve existing aggregate/historical usage retention rather than rewriting that policy. Use bounded owner indexes or known keys for removal, never a global key scan. A removed account/device cannot retrieve an old receipt or recreate deleted usage through a late finish. Test removal racing with renew/end, interrupted cleanup and eventual expiry. Update the privacy retention description to match the final inventory.

### Duration and charging

Client active duration uses a monotonic recording clock, excludes paused intervals and remains stable across token renewals. Persist the active-duration checkpoint with existing interrupted-recording bookkeeping at most once per 15 seconds while capturing, plus pause/Stop, without introducing an idle file-write loop. Hard-exit recovery reports only confirmed persisted active time, with its possible checkpoint tail loss recorded; it must not count downtime after the process dies. This is bounded accounting persistence, not the later transcript-checkpoint project.

Coalesce and serialize disk work off the capture/main-thread hot path. Preserve write ordering across pause, Stop and the next recording so a delayed checkpoint cannot overwrite finalized state. The [planning audit](../releases/3.8.0-planning-audit.md#performance-and-resource-acceptance) owns measured capture/Stop, idle-write, queue and Redis comparisons; structural bounds alone are not measured performance evidence.

At finalization accept `min(client_duration_ms, max(0, server_now - original_start))`, with no four-hour ceiling on v2. Zero stays zero, including cancel-before-capture and a fully paused interval. This is a deliberate v2 behavior correction: the current legacy route replaces a zero report with elapsed server time for an existing live session. Negative input is already rejected before that fallback. Preserve that zero-to-elapsed fallback on the legacy live path for compatibility in 3.8.0, including its four-hour cap; change it only through a separately scoped legacy migration. Existing prerecorded Watch and missing-session zero reports retain their current zero behavior. V2 never falls back to elapsed time just because captured duration is zero. Convert milliseconds to minutes once for legacy counters. Test totals within one millisecond before float conversion; UI rounding is not the accounting assertion. A six-hour continuous recording must accept 360 minutes, and six wall-clock hours with one paused hour must accept 300. Delayed upload does not increase the frozen active duration.

Charge current device cycle/lifetime, global lifetime, daily total, daily device and daily platform counters once, using the current `incrementUsage` counter inventory. Preserve existing report-day attribution and billing-period behavior; cross-day splitting and a new account ledger are excluded. Monthly reset and account-switch races need an expected-period/owner check in the atomic operation, not an earlier read alone. Refresh account totals after charging; an aggregate display response is a snapshot, not a reservation across all devices.

The reset side must participate too. Current `getOrCreateDevice`, `linkDeviceToSubscription` and `linkDeviceToAppleSubscription` can write zero from stale reads after a concurrent new-period charge. MT2 coordinates these applicable reset writers through the same expected-period/counter contract, with reset once per actual period transition. Preserve Polar/Apple precedence and existing docs-lookup reset rules. Delayed duplicate or older billing notifications must not reset a newer period or overwrite its increment. Test controlled interleavings of passive reset, both subscription writers and legacy/v2 finalization in real isolated Redis. This bounded correction is required for charging integrity; it does not implement B0/B2 ownership migration.

One Redis script/transaction owns counter changes, active-to-finalized transition and the replay receipt. Validate all key types/numbers and expiry/owner conditions before writes: Redis Lua errors do not roll back earlier writes. Do not use a short-lived lock around the existing multi-call `incrementUsage` implementation as a substitute. Tests inject failed requests before commit and lost replies after commit. Renewal has a final authorization/state check after provider token issuance; a concurrent Stop wins without reopening the session. At most one usable result is applied by the client; unused issued grants do not create accounting entries.

### Account transitions and compatibility limits

Freeze end reports to their original owner; flush while that owner is still authorized. Signing out must remain possible offline. After sign-out, retain pending reports without using another identity; if the same owner returns before expiry, retry. After an explicit move to a different account, drop/quarantine old-owner reports as unreportable and count that coverage gap. Never charge the new owner or resurrect revoked authorization. Existing device-level historical ownership movement is outside this release's account-ownership scope; this plan cannot promise correct retroactive attribution across that migration.

Legacy queue migration preserves the old wire format. If an old entry has no trustworthy ownership evidence, quarantine/drop it as incomplete coverage rather than assigning the current account by guesswork. Test old queue decoding, known/unknown owners, both usage-key spellings without a new shadow hash, and replay after detach/revoke/account removal. Add old Apple/Linux response-decoding fixtures for additive fields. A valid legacy grant is accepted only before an active journal/capture has selected v2; an uncaptured failed request alone cannot permanently prevent legacy negotiation. Invalid or ambiguous acknowledgement fails before capture. Never send a legacy zero-duration finish for failed capture, since that can bill elapsed time.

The client persists recording/account/session identity before applying a renewed grant, fences callbacks by recording generation, and stops renewal on Stop/account changes. A new recording must never inherit a prior root session. An ordinary network reconnect uses the same v2 root. Resume after an interrupted recording reports the old frozen interval once and follows the existing explicit resume semantics for a new accounting interval; do not include process downtime.
