## Implementation contract

### B0: one device record per device (miniti-api first, clients after)

**Today:** two `device:` records per Apple device; reads in `deviceTier`, `findSponsor`, `otherDevicesUsage`, `webAccount` try both; `usage.ts`, `costs.ts`, `apple.ts`, `session/*`, `admin/devices` use the header spelling; admin lists both rows. Many other namespaces embed the header spelling too.

**Namespace inventory.** Every key that embeds a device id, with its rule during and after B0:

| Namespace | Written by | Spelling today | Rule |
|---|---|---|---|
| `device:{id}` | usage, auth mirror | both | canonical lowercase; merged (below) |
| `auth:installation:{id}`, membership sets, replay guards, refresh records | auth store | lowercase | unchanged |
| `polar_sub:{sub}:devices`, `apple_sub:{otx}:devices`, `apple_sub_state`, `apple_sub_events` | webhooks, verify | header | members rewritten lowercase in the merge pass; readers lowercase before lookup |
| Polar `customer.external_id` | checkout | header (uppercase for Apple) | webhook lowercases before lookup; existing checkouts keep working |
| `session:{id}` body `deviceId` | session create | header | end compares case-insensitively; new sessions store lowercase |
| `session_end:{deviceId}:{sid}` | session end | header | read under both spellings for at least 35 days after deploy; preserve existing receipt retention and replay margin; write lowercase |
| rate-limit buckets keyed by device | `lib/ratelimit.ts` | header | lowercase from deploy; a device may get one fresh window, acceptable |
| `{google,attio,twenty}:token:{id}`, `*:oauth:state:*` payload `deviceId` | integration routes | header | **not renamed by B0**; readers try the lowercase key, then the **uppercase** key (not the raw header, which becomes lowercase once Swift changes and would hide old uppercase tokens) until B5 adopts them; OAuth state in flight keeps its spelling; Twenty uses a 10-minute Redis TTL, while current Google/Attio state has no configured expiry (reconcile stale callbacks under B5) |

If an audit of the repo finds a namespace missing from this table, B0 does not deploy until it is added. The [2026-11-10 source inventory](../research/ownership-source-inventory-2026-11-10.md) expands this summary with v2/index, legacy receipt, local-duration, diagnostics, provider-cost and administrative writers. It is preparation, not live inventory or AO0 acceptance.

**Proposed:** `getDeviceId` keeps returning the raw header; a new `canonicalDeviceId(raw)` lowercases, and every route uses it for keys, with `readDevice(id)` returning the canonical record merged with its uppercase twin while the twin exists.

**Order of operations:**
1. Deploy read-merge and canonical write routing together, where "canonical write" means: every write to `device:{lower}` goes through one Lua script, `adoptThenWrite`, that first checks a `baseline` field on the lowercase hash. If absent and an uppercase twin exists, the script copies the twin's counters and fields into the lowercase hash under the merge rules (subscription fields from the record with an active one, conflict → abort the write with `twin_conflict` and log; `accountId` and enrollment fields from lowercase; `createdAt` the earlier), computes a **period-aware baseline for the counters from both records inside the script**: a record whose `resetDate` is in the past contributes 0 to `minutesUsed` and `docsLookupsUsed` (its period is over), a record whose `resetDate` is current contributes its full counters, and the two current contributions are **summed**, as a retained gross baseline, without assuming the historical increments are disjoint; `minutesUsedLifetime` is always summed. **Billing-period policy when both are current with different reset dates** (one record on a Polar or Apple billing day, the other on the 1st): the merged `resetDate` and period are those of the record that holds the active subscription, else the later date; the other record's current counters are still summed in, because both windows overlap the merged period and neither record can say when its minutes were incurred. Because that sum can over-count by up to the smaller counter and stop someone recording before their real allowance is used, the script also writes `migrationCredit = the smaller current counter` on the merged record for the current period. **One effective-usage rule, everywhere:** `minutesUsedGross` is the stored sum; `effectiveMinutesUsed = max(0, minutesUsedGross − migrationCredit)`; every API response puts the effective value in `minutes_used` (the field old clients compare against `minutes_limit` themselves, `MinitiAPIService.swift:208`, so an old client with gross 600, credit 200 and a 500-minute allowance sees `minutes_used: 400` and 100 remaining, not a refusal) and adds `minutes_used_gross` for accounting; the server gates (`isAtLimit`, `/api/session`), the account aggregation (`otherDevicesUsage`) and B2's seed all read the effective value, and B2 records the credit it seeded through as `seedCredit` on the account period hash so gross can still be reconstructed. The credit is cleared at the next reset. In numbers: effective usage equals the **larger** of the two current counters (sum minus the smaller), which is the chosen customer-protective credit policy, not a reconstruction of actual usage; the digest lists each such pair (`merged_two_windows`). Ian confirmed D10 on 2026-11-10: use the larger current counter through this migration credit, not the plain sum. For 400 and 200, gross is 600, credit 200 and effective current-period usage 400. The script also appends every counter mutation from this moment, including the baseline itself, to a **journal** `device_journal:{lower}` (op, field, delta, period, at; 90-day TTL), which is what any later correction replays. The script then sets `baseline`, `mergedFrom` and `mergedAt`, renames the twin to `device:merged:{ID}` with a 90-day TTL, and only then applies the write. All in one script, so "uppercase 100, lowercase 0, increment 10" ends at 110; "uppercase 100, lowercase 120, increment 10" ends at gross 230, credit 100 and effective 130; "uppercase 100 with an expired reset, lowercase 0, increment 10" ends at 10. A device whose twin has no conflict is therefore merged at its first write after deploy.
2. Run the merge cron (`GET /api/cron/device-merge`, cron auth, heartbeat) for devices that have not written since deploy: the same script with a no-op write. Rerunnable; a hash with `baseline` is skipped, and nothing can have written to its twin since the rename.
3. The same pass rewrites the subscription reverse sets to lowercase. Pairs that aborted with `twin_conflict` are listed for Ian and keep reading through the merge view until a reviewed mapping and tested repair command resolve them; never hand-edit production records.

**Mixed versions:** old Apple clients keep sending uppercase; the server canonicalises, so their writes land on the canonical record from step 1. Linux already sends lowercase. No client change is required for correctness; Swift lowercases `X-Device-ID` in a later release for tidiness.

**Reconciliation:** ops-health gains `device_twins` (uppercase `device:` keys with a live lowercase twin; warn above zero after step 2) and `session_end_dual_reads` (count of idempotency hits found only under the raw spelling; informational).

**Rollback:** fix-forward from the moment step 1 is deployed, because live devices merge at their first write and a build that writes uppercase again would re-create the split and lose the increments written to the canonical record since. There is no redeploy-safe window after step 1 starts serving traffic. A correction script is written and tested **before** step 1 for the case where a merge rule turns out wrong; it restores the pre-merge values from `device:merged:*` and replays the journal from the merge onward, field by field, and never deletes the canonical record. Nothing is reconstructed from `session_end` stored responses: they carry cumulative account totals that include other devices (`session/end/route.ts:115`), not per-operation charges. A correction that the journal cannot support (a journal expired past 90 days) is limited to changes that keep the current counters. Deploy step 1 on a weekday morning with that script staged.

**Tests:** the three worked baselines above (110, 230, 10); both records current with different reset dates (Pro record on the 14th, free record on the 1st: period from the Pro record, counters summed, `migrationCredit` equals the smaller, `minutes_used` in the response is the effective value, `minutes_used_gross` the sum, the session gate and the account aggregation use the effective value this period and not the next, `merged_two_windows` recorded); **an old client receiving credited usage records normally at gross 600 and credit 200 on a 500 allowance; the account is then seeded and its remaining allowance is unchanged**; journal entries for the baseline and every later increment; merge rules per field including the conflict abort; first write after deploy merges, second write does not re-merge; idempotency across restarts mid-batch; header in either case reads and writes one record; webhook with uppercase `external_id`; session created uppercase before deploy and ended after; idempotency hit under the raw spelling; integration status for a device with an uppercase token key; admin report shows one row per device and `pro_devices` applies the sponsor overlay.

### B1: subscriptions owned by the account (miniti-api)

**Today:** Polar and Apple fields on the device record; `findSponsor` overlays at read time; restore and verify bind to any device; attach refuses same-rail conflicts at move time.

**Interim conflict guard lifetime:** the bounded 3.9.0 device fix ships at S0, before B1 writers. Read both UUID spellings for the moving device and destination members; reject only a different `polarSubscriptionId` or Apple original transaction on the same rail, and accept the same subscription on both devices. It performs no B0 merge. At S2, B1 cutover step 2 becomes the authoritative ownership-before-transfer guard; the interim check may remain as a conservative compatibility check while backfill completes. Remove it at S3 when B1 reads are authoritative, so source-account subscriptions cannot prevent a valid installation move. Final attach checks account ownership preconditions, not whether the destination has the same purchase rail.

Phase tests: S0 accepts shared subscription identity, rejects distinct same-rail identity, preserves cross-rail behavior and covers both spellings on both sides. S2 establishes source ownership before any permitted transfer and preserves the blanket old-client gate, including expired/cancelled subscriptions. S3 allows an authorized move between accounts with different subscriptions on the same rail, gives the device only destination-eligible Pro, and preserves renewal/entitlement on the source. No final-stage path still calls the interim rail-conflict check.

**Proposed authoritative record:** `sub:{rail}:{externalId}` hash: `accountId` (the owner, fixed at first bind), `purchasedByDevice`, `purchasePlatform`, `status`, `currentPeriodStart`, `currentPeriodEnd`, `polarCustomerId` or `appleEnvironment`, `productId`, `updatedAt`, `boundAt`, `boundVia` (checkout, verify, restore, backfill). Index `auth:account:{id}:subscriptions`. The device record keeps its mirror fields during migration.

**Ownership rules:**
- **Owner of a new `sub:` record, one rule everywhere:** checkout attribution if the webhook names a checkout we recorded; else, for a subscription id already on a pre-B1 device record, that device's current account (transfers of such devices are blocked until the record exists, cutover step 2); else `unresolved_owner`, which grants nothing and is listed. Current membership is never used for a new purchase.
- **Checkout attribution at start.** B6d already shipped account capture in `GET /api/subscribe`, Polar metadata and a seven-day `checkout:return:{checkoutId}` correlation record. Reuse/reconcile that verified implementation rather than inventing another attribution namespace. B1 still must bind the first subscription webhook to that captured account in `sub:`, not to wherever the device is by then; purchase-return readiness alone does not implement durable ownership. Apple: `/api/apple/verify` binds to the presenting installation's account at first verification.
- **Renewals, cancellations, refunds, grace, billing retry** update the `sub:` record by `(rail, externalId)` and never consult installation membership. A subscription whose buying device has since moved keeps renewing for its owner account.
- **Binding a subscription that already has an owner** from a device on a different account (restore with a license key, verify with a restored receipt, a webhook for a known subscription arriving with a different attribution) is refused: `409 subscription_owned_elsewhere`, generic message "This subscription belongs to another miniti account. Sign in to that account to use it." No transfer happens here (D3).
- **Duplicates:** `/api/subscribe` keeps refusing a Pro account; verify and restore refuse a second active subscription on the same rail for the same account (`409 already_subscribed`); cross-rail stays allowed under confirmed D4. With two active records on one rail, the earlier `boundAt` wins deterministically and ops-health warns `duplicate_subscriptions`.
- **Entitlement:** `accountEntitlement` reads the account's subscription set first. During migration it may still read a device's mirrored Polar or Apple fields, but only when **no `sub:` record exists for that subscription id**, or the record's owner is the account being evaluated. A device that bought on account A and now sits on account B therefore grants nothing to B, because `sub:{rail}:{id}` names A. The same rule governs the rollback path: reverting the read order is allowed only as "device fields, filtered by owner", never raw device fields. Per-consuming-device eligibility keeps `sponsorEligible` (Apple on iOS only, Polar anywhere).
- **Polar webhooks** gain `event.id` idempotency (`polar_event:{id}` SET NX 14 days, the Apple pattern).
- **Attach after S3** neither moves subscriptions nor applies the interim same-rail conflict check. It retains source-ownership preconditions and the capability/version gates.

**Polar correlation and bounded diagnostics gate:** current `app/api/webhooks/polar/route.ts:60–85` links by `external_id` and does not consume `miniti_checkout_account` metadata. The seven-day `checkout:return:` record may expire before a delayed first bind or backfill. Before B1 writers, verify provider-authenticated checkout/subscription metadata correlation and `external_customer_id` case preservation with synthetic/provider evidence. Persist verified owner attribution into the durable `sub:` record at binding; for delayed first binds after return-record expiry, require provable provider metadata or another explicitly designed durable capture. Missing evidence means `unresolved_owner`, never current membership. Do not silently invent an unverified nonce/join or a new `checkout_attr` namespace. Set and document durable pre-bind retention/reconciliation before coding if metadata alone is insufficient. Tests cover day-8 first webhook, delayed backfill, replay after TTL, missing/contradictory metadata and mixed-case external IDs.

`route.ts:57` currently logs 500 characters of raw webhook data. B1 replaces this with bounded structured fields: allow-listed event type/outcome, idempotency/reconciliation result and non-identifying correlation suitable for debugging. No raw payload fragment, customer email/name, token, checkout secret or provider error body. Test a payload containing customer details and assert they never enter logs, including failure/replay branches. Truncating raw content is not redaction.

**Backfill:** cron walks canonical `device:*` and writes `sub:` records for every device naming an identifiable subscription, including expired, cancelled and grace states, `boundVia: backfill`. Owner comes from the source binding protected by step 2, including the pre-revocation account for a revoked/re-created installation; never blindly read the replacement installation's current account. Establish the source at S2 under the same serialization as membership/re-enrollment changes, retain it durably until adoption/reconciliation completes, and bind before overwriting it. An unchanged installation record can supply the source; an overwritten record without trustworthy retained evidence cannot. A device with no provable source stays unbound and listed for D9. This does not invent historical owners for pre-S2 transfers. Idempotent on `(rail, externalId)`. Two devices on different accounts claiming one subscription: logged, left unbound, listed for D3. **Ian's own case is one of these** (one Polar subscription linked to Mac records on two of his accounts, found 2026-10-26): before the B1 cutover a reviewed mapping file names the intended owner for every listed collision, and the backfill applies it; it will not pick the owner on its own.

**Mixed versions:** existing successful response fields and `entitlement_via_account` keep their meanings; capability metadata is additive. Attach/email-join/restore-into-account and create reusing a previously bound installation gain the blanket 426 `update_required` gate at S2. Server-proven same-account repair and exact authorized replay retain the release's narrow exception; genuine new-ID create remains supported without adopting old assets. The original unknown-code Apple rendering is explicitly accepted; verify old Linux behavior. These routes must refuse before any identity mutation or single-use approval consumption. Ordinary usage/recording remain supported. Compatible apps must be public on all three platforms before S2. See the release stage/publication matrix, including the bounded pause and separate conditional iOS minimum-version decision for owned-elsewhere verify loops.

**Reconciliation:** nightly, every active `sub:` has an owner that exists (active or dormant); every device-field subscription has a `sub:` twin with the same status and period.

**Cutover, in this order and no other:**
1. **Writers first, correct while the backfill is incomplete (S2).** Enable the blanket platform/version transition gate and advertise `preparing` before changing ownership behavior. Deploy webhooks, verify and restore writing device mirrors plus `sub:`. For a missing `sub:`, choose its owner by the same rule as above: (a) verified checkout attribution captured at `/api/subscribe`, reusing `checkout:return:{checkoutId}` (seven-day TTL) and `miniti_checkout_account` metadata after the provider correlation is proven; (b) an identifiable pre-B1 legacy subscription uses the source account protected by step 2; (c) otherwise `unresolved_owner`, no entitlement. Current membership never supplies attribution for a new Polar purchase. The return record alone cannot prove a day-8 first bind: use verified provider metadata or the explicit durable pre-bind design required above; absent proof stays unresolved. Apple first verify binds a never-seen original transaction to the authorized presenting account under the purchase/verify flow, with the recommended `appAccountToken` design evaluated separately; a known owner never changes on restore. Backfill runs through durable `migration:sub_backfill` progress (`pending` → `complete`), not an instance-start hook. Preserve owner evidence when writes/first replies fail. Partial stages defer compatible end-user transfers until S5 while internal precondition/backfill tests still exercise source ownership.

2. **Ownership before any transfer or re-enrollment, for every identifiable subscription.** `attach`, email join, restore into another account and **create on a previously bound device ID after sign-out/removal** gain the same precondition. A device whose canonical record names **any** Polar subscription id or Apple original transaction id, active, expired, cancelled or in grace, with no `sub:` record yet, **cannot change accounts or replace its source binding** until the route has created that record with the proven source owner, inside the tested account-serialization protocol. For a revoked installation that is its retained pre-revocation account, never the newly created destination. Revoke/cleanup must preserve this evidence; `writeInstallation` must not erase it before B1/B2/B5 adoption. Serialize create, revoke, restore, transfer and backfill against one another; an account-only lock that permits a concurrent installation rewrite is insufficient. Missing or contradictory evidence is unresolved and blocks adoption, not permission to infer a new owner. Same-account repair preserves the source and credentials' authorization rules. Fresh rotated IDs have no right to old-ID assets. Ownership and entitlement are separate: an expired subscription still has an owner, so a later reactivation grants the account that held it. The backfill's scope includes every identifiable subscription id. This replaces the interim conflict check's responsibility at S2; remove that old check at S3. Stage/capability readiness still defers end-user account changes until S5.
3. **Reads last.** Only when `migration:sub_backfill` is `complete` and the reconciliation check has been green for 24 hours does `accountEntitlement` start preferring `sub:`. A cancellation or renewal before that point updates device fields (which are still authoritative) and the `sub:` record together, so no stale record can be preferred.
4. Stop writing device fields after one full billing cycle without warnings.

### B2: usage charged to the account (miniti-api)

**Today, revalidated 2026-11-09:** per-device counters and reset dates still determine the account total at read time. Shipped 3.8.0 `managedAccounting.ts` already stores original account/device and the exact usage-storage key, with atomic v2 finalization; `legacyAccounting.ts` also finalizes atomically. V2 roots/receipts have 35-day retention, while client reports are bounded to 30 days. These protect recording accounting but do not implement an account-owned period ledger. The [metering contract](managed-reconnect-metering.md) is the regression baseline.

**Required reconciliation before B0/B2 implementation:** the proposed attribution/seeding design below predates that baseline. Inventory v2 roots/indexes, legacy receipts, reset writers, local-duration reporting and paid Watch results alongside the B0 namespaces. Define how an active v2 root retaining an uppercase `storageDeviceId` resolves after canonical adoption without recreating the twin. Preserve the existing 35-day replay margin; B2 attribution must retain at least that margin and must not silently shorten existing receipts. Define authorization for settling A's pending work after a device joins B, since current v2 finalization requires current membership in A. Original attribution alone must not authorize reading A's receipt through B. Also define period selection for already-running sessions and at cutover. These are open migration design gates, not permission to replace the shipped charging path or relax its owner checks.

**Proposed authoritative record:** `usage:account:{acct}:{period}` hash (`minutesUsed`, `docsLookupsUsed`, `sessions`, `prerecordedMinutes`, `updatedAt`); `period` is `YYYY-MM` for free accounts or `{rail}:{externalId}:{periodStartISO}` for Pro, derived from the account's `sub:` record (B1). `auth:account:{id}` gains `currentPeriod`, `periodEndsAt` and `usageLedgerSince`.

**Attribution:** session create and prerecorded create write `session_attr:{sessionId}` = `{accountId, period, deviceId}` with a **35-day minimum retention matching the shipped v2 replay margin**, independent of short-lived provider/session records. End charges the attribution's account and period, subject to the finalized authorization contract above. An end with no attribution record (expired or created before attribution support) is **unresolved**: bounded diagnostics and ops counts, **not charged to anyone**; never report an accepted duration that was not actually recorded. Preserve version-specific missing-session/error semantics while finalizing this migration. Docs lookups capture the authorized account and UTC month at request admission, with an idempotency key per actual lookup operation, under the cutover contract below.

**Atomicity:** one Lua script per end: if the idempotency key exists, return the stored response; else `HINCRBYFLOAT` on the account period hash and, while that account is dual-writing, on the device record; `SET` the idempotency key with TTL; return. Tested with the fake KV used by the existing route tests plus one run against a real Upstash database in CI (`SYNC_TEST_DATABASE_URL`-style gating) because script semantics are what matter.

**Limit check:** `isAtLimit` reads the account period hash when `usageLedgerSince` is set, else today's device sum.

**Period regression required (review follow-through, 2026-11-10):** given a stale twin with 400 minutes and a current-period twin with 200, the opening effective contribution is 200, not 0 or 400. Apply period eligibility to each twin before the D10 larger-current-counter credit. Cover both spellings, reversed larger/smaller values, both expired, differing current period boundaries and the subsequent reset/seed. The current `otherDevicesUsage` reader chooses a twin before checking its reset date and can drop the current smaller contribution; that inherited read behavior is not the migration contract.

**Seeding, per account, atomic, and claimed per device:** one script under the `account:{id}` lock reads the current members' device counters (canonical records, B0 is a prerequisite), **skips any device whose record already carries `usageClaimedBy`**, writes the current period hash with the members' **effective** usage (gross minus any migration credit), `seedCredit` as the sum of credits applied, `seededFrom: devices` and `seededAt`, sets `usageLedgerSince` on the account, and stamps every device it counted with `usageClaimedBy = {accountId}` and `usageClaimedAt`, all in the same script. A device's historical counters can therefore be seeded into exactly one account, ever. From that moment ends for this account take the ledger path; increments before the seed were in device counters only and are inside it; increments after go to the ledger (and, for one cycle, the device record for legacy readers, which the claim marker tells every reader to ignore for account totals).

**Membership changes during the rollout.** Every path that changes membership (`attach`, email join, restore into another account, create reusing a revoked installation ID, revoke of a last device) runs **inside the seeding protocol**: before the membership write, it seeds the source account if unseeded and the destination account if unseeded, under both account locks in a fixed order (lexical by account id, to avoid deadlock). The worked sequence "A seeded with the device's 100 minutes; device moves to B, unseeded; B's seed reads the same 100" cannot occur: B is seeded before the move, and even if it were seeded later the device's `usageClaimedBy = A` excludes it. Late charges go to the attribution's account (above), never to a device mirror; the device-sum fallback used by unseeded accounts also excludes claimed devices, so a mirror cannot leak claimed minutes into an unseeded destination. Seeding of idle accounts runs from a cron, idempotent on `usageLedgerSince`.

**Reconciliation:** not against device sums, which are expected to diverge once devices move, and not against stored `session_end` responses, whose `minutes_used` is a cumulative account total rather than the session's charge. The metering script also appends one **charge record** per operation, `usage_charge:{acct}:{period}` hash keyed by session or lookup id → minutes charged, with the same 90-day retention as the period hash (long enough for the longest billing period plus the 30-day late window). Reconciliation per account and period is: `seededFrom` opening balance + sum of charge records = ledger, within one minute. Unresolved entries are reported separately and are not in either side.

**Rollback:** limited. Before an account is seeded, nothing changes for it. After seeding, the ledger is authoritative; reverting reads to device sums would reintroduce the attribution bug, so rollback for seeded accounts means fixing forward. The dual-write to device records continues for one cycle only so that admin and the old summation keep working, not as a rollback path.

**Tests:** session on A, device attached to B, end charges A; end 20 days later still charges A; end with no attribution is unresolved and uncharged; two concurrent ends charge once and write one charge record; retry after the script ran returns the stored response and writes no second charge; prerecorded minutes; docs lookup idempotency; period rollover changes the key without zeroing; seeding script with concurrent ends before and after; **the A-seeded, device-moves-to-unseeded-B sequence charges 100 minutes once**; a device claimed by A is excluded from B's seed and from B's device-sum fallback; attach seeds both accounts before the membership write, in lock order; reconciliation of opening balance plus charges (two 10-minute sessions reconcile to 20, not 30); limit check on both paths.
