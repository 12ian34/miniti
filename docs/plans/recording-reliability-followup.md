## Confirmed defects and limits

### 1. iOS readiness requires an impossible source

`AppState.beginRecordingDiagnostics` copies the shared default-on `captureSystemAudio` preference. `sampleRecordingDiagnostics` requires every requested source's PCM. The iOS `AudioCaptureService.hasRecentCaptureBuffers` deliberately returns false when system audio is requested. Consequently, an otherwise working microphone session never becomes ready and `finishRecordingDiagnostics` labels it cancelled. The same source predicate prevents the strong recovery event on iOS.

Fix with one platform-valid capture-source snapshot per attempt, reused for readiness, recovery and reporting. On iOS it is microphone-only regardless of the unused system preference. Do not rewrite a person's stored Mac preference or relax checks for genuinely requested Mac sources. Separate lifecycle outcome (stopped, failed, cancelled) from transcription outcome (no speech evidence, words received, speech without words, interrupted). This prevents fixing the label from concealing the no-transcript problem.

Sources: `Miniti/Models/AppState.swift` (`beginRecordingDiagnostics`, `sampleRecordingDiagnostics`, `finishRecordingDiagnostics`, `applyAudioRecoveryState`); `MinitiMobile/AudioCaptureService_iOS.swift` (`hasRecentCaptureBuffers`).

### 2. Connected, audio flowing and words arriving are different evidence

`handleDeepgramConnectionState(.connected)` clears/cancels reconnect work. `updateAudioRecoveryState` can then report healthy without a new transcript; its recent-capture validation is currently Mac-only. `RecordingDiagnosticAttempt` accumulates booleans across the attempt, so old PCM/transcript evidence cannot prove a later recovery. `sendAudio` increments the packet count before its asynchronous send completes, and uses the same count for local ingestion. The current `pcm_sent` flag means a send/ingest was attempted, not server receipt or successful decoding.

Retain separate capture, transport/local-ingest and transcript progress markers with connection/recovery generations. Report connection restored promptly, but only report transcription resumed after a new non-empty transcript for the current recovery. Quiet periods remain neutral; absence of words alone must not produce an error. A recent successful send callback is stronger transport evidence than an attempted packet, but still does not prove provider receipt. Keep legacy `recording_recovered` semantics compatible with the backend; introduce additive evidence rather than silently redefining an existing event.

### 3. Recovery evidence is stripped or ambiguous

The Swift producer emits `gap_seconds`, `audio_gap_seconds`, levels, free-form reconnect `reason` and `max_attempts`. `lib/clientDiagnostics.ts` discards those keys/values under its allowlist. Most connection/starvation events carry no attempt ID or actual-engine field. Intentional `disconnect()` during restart publishes disconnected, and the app reports that as `deepgram_unexpected_disconnect` while recording. Local restarts pass through the same naming path. These events must not be counted as independent network failures.

Use bounded structured evidence: attempt UUID, actual engine, connection/recovery generation, a fixed reason code, integer gap durations and progress counters. Add explicit units/bounds; keep raw error strings, audio and transcript out. Carry the same fields through the producer, ingest sanitizer, local support-report sanitizer and admin reader. Deploy additive backend acceptance before the client. Mark planned restart separately from unexpected closure. Preserve build/version attribution for queued reports; request-time app version alone can change after an update.

Synthetic probes against the actual backend functions confirmed that the current sanitizer drops gap/reason/max-attempt fields and that `buildUsageChart` counts uppercase/lowercase aliases twice. Two temporary Vitest probes passed using the in-memory KV stub; probes were removed afterward. This is reproduction of existing behavior, not a fix or real-Redis test.

### 4. Recovery can discard audio and pending words

Confirmed code paths, with their contribution to the observed iPhone attempt still unproven:

- `sendAudio` drops incoming buffers while `_sendConnected` is false. Capture starts without waiting for the cloud handshake and continues through reconnect. The send path has no replay queue, so a 1–2 second reconnect is not evidence of zero audio loss.
- `stopRecording` only uses `gracefulDisconnect()` when it already sees text. With no visible text it disconnects immediately, abandoning any pending provider/local output. The attempt diagnostic is finalized before either path settles.
- Starvation restart also disconnects without draining. The existing graceful close waits briefly and can exit on the first final; do not assume that it covers every source's tail in a dual-source session.
- The watchdog uses audio energy, not confirmed human speech. Noise can satisfy its threshold. It restarts after a transcript gap exceeding 20 seconds, with checks every four seconds. After the first recovery, the connected-path cooldown doubles from 30 to 60 seconds. iPhone A stopped 56 seconds after its first restart, before that next restart could be eligible even with qualifying audio activity.
- The reconnect loop waits roughly three seconds before advancing to the next backoff step, while the service's initial-connection timeout is 12 seconds. The next retry can replace a still-connecting task before that timeout. Align the retry owner with connection completion/failure so a slow valid attempt is not repeatedly replaced. Keep task cleanup generation-aware; cover an old cancelled task finishing after replacement work starts.

First reproduce these boundaries with controllable transport/local-engine fakes. Give a started attempt a bounded final flush even if no words are visible, then classify and persist its final result with existing meeting/deletion/account fences intact. Do not add a generic long wait or reopen saved-AI/webhook ownership. Distinguish a transport failure from healthy capture with delayed words; retain bounded backoff and a visible unresolved-transcription state instead of simply reconnecting more often.

A small in-memory buffer for audio captured while the connection is not ready is a possible follow-up, not an automatic fix in this scope. Before selecting it, define memory/time caps, overflow disclosure, ordering, timestamp offsets, speaker alignment and no duplicate replay. Do not replay audio already submitted to a zombie connection without an explicit overlap/deduplication contract. A local session must never fall back to cloud mid-meeting.

Sources: `AppState.startRecording`, `checkTranscriptHealth`, `evaluateTranscriptHealth`, `scheduleDeepgramReconnect`, `stopRecording`; `DeepgramService.sendAudio`, `connect`, `connectLocal`, `disconnect`, `gracefulDisconnect`.

### 5. A single speech-without-transcript attempt can escape incident classification

The final record is an info-level `recording_final`, which has no incident family. Current recording incidents normally require qualifying failures in three distinct ten-second windows, or an already-defined terminal failure. One starvation warning plus a final no-transcript outcome can therefore remain below the alert threshold. Changing cancelled to stopped alone does not repair this evidence gap.

After final drain and a validated producer contract, emit a bounded explicit outcome for an attempt with substantive speech evidence but no words. Show it in the admin investigation view; decide its severity/notification policy from controlled fixtures, with ordinary silence and noise excluded. Do not classify all older cancelled sessions as failed transcription or add an unconditional email per empty recording. Preserve existing hourly cadence, deduplication and alert cooldowns.

### 6. Activity reporting treats casing aliases as different devices

`lib/usage.ts` adds caller spelling to daily active sets; `lib/adminUsage.ts` returns set length; `lib/opsDigest.ts` unions raw IDs; dashboard filters and active-day joins compare raw IDs. A chart-only lowercase fix leaves filters/digest/leaderboards inconsistent.

Normalize identities for analytics writes, reads and joins; deduplicate daily/period active sets; choose latest-seen version metadata deterministically and preserve unknown/tied cases. Preserve all numeric usage contributions when grouping per-day hashes, rather than dropping one alias. Keep authoritative global totals unchanged. Do not rewrite device/billing keys, sum conflicting entitlement snapshots or infer historical registration counts from aggregates: full record ownership/registry repair remains in its existing plans. Distinguish raw records from normalized installations in the device report until that migration has an explicit contract.

### 7. Backend completion does not explain client AI failure

The five new warnings are observed failures at the client boundary, not confirmed provider/model defects. Add a bounded investigation of live and final AI request construction, transport, response decoding and result application, using controlled fixtures and content-free request correlation where available. Identify expected cancellation/supersession separately from genuine transport, auth/admission, decoding, provider and persistence failures. An absent matching backend request remains unknown, not proof of any one cause.

Define an allowlisted diagnostic contract with task mode, live/final/saved stage, fixed failure category, HTTP status when known and bounded opaque request correlation. Preserve account/private-mode and consent boundaries; do not attach prompts, transcripts, generated content, credentials or raw exception messages. Carry fields through backend ingest and Help sanitization before a new client emits them. Correlation may be absent on legacy events or pre-network failures. Preserve API response shapes and bounded retries unless reproduction demonstrates a specific necessary correction.

Acceptance requires successful server response followed by client decode failure, network loss/timeout, legitimate cancellation or stale authority, and final-summary failure fixtures. A valid current response must apply once; stale work must remain fenced; failed summaries must not erase transcripts or block configured webhook settlement. Separate truthful reporting from reproduced functional fixes. Do not automatically replay customer requests or add cross-model retries. If the original warnings remain unexplained, record that limitation rather than declaring them fixed because new telemetry exists.

## Accepted impact and implementation boundaries

- Performance: use bounded counters and transition-based diagnostics, not per-buffer events or a heavier model. Measure CPU/memory and recording responsiveness against the released baseline; negligible overhead is an expectation to validate, not a measured result.
- User experience: normal recording should feel unchanged. Stop may briefly show finishing-transcript status for an initially empty attempt while a bounded flush completes. Retain the existing platform/engine close budget initially, removing the text-present prerequisite and first-final shortcut where they truncate tails; measure before changing the budget. Stop capture before draining, keep local diarization/transcription output valid until drain or deadline, then finalize diagnostics and saved output once. No indefinite wait or second final-AI/webhook completion owner. Show unresolved transcription while recording continues, without treating ordinary silence as a failure.
- Transcript quality: preserve pending words and distinguish resumed transcription from a reopened connection. This improves completeness, not recognition accuracy, and cannot recover audio already discarded. Tests must reject duplicate finals, incorrect timestamps and late output applied to another meeting.
- Reliability: validate stop/cancellation, stale callback and account/deletion boundaries. Success means better saved output and fewer unnecessary restarts, not simply fewer warning events.
- Cost: this reliability work retains existing models, routine AI-call cadence, allowances and Deepgram cost accounting; the separately selected retirement plan owns model changes. Bounded final flush finishes the existing session. Metadata reporting adds bounded backend writes/storage; measure it without promising a specific saving or zero provider-cost change. Local-minute visibility does not consume managed transcription allowance; existing cloud AI costs remain.
- Privacy: keep diagnostics content-free and consent-gated. The usage plan separately counts all managed duration, including local/private recordings, independently of Share diagnostics, with BYOK excluded as confirmed 2026-11-03. No new audio or transcript upload is authorized by this reporting work.
- Audio buffering/replay is excluded from the first delivery. It needs separate selection and evidence for memory caps, overflow, duplicate prevention, timing/speaker alignment and additional provider usage.

## Initial local implementation, 2026-11-03

Stop now enters finalization before deciding an empty recording has no content. Capture stops first; a bounded drain accepts late finals from both sources, then buffered segments and visible interim text are settled before diagnostics, voice learning and persistence. Socket CloseStream sending is asynchronous within the existing 800 ms receive window, so a stuck send cannot hold Stop indefinitely. Local recognizer finishing is bounded to two seconds and abandoned afterward; real-model tail coverage at this limit still requires device validation. A first final no longer ends the window early. Connection generations prevent an abandoned drain from disconnecting replacement work. Empty recordings still create no persisted meeting.

Reconnect waits for the active connection attempt's terminal state/timeout instead of replacing it after three seconds. Cleanup only clears the matching recovery task, and credential-await cancellation/recording guards prevent an abandoned attempt from reconnecting. iOS diagnostic attempts request only microphone PCM, never system audio. Diagnostics settle after drain; discard/account transitions close an abandoned attempt before the next starts.

Controlled tests cover late first words, two source tails, duplicate Stop, a held close, replacement connection fencing, bounded connection wait and replacement rejection. The full isolated macOS suite passed at `Test-Miniti-2026.11.03_12-10-01-+0000.xcresult`; subsequent discard/diagnostic cleanup passed focused meeting/delivery checks, and the iOS test bundle compiles. This is not full plan completion: shared diagnostic schema, truthful recovery UI, failure-stage correlation, analytics alias normalization, richer outcomes, physical iPhone reproduction and local/speaker fault cases remain pending. No audio replay or mid-session cloud fallback was added. The reported iPhone/client-AI incident causes remain unknown.
