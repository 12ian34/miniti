## Decisions taken while planning

- **Historical version decision:** keep 3.4.0 while preparing build 139, before publication (the Mac DMG had been 137, TestFlight 138). Final delivery is build 141. `CURRENT_PROJECT_VERSION` and `CFBundleVersion` are set by hand before the Mac lane, as RELEASE.md step 1 says.
- **Order: U2, U1, B6a.** Smallest and most isolated first. Each slice is one commit series, reviewed by Astra, with its findings fixed before the next starts. The B6a backend change goes first within B6a so the client is tested against the deployed contract.
- **U2 keeps consent version 2.** Recipients (Deepgram, OpenAI), data categories and purposes do not change; the rewrite drops claims that were not true ("audio is never stored", "nothing leaves this device") and shortens the rest. Nobody is asked again. If implementation finds a recipient, datum or purpose that was missing from version 2, the version is bumped deliberately and this file says why. Keeping the version says nothing about whether every dispatch path honours the answer: that is the wider R2 audit, still deferred. The known History/Watch bypasses joined 3.4.0 on 2026-10-27 under the narrowed reliability scope; U2 must not claim a complete audit.
- **Email guard, per operation.** `GET /api/account/email` keeps bearer authentication without proof (shipped clients sign only writes); `POST` and `DELETE` keep the proof requirement. Configured email delivery gates `POST` only; reading and removing an address work while delivery is down. All three drop the Pro check, the cloud rollout allowlist and the person's cloud switch. BYOK stays refused (`cloud_requires_managed`). The server-wide `CLOUD_SYNC_ENABLED` switch and the store check still apply because the address lives in the same store; they are operator guards, not user gates.
- **Email state is two addresses, not one.** The server deliberately returns the verified address and a pending replacement together; the client keeps both. An account with a verified address is protected until that address is removed or replaced, whatever is pending.
- **Account surfaces read one state.** The shared Cloud section (compiled into both apps), the Cloud enable sheet's optional email field and the API tab's "add an email in Cloud" guidance all move to the shared `AccountEmail` state or link to Settings, Account. Web sign-in and new-device approval keep working exactly as today with the account's email, and the browser confirmation handoff (`.minitiCloudCallback`) is preserved and now refreshes the shared state.
- **The Home card trigger is "first saved meeting on an enrolled managed account".** Today the key nudge shows as soon as the account exists. Moving it after the first meeting is what B6a specifies; the first launch stays uninterrupted.
- **Not in this batch:** A4's choice state, any change to automatic enrollment, account merge, compulsory email, B1 subscription ownership, the Linux implementation (a note in `../miniti-linux/PLAN.md` only), R4–R8 and the wider R2 audit. On 2026-10-27 Ian added the auth persistence follow-up, R1, narrowed R2 and R3 as separate pre-release fixes in the reliability plan; they were implemented and delivered in build 141. U1 describes routing; the wider R2 audit remains deferred.

## B6a: visible account identity and optional email

### Backend first (miniti-api)

**Files:** `lib/cloud.ts` (an option on `requireCloudDevice`, `{ accountEmail: true }`, that skips the allowlist and tier checks and nothing else), `app/api/account/email/route.ts` (uses it; `GET` without proof as today, `POST` and `DELETE` with proof as today; `emailConfigured()` checked in `POST` only, as today), `app/signin/confirm/route.ts` (unchanged: it consumes a `confirm_email` link and needs the store, not the allowlist), `app/api/auth/email/start|status` (unchanged: they already run on the store guards and their own limits), `docs/agents/08-cloud.md` (the email contract moves to "any managed account"), the route tests.

**Contract.** `GET /api/account/email` answers `{ email, pending }` for any enrolled managed device with a bearer: 401 without device auth, 403 `cloud_requires_managed` for BYOK, 503 `cloud_unavailable` when the store or the server switch is off, 429 on the per-account limit. `POST` additionally needs proof and configured delivery (503 `email_unavailable`), keeps 409 `email_in_use` and 202 with `pending`. `DELETE` needs proof, works with delivery down, still revokes web sessions and connected apps and still says how many. The web sign-in page, tokens, connected apps, sync push and pull keep every gate they have.

**Tests.** A free account with the cloud switch off and no allowlist entry adds, reads and removes an email; an account outside the allowlist adds an email and is still refused on `/api/cloud/*`; BYOK refused; store off refused; an unsigned `GET` from a 3.3.0-shaped client (bearer only, no proof header) answers 200; `GET` and `DELETE` answer 200 with delivery unconfigured while `POST` answers 503; the existing collision, pending and removal tests pass unchanged. Then `vitest`, `tsc`, `eslint`, push (deploys), confirm with a curl against production from an enrolled free account before the client work starts.

### Client state (`AppState`, `MinitiAPIService+Cloud.swift`)

```swift
struct AccountEmail: Equatable {
    var verified: String?      // the address on the account
    var pending: String?       // a replacement awaiting its link, nil when none
}
enum AccountEmailState: Equatable { case loading, unavailable(String), loaded(AccountEmail) }
```

Published on `AppState` as `accountEmailState`. `loaded(AccountEmail(verified: nil, pending: nil))` is "no email yet"; `loaded(.init(verified: a, pending: nil))` is verified; `loaded(.init(verified: nil, pending: b))` is first verification pending; `loaded(.init(verified: a, pending: b))` is verified with a replacement pending, shown as both. "Protected by email" is `verified != nil`, whatever `pending` holds.

**Generation and ordering.** `AppState` keeps `accountGeneration: Int`, incremented whenever the enrolled account id changes, on sign out, on revoke, and on every email mutation (add, remove, resend) so that an older read cannot overwrite a newer write. Every request captures `(accountID, generation, sequence)` before it starts; a response is applied only when the generation still matches and the sequence is the latest issued for that generation, otherwise it is dropped and logged at debug level. A failed fetch sets `.unavailable(message)`, never `.loaded(empty)`; a provider error on add or remove keeps the previous `.loaded` state and surfaces the error beside the control with Retry. A-to-B-to-A is tested: A's original in-flight response is dropped because the generation moved twice.

**Refresh points.** `refreshAccountEmail()` runs on enrollment, when the account generation changes, when Settings, Account or the Cloud section appears, after each mutation's response, on `.minitiCloudCallback` (the browser confirmed the link and handed back), and on app activation (`NSApplication.didBecomeActive` / `UIApplication.didBecomeActiveNotification`) for every enrolled managed account whatever the current state (`loading`, `unavailable`, no email, pending or verified), coalesced to one in-flight request and skipped when the last successful load is under 60 s old, so a link opened on another device clears "Check your email" here, a device that last saw "no email" picks up an address added and confirmed elsewhere and drops its access card, and a device that was offline retries on the next activation instead of staying "unavailable". The three API calls move off the cloud-gated path: they use the ordinary managed request path and do not check `cloudSyncEnabled` or the pause reason.

**Surfaces that change.** `CloudSettingsSections` (shared, both platforms) stops holding its own `email` and `pendingEmail` and renders from `accountEmailState`; its add and remove controls go, replaced by "Email: Settings, Account" with a jump (Mac) or a link (iOS). `CloudEnableSheet` keeps "turn on cloud" and drops the optional email field; when the account has no email the sheet says web sign-in needs one and offers "Add email first" (opens Account) beside "Turn on without email". `APIAccessSettingsView` reads the shared state and its guidance becomes "Claude and ChatGPT sign you in with the email on your account. Add one in Settings, Account." with the jump. The callback handler keeps posting `.minitiCloudCallback`; nothing about the link flow changes.

**Persisted per installation, keyed by account id:** `accessCardDismissedAt`. `showRecoveryKeyNotice` is replaced by `showAccessCard`, true only when: managed and enrolled, `accountEmailState` is `.loaded` (loading and unavailable suppress it), `verified == nil`, at least one meeting saved on this installation, not recording, recovery key not acknowledged for the current key, not dismissed for this account. Key rotation clears the acknowledgement; the existing `markRecoveryKeyAcknowledged` stays.

### Signing-probe decision (F3)

The local probe is the chosen implementation. A refresh-token grant is unsigned, even if described as a token refresh, and `/auth/challenge` only issues a nonce. Neither alone tests signing. If a later requirement calls for server verification, the existing protocol is `/auth/challenge` with purpose `token`, followed by `/auth/token` with `grant_type: "challenge"`, the challenge ID and the signed proof. That would need its own token/concurrency handling; do not use `grantChallengeOrRebind` for this retry, since its fallback can rebind. A successful local probe means the original key can sign again; it does not assert that the server still accepts the installation.
